# 项目地图

> **这是什么**：Harbor 由哪些层组成、每层干什么的一张导览图 —— 给「刚接手 / 隔几天回来 /
> 想估个活该放哪」的人一个方位感。想知道「某件事该读哪份」看 [`README.md`](README.md)；
> 想知道「一次对话在代码里怎么走」看 [`架构.md`](架构.md)。
>
> **本文刻意不写任何计数。** 文件数 / 行数 / 测试数这类数字**每版都会涨**，抄进来必然过期
> （`AGENT.md` 硬约束 8：会涨的数字只准出现在「一份定义 + 命令输出」里）。要数字 →
> 跑 [`npm run map`](#一条命令拿整张图)，它才是「现状」的真相源。**本文只讲结构 —— 结构稳定，数字会漂。**

## 一、四层骨架

Harbor 大致分四层，越往下越靠近机器：

| 层 | 目录 | 干什么 |
| --- | --- | --- |
| 界面层 | `src/` | React 组件 + 状态（store）+ 纯逻辑。用户看得见的一切 |
| 内核层 | `electron/` | 主进程。**业务逻辑全在 `core/`**，IPC 处理器在 `handlers/` |
| 工具链 | `scripts/` · `tools/` | 自检 / 安全 / 规则检查 / 行数红线 / 截图 / 验收 |
| 文档 | `docs/` | 设计稿 / 踩坑 / 数据模型 / 安全模型 / 架构 … |

**界面层是最大的一块** —— 这是「把界面当产品做」的应用，不是 CLI 套壳。
各层占多少（文件数 / 行数 / 谁占多少）→ `npm run map`。

## 二、界面层 `src/`

| 子目录 | 是什么 |
| --- | --- |
| `components/` | 所有可见组件。按功能区分：`chat/`（对话，最大）`settings/` `layout/` `ui/` `boot/` `onboarding/` `dialogs/` |
| `stores/` | 状态管理（`useAppStore` / `useUIStore` / `thread/` …） |
| `lib/` | 纯逻辑 / 工具（无 UI） |
| `hooks/` | React hooks |
| `types/` | 类型定义 |
| `constants/` | 常量（含**设计 token** —— 值的唯一来源是 `constants/design.ts`） |
| `assets/` · `styles/` | 图片 / 字体（二进制，不计行数）· 全局样式 |

## 三、内核层 `electron/`

- `core/` —— **全部业务逻辑**。
- `handlers/` —— IPC 处理器。
- IPC 通道清单：**每版都会涨** —— 唯一定义在 `electron/ipc-channels.cjs` 的
  `EXPECTED_CHANNELS`；跑 `npm run test:app` 看 `channelsExpected`。

`core/` 的模块按前缀成簇（看前缀就知道做了多少块）：

| 簇 | 做什么 | 簇 | 做什么 |
| --- | --- | --- | --- |
| `task-*` | 任务台账 / 生命周期 | `download-*` | 下载管理器 |
| `loop-*` | 对话主循环 | `image-*` | 生图 |
| `config-*` | 配置 | `prompt-*` | 提示词 |
| `memory-*` | 记忆 | `changeset-*` | 改动事务 / 回滚 |
| `session-*` | 会话 | `context-*` | 上下文装配 |
| `clarify-*` | 「先问我」澄清 | `risk-*` / `capability-*` | 权限 / 风险模型 |
| `mcp-*` | MCP 接入 | `project-*` | 读 AGENT.md / .harbor 规则 |
| `browse-*` | 内置浏览器 | `llm-*` / `error-*` | 模型调用 / 错误分类 |

另有 `core/tools/`（具体工具实现）。

**谁是骨干？** 跑 `npm run map` 的「耦合 · 扇入」段 —— 被最多文件引用的模块就是地基，
改它要最小心。

## 四、质量网

| 类型 | 在哪 | 怎么看 |
| --- | --- | --- |
| 前端单元测试 | `src/**/*.test.ts(x)` | `npm run test:unit` |
| 内核自检组 | `scripts/selftest/groups/*.mjs` | `npm test` —— 看末尾「通过 N 项 / 失败 0 项」 |
| 安全测试 | `scripts/security/` | `npm run security` |
| 规则检查 | `scripts/check-rules*` | `npm run check:rules` · `npm run test:rules` |
| IPC 通道自检 | `electron/ipc-channels.cjs` | `npm run test:app`（看 `channelsOk`） |

**各有多少个 → `npm run map`。** 「可验证」是本项目的核心规矩之一：改完代码，机器能替你
跑一整链检查，全绿才算数 —— 不是靠「我读了一遍」。

## 五、功能面（实际做出来的东西）

```text
对话主循环 · 任务中心(台账/暂停/恢复) · 改动审查与整批回滚
记忆系统 · 项目上下文(AGENT.md/.harbor 规则) · 澄清提问
内置浏览器(可操作网页) · 终端(node-pty) · 下载管理器(分段/续传)
生图 · MCP 接入 · 技能 · 权限/风险模型 · 审计日志
多模型路由(fast/reasoning/coding/vision/cheap) · 每对话参数
```

## 六、文档结构

顶层（架构 / 数据模型 / 安全模型 / Runtime 状态机 / 踩坑记录 …）+ `research/`（调研）+
`archive/`（归档）+ `改造任务/`。入口在 [`README.md`](README.md)（文档地图）。
**文档量与代码量同量级** —— 在同类项目里少见。

| --- | --- |
| 提交数 | `git rev-list --count HEAD` |

## 一条命令拿整张图

```cmd
npm run map
```

它打出 —— 文件数 / 行数 / 各目录分布 / **耦合（扇入 · 扇出）** / 质量网文件数。
**这些数每版都会涨，命令输出才是真相源；本文不背数字。**

其余单项：

```cmd
git rev-list --count HEAD      :: 提交数
git tag                        :: 发布 tag
npm test                       :: 内核自检项数（看末尾）
npm run test:app               :: IPC 通道数（看 channelsExpected）
```

## 一句话读法

> 这不是 demo，是一款**把界面当产品做**的桌面应用 —— 界面、内核、工具链、文档、测试网
> 都在，而且成体系。接下来真正稀缺的不是「再堆量」，而是**收敛** —— 这么多模块之间的
> 边界和唯一真相源守不守得住（`AGENT.md` 里那些「跨模块约定」「会涨的数字」「重复状态」
> 的规矩，全是冲这个去的）。
>
> 想知道**体量 / 骨干是谁** → `npm run map`；想知道**哪里重复、真相源在哪** →
> 那是**判断**不是统计，尚未立项。
