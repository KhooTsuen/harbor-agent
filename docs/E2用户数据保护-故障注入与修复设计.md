## 0. 结论速览

| 模块 | 风险 | 故障注入实测（本轮） | 是否需原子写 | 首要问题 |
|---|---|---|---|---|
| `task-io.cjs` | **P0** | 覆盖写中断 → 台账 237B→30B、**读回 null、从任务列表消失** | **是** | 无原子写、无损坏留档、备份不含 tasks |
| `credentials.cjs` | **P0** | 损坏 → `load()` **静默**退化空 → 下一次 set 后**其它凭证全消失** | **是** | 损坏 = 空 ≠ 用户清空；无留档、无提示 |
| `changeset.cjs` | **P1** | meta 中断 → **无法回滚**（`事务不存在`）、事务从列表消失、快照成孤儿 | **是** | 无原子写；坏事务还撤不掉 |
| `session-io.cjs` | **P2** | `writeLines` 中断 → 190B→40B、**读回 0 条**（静默丢） | 是（一行改动） | 非原子；但生产只拿它写一行 meta |

**一句话**：项目**已经有**一套成熟、且被自检钉住的写法（`safe-write.cjs` 的 `writeAtomic` +
`keepCorruptCopy`）—— 记忆 / 会话 meta / 会话压实 / 项目 / 下载都用它。**问题不是没能力，是标准没铺满**：
**任务台账、凭证、改动事务**这三样同样写用户数据，却还在裸 `fs.writeFileSync`。

> **重要更正（对上一份复核报告的自我修正）**：上一份把「会话正文整篇重写」列为新缺口 ——
> 本轮实测澄清：`session-io.cjs` **已 import `writeAtomic`**，重写路径（`writeMetaLine` / 压实 /
> 加密迁移）**都是原子的**；只有 `writeLines` 一个函数仍裸写，而它**生产上只被用来写一行 meta**
> （`session-write.cjs:59/78`）。故其风险从「P0」下调为 **P2**。这是「不要把未验证视为已实现/未实现」的落实。

## 1. 方法与安全边界（怎么保证不碰真数据）

**隔离机制**（`electron/core/paths.cjs` 的 `dataDir()`）：当环境变量 `HARBOR_UNIT_TEST=1` 时，
`DIRS.data` 指向 `<root>/data/unit-test-data`，**不是**用户真 `data/`。故障注入脚本开头就**断言**路径含
`unit-test-data`，否则拒绝运行。

**独立进程**：每个场景由驱动 `tmp/_e2-inject.mjs` 用 `execFileSync` 派生**一个新的 node 进程**
（`tmp/_e2-child.cjs <场景>`）执行，跑完销毁。好处：① 模块级缓存（凭证 `cache`）在场景间不串；
② 一次「崩溃式」注入不会污染别的场景。

**注入手法**：把 `fs.writeFileSync` 临时替换成「**先按 `'w'` 截断、只写前 N 字节、再抛 ENOSPC**」——
这忠实还原 `writeFileSync` 写到一半失败后**磁盘上的真实形态**（旧内容已随截断丢失）。

**未使用任何真实数据**：脚本自造任务 / 凭证 / 会话 / 改动事务；凭证一律用 `sk-FAKE-*` 假串，
**从未读取用户真 API Key / 任务 / 会话 / 个人文件**。跑前跑后清理 `data/unit-test-data`。

复现命令：

```
node tmp/_e2-inject.mjs      # 4 个场景各起一个独立进程，输出原始观察
```

## 2. 故障注入结果（原始观察）

### 2.1 `task-io.cjs` —— 任务台账覆盖写中断（P0）

```
写入前文件: 237 字节   写入后文件: 30 字节    旧数据是否被覆盖: true
写入后能否解析: false   读回结果: null（任务读不出来）
list 前: ["task_e2probe"]      list 后: []        ← 任务从列表消失
未捕获的异常: ENOSPC       遗留损坏副本: []       ← 没有任何 .corrupt/.broken 留档
```

- **触发器**：任一 `task.update()/finish()/setPlan()`… → `task.cjs:79 io.write()` → `task-io.cjs:47`
  `fs.writeFileSync(fileFor(id), …)`。写盘期间进程被杀 / 断电 / 磁盘满即命中。
- **后果**：该任务文件被截断 → `get()` 解析失败返回 `null`（`task-io.cjs:79-82`）→ **任务中心里它直接消失**；
  且**无留档**、**备份不含 tasks**（见 §3）。用户看到的是「任务莫名其妙没了」。

### 2.2 `credentials.cjs` —— 凭证损坏 → 解析失败 → 后续保存（P0）

```
损坏前凭证: ["provider:alpha","provider:beta"]
损坏后 load 读到: []          has(provider:alpha): false
一次 set(provider:gamma) 的返回: { ok:true, backend:"plain" }
保存后文件里的 ref: ["provider:gamma"]    旧凭证是否被覆盖: true
是否有 .corrupt 留存: []
```

- **触发器**：`credentials.json` 损坏（截断 / 断电 / 硬改）→ 之后**任何一次** `set()`。
- **机理**：`load()` 的 `catch`（`credentials.cjs:69-75`）把**任何**异常都当成「全新文件」→
  `entries = {}`（**静默，连一条日志都没有**）；随后 `set()` 走 `persist()`（`:79-83`）把
  `{entries:{新键}}` **整篇覆盖** → alpha/beta 永久消失。
- **这正是复核报告点名的红线**：`load()` 解析失败**不能等价于「用户主动清空凭证」**。
  加一份 `.corrupt` 副本**也只是留证据、救不回可用性**（见 §5 的可选加强项）。
- **对比**：记忆（`memory-store.cjs:51`）在同样情形会 `keepCorruptCopy` + `log.error`，
  且被安全自检 **SEC-063** 钉住（`坏文件被另存留档`）。凭证这边**同类能力一个都没有**。

### 2.3 `changeset.cjs` —— 改动事务 meta 覆盖写中断（P1）

```
中断前 meta: 403 字节 → 中断后: 25 字节      中断后能否解析: false
readMeta结果: null        list 是否还列出它: false
rollback 返回: { ok:false, error:"事务不存在" }     快照文件: ["0001.snap"]（成孤儿）
未捕获的异常: ENOSPC
```

- **触发器**：`commit()` / `record()` / `rollback()` 写 `meta.json`（`changeset.cjs:87 writeMeta`）时中断。
- **后果**：事务**从审查面板消失**（`list()` 见 `readMeta` 为 null 就跳过），且**用户无法回滚**
  ——`rollback()` 先 `readMeta`，拿不到就返回「事务不存在」。**改动前的快照还在磁盘上，却没有任何入口能用到。**
  这恰好击穿改动事务存在的意义（「模型改错了能一键撤」）。

### 2.4 `session-io.cjs` —— `writeLines` 整篇重写中断（P2，已下调）

```
中断前文件: 190 字节（3 行） → 中断后: 40 字节（1 行）    读回条数: 0   读回类型: []
未捕获的异常: ENOSPC       遗留损坏副本: []
```

- **触发器**：`writeLines`（`session-io.cjs:125-129`，裸 `fs.writeFileSync`）被中断。
- **读回为什么是 0**：被截断的第一行 `JSON.parse` 失败 → `readLines`（`:90-94`）**静默跳过**
  （该分支只在「解密封装失败」时计数告警，**纯 JSON 破损是无提示丢弃**）。
- **务必如实标注**：生产代码目前**只有 `session-write.cjs:59/78` 两处**用它，且都只传**一行 meta**
  （新会话建档）。因此现实影响面**小**；真正的重写（压实 `session-compact.cjs:111`、改标题
  `writeMetaLine`、加密迁移 `session-crypto.cjs:263`）**已经走原子写**。列为 P2，是「顺手对齐一致性」，
  不是「正在丢数据」。

## 3. 写入面全景与备份现状

### 3.1 写用户数据的调用点分类（快照，复算见 `_e2-inject` 同类扫描）

| 类别 | 记法 | 模块（举例） |
|---|---|---|
| **原子写**（`writeAtomic`） | 安全 | `memory-store` · `projects` · `download-store` · `schedule-store` · `session-io.writeMetaLine` · `session-compact` · `session-crypto` · `project-rules` · `download-store` |
| **直接覆盖写**（`writeFileSync`） | **风险** | **`task-io`** · **`credentials`** · **`changeset.writeMeta`** · **`session-io.writeLines`** · `config.persist` · `artifact` · `capability` · `task-index` · `stats` · `context-diag` |
| **追加写**（`appendFileSync`） | 低危 | `log` · `log-actions` · `error-observer` · `events` · `audit` · `session-write.appendEvent`（崩了只丢最后一行） |
| **可重建索引** | 低危 | `task-index._index.json`（可从 tasks 重建） · `search-cache` · `context-diag` |

> 本报告聚焦**用户数据**四样：任务台账 / 凭证 / 改动事务 / 会话。`config` 有独立 `.broken` 兜底（见 3.3），
> 但**其 persist 仍非原子**（截断风险与凭证同型），本轮一并登记、不单独展开。

### 3.2 备份覆盖范围（重要缺口）

`backup-scan.cjs:20-27` 的 `ITEMS` **只备 4 样**：

```
config.json · memory.json · sessions/ · skills/
```

⇒ **任务台账（tasks/）、凭证（credentials.json）、改动事务（changesets/）都不在备份里** ——
恰恰是**最不可重建**的三样。`backup.cjs:79` 还有一条：「一个用户项都没拷到 → 这份备份不留」，
所以只有 tasks/credentials 的新装用户，备份**直接不出**。

### 3.3 备份 / 恢复 / 容错现状对照

## 4. 风险分级与用户影响

| 级别 | 项 | 触发条件 | 用户可感知的后果 | 可否恢复 |
|---|---|---|---|---|
| **P0** | 凭证损坏后一次 set | 文件损坏 + 任意一次保存密钥 | 所有 API Key 静默消失，须逐个重填 | 无留档则**不可恢复** |
| **P0** | 任务台账覆盖写中断 | 任意 task 写入期间进程被杀/断电/盘满 | 该任务从列表消失 | 无备份则**不可恢复** |
| **P1** | 改动事务 meta 中断 | commit/record/rollback 写入期间中断 | 撤不回改坏的文件；事务从面板消失 | 快照在，但**无入口** |
| **P2** | `writeLines` 中断 | 仅新建会话时 | 新建的会话首行坏 → 读回 0 条 | 新建，损失有限 |

**共同病根**：`writeFileSync(整篇)` = **先截断、再写**（`safe-write.cjs` 文件头原话），
中途失败即丢旧数据；而三个模块**都缺**「原子写 + 损坏留档」这层。

## 5. 最小修复方案（每项独立、可单独提交/回滚）

**总原则**：**复用现成的 `safe-write.cjs`**（`writeAtomic` + `keepCorruptCopy`），
它是内核里**唯一**的文本原子写实现，且被自检 `118-safe-write` 钉着（「`electron/**` 只允许一个 `writeAtomic`」）。
⇒ 本方案**不新建任何框架、不改数据格式/字段/迁移**，只把已有写法铺到遗漏的模块。

### 5.1 `task-io.cjs`（推荐先做）

| 问题 | 答案 |
|---|---|
| 触发条件 | `task-io.cjs:47` 覆盖写期间中断 |
| 现状容错 | `get()` → `null`（`:79-82`，仅 warn） |
| 需原子写？ | **是** |
| 失败会覆盖旧数据？ | **会**（实测 237B→30B） |
| 留损坏证据 | 否 → 改为 `keepCorruptCopy` + `log.error` |
| 最小改动 | ① `write()`：`fs.writeFileSync(...)` → `writeAtomic(fileFor(id), text)`；② `get()` 的 `catch` 里，对「文件存在但解析失败」调 `keepCorruptCopy` + `log.error`（`ENOENT` 仍静默） |
| 影响面 | **1 文件 + 1 import**；不改字段、不改格式 ⇒ **无迁移** |
| 回滚 | 单 commit revert 即回裸写 |
| 验收 | 注入「写中断」→ 旧任务**仍可读回**；注入「文件损坏」→ 出现 `.corrupt-<ts>` 且 `log.error` |

### 5.2 `credentials.cjs`

| 问题 | 答案 |
|---|---|
| 触发条件 | `persist()`（`:82`）写入中断；或文件损坏后 `load()`（`:69`） |
| 现状容错 | **静默**空（无日志、无留档） |
| 需原子写？ | **是** |
| 失败会覆盖旧数据？ | **会**（实测其它凭证全丢） |
| 留损坏证据 | 否 → `load()` 区分「不存在(ENOENT)」vs「存在但坏了」：后者 `keepCorruptCopy` + `log.error` + 置 `_loadWarning` |
| **关键要求** | **不得把「解析失败」等同「用户清空」**：修后 `load()` 仍可返回空以便启动，但**必须**（a）留存坏文件、（b）留下可展示的告警、（c）**不在损坏未被处理时用只含新键的内容覆盖**（见「可选加强」） |
| 最小改动 | ① `persist()` → `writeAtomic`；② `load()` 的 catch 区分两类、留档 + 告警 |
| 影响面 | 1 文件；**加密后端不变、文件格式不变** ⇒ 无迁移 |
| 回滚 | revert 即回 |
| 验收 | 注入「损坏→set」→ 出现 `.corrupt`、产生告警、**原凭证内容仍能从留档里读出**（证明不是「被清空」） |

> **⚠️ 仅加 `.corrupt` 不够**（用户明确指出）：留档只是「证据」。若要在**可用性**上也不丢，
> 需要一个「损坏时把可解析的部分尽力保住 / 或拒绝覆盖」的策略 —— 那是**更大的一步**，列为**可选加强项**，
> 单独评估（可能触数据结构，属硬禁区 11，需另行批准）。本轮**只推荐先留证据 + 告警**。

### 5.3 `changeset.cjs`

| 问题 | 答案 |
|---|---|
| 触发条件 | `writeMeta()`（`:87`）期间中断 |
| 现状容错 | `readMeta` → `null`（静默）；`rollback` 返回「事务不存在」 |
| 需原子写？ | **是** |
| 失败会覆盖旧数据？ | **会**（meta 403B→25B） |
| 最小改动 | ① `writeMeta()` → `writeAtomic`；② `readMeta()` 对「存在但解析失败」补 `log.warn`（现完全静默） |
| 影响面 | 1 文件；`meta.json` 格式不变 ⇒ 无迁移 |
| 验收 | 注入中断 → meta **仍可解析**；注入损坏 → 有告警，且不崩 |

### 5.4 `session-io.cjs`

| 问题 | 答案 |
|---|---|
| 触发条件 | `writeLines()`（`:128`）期间中断 |
| 需原子写？ | 是（与同文件 `writeMetaLine:170` 对齐） |
| 最小改动 | `fs.writeFileSync(fileFor(id), text, 'utf8')` → `writeAtomic(fileFor(id), text)`（**一行**） |
| 影响面 | 1 文件、1 行；格式不变 ⇒ 无迁移 |
| 验收 | 注入中断 → 会话文件**不被截断**（要么旧、要么新） |

### 5.5 Windows 文件替换行为（四者共用，来自 `safe-write.cjs`）

- 原子写 = 同目录 `写 .tmp-<pid>` → `renameSync` 覆盖。
- **Windows 上 `rename` 撞「文件被占用」会报 `EPERM/EACCES/EBUSY`**（VS Code watcher / 杀软 / 另一进程在读）——
  `renameWithRetry` 对这三类**退避重试 5 次（40/80/120/160ms）**，其它错误立刻抛（`:30-53`）。
- **诚实的限制**：`writeAtomic` **没有 `fsync`** ⇒ 它保证「**不出现半截文件**」（这是主要目标），
  但**不保证掉电后最新一次写入一定持久**。若要求断电级持久，是另一个议题（需评估性能），本轮不纳入。

### 5.6 对既有数据格式与迁移的影响

**零影响**：四项都是「**改变写的方式**」，文件的**内容形状、字段、编码、路径全不变**。
⇒ **不需要迁移**、不需要改 `migrate`、旧数据原样可读。这是它们能「单独提交、单独验收」的前提。

## 6. 自动化回归测试方案（含负向）

**落点建议**：放进**安全自检套件**（`scripts/security/suites/*`，已被 `npm run security` 覆盖），
**而不是**新增 `scripts/selftest/groups/*` —— 因为 `selftest.mjs` 的 `GROUPS` 是手写清单、**已恰好 300 行贴线**
（见改进清单 B1）。安全套件里**已有同型先例**：`SEC-033`（改动事务回滚）、`SEC-055`（损坏台账迁移）、
`SEC-063`（记忆损坏留档）。

每个模块一组，**正向 + 负向**都要有：

| 用例 | 断言（正向：修后必须过） | 负向（证明检查真的会红） |
|---|---|---|
| task 原子写 | 注入写中断 → `get()` 仍读回**原任务**（内容=改动前） | 把 `writeAtomic` 临时换回裸写 → 同一注入会丢数据 ⇒ 断言「原内容仍在」**失败** |
| task 损坏留档 | 写坏文件 → `list` 出现 `*.corrupt-*`、有 error 日志 | 去掉 `keepCorruptCopy` → 断言「留档存在」**失败** |
| 凭证损坏≠清空 | 损坏→set → 出现 `.corrupt`、原凭证内容**能从留档读出** | 只做「不崩」断言 → 无法暴露「其它键被覆盖」⇒ 负向用例专门断言**旧键仍在留档里** |
| 改动事务 | 注入 meta 中断 → `readMeta` 非 null、`rollback` 可用 | 去掉原子写 → `rollback` 返回「事务不存在」⇒ 断言失败 |
| 会话 | 注入中断 → 文件行数 = 中断前 | 去掉原子写 → 行数变少 ⇒ 断言失败 |

**负向实现方式**：在测试内**临时**把目标模块的写入点替换成裸写（或注入一次截断），断言「机制被绕过时会被抓到」——
即证明**断言不是恒真**。这是本项目 [`判据自检.md`](判据自检.md) 要求的「反向用例」。

**通过标准**：`npm run security` 中新增项 PASS；且**临时移除修复**（负向）时对应项必须 FAIL。

---

## 7. 推荐先实施的一项

> ### 先做 **`task-io.cjs`（§5.1）**

理由（按「影响 × 最小改动」）：

1. **P0、且后果最直观**：中断即「任务凭空消失」，用户无从理解、无从恢复。
2. **改动最小**：**1 文件、1 个 import、2 处**（写入改原子 + 读损坏留档）。不改字段/格式 ⇒ **无迁移**。
3. **复用而非创新**：`writeAtomic`/`keepCorruptCopy` 都是现成且已被自检钉住的实现，风险低。
4. **可独立验收、可一键回滚**：单 commit；负向用例能明确证明「没修就会丢」。
5. **为后续三项立模板**：task 的验收脚本几乎可原样套到 credentials / changeset。

**验收标准（一句话）**：注入「写中断」后，任务台账仍能 `get()` 回改动前的完整内容；
注入「文件损坏」后，`data/tasks/` 出现 `*.corrupt-<ts>` 且 `list()` 不再把该任务**当空**吞掉。

## 8. 实施边界（本轮做了什么 / 没做什么）

**做了**：4 个模块的**独立进程故障注入**（含真实观察）、写入面分类、备份/容错对照、风险分级、
逐模块最小方案、回归测试与负向方案、推荐顺序。

**没做（等你批准）**：任何内核改动；任何备份范围调整；任何凭证「拒绝覆盖 / 尽力恢复」的加强策略；
`config.persist` 的原子化（已登记、未展开）。

**明确不触**：Runtime、权限模型、IPC、持久化**结构**、事件契约、迁移逻辑。
本方案只改「怎么写」，**不改「写什么」**。
