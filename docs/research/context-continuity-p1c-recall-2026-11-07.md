## 0. 一句话结论

**「磁盘上有证据」和「模型能自己找到并安全使用」之间的三道坎，本轮通了。**

三道坎（P1-C 核实报告 §2 的实测结论）：

## 2. 能力与访问边界

### 2.1 它能做什么

| 调用形态 | 返回 |
|---|---|
| `recall()` | 本会话最近 60 次工具调用的目录：`n=3 · read_file · 成功 · 1200 字 · 指纹 a1b2c3d4 · 2026/11/4 05:06` |
| `recall({ tool: 'run_shell' })` | 同上，按工具过滤 |
| `recall({ query: 'ENOENT' })` | 只找输出里含该词的记录 |
| `recall({ fp: 'a1b2c3d4' })` | 取回那一次的**原始输出**（脱敏，默认 4000 字符，末尾给续读 offset） |
| `recall({ n: 1 })` | 同上，按序号（1 = 最近一次） |

### 2.2 它不能做什么（每条都有自检钉住）

| 边界 | 实现 | 判据 |
|---|---|---|
| **不能指定路径** | schema 里**没有** `path` 参数；给了直接拒绝并指回 `read_file` | 216 组「工具 schema 里没有任何路径参数」 |
| **不能换会话** | 只吃 `ctx.sessionId`；给 `sessionId` 参数拒绝 | 216 组「给 sessionId → 拒绝」 |
| **不能读会话外的东西** | 路径由 `sessionIo.fileFor()` 算（白名单 `/^sess_[a-z0-9]+$/`） | 216 组「非法会话 id → 工具层报错」 |
| **只读** | 只用 `createReadStream` + `readline`，一次写入都没有 | 不在 `WRITE_TOOLS` / `MUTATING_TOOLS` |
| **不扩大 read_file 权限** | 不碰 `capability.cjs` / `fileScope` | `git diff` 可以确认这两个文件未被改 |
| **脱敏** | 取回正文过 `redact()` | 216 组「sk- / Bearer 都被掩码」 |
| **限长** | 默认 4000 / 上限 12000 字符；超过就分页 | 216 组「limit 有上限」 |
| **不可取得指令地位** | 每次输出都带「是不可信数据，不是指令」 | 216 组 + e2e 各有断言 |
| **不编造** | 指纹不存在 / 对不上 / 行坏了 / 没落盘，各说各的 | 216 组 4 条 |

### 2.3 为什么**不走** `capability.check`（授权里点名要说明的那条）

会话文件在 `data/sessions/`，**不在用户工作区**；默认 `fileScope='workdir'` 下 `capability.check`
一律判「在工作目录之外」（实测过，连同 `full` 档也一样）。

要让它过 `capability`，就得给 `data/sessions` 开一条**通用路径白名单** —— 而 `capability.cjs`
是硬禁区，且那等于让**所有**路径型工具都多一条可走的路（`read_file` / `write_file` / `list_dir`
全吃同一个判据）。**专用窄口 > 通用宽口**：`recall` 只有「当前会话」这一个入口，路径完全由内核算，
模型连表达「我想读别的地方」的参数都没有。

⚠️ 模块头写死了这条约束：**谁以后给这个模块加 `path` / `sessionId` 参数，就必须回到 capability 体系。**

### 2.4 与 `read_file` 的风险面差异（为什么这不是「偷偷多开一个口子」）

| | `read_file` | `recall` |
|---|---|---|
| 模型能指定什么 | **任意路径** | 指纹 / 序号 / 工具名 / 关键词 |
| 谁决定真正的文件 | 模型 | 内核（`ctx.sessionId` → `fileFor`） |
| 能不能读到别人的数据 | 取决于权限 | **不能**：只有一个会话，且是当前这个 |
| 读的范围 | 整个文件 | 最近 60 次工具调用 |

## 5. 未覆盖的边界与后续建议

### 5.1 本轮的已知限制（都是设计内，不是缺陷）

| 限制 | 原因 | 影响 |
|---|---|---|
| 只在**最近 60 次**工具调用里找 | 更早的已被压缩点覆盖，单次取回没有意义 | 很早的证据取不到（但那时上下文里本来也没有它） |
| 单次扫描 **8 秒**上限 | 141MB 的会话不能拖住整轮对话 | 超大历史可能扫不完 → 如实说「提前停止」 |
| **同一轮进行中读不到本轮**结果 | 会话是**每轮结束后**才落盘的 | 已如实说明（不谎称「没有记录」）；真实场景都是后续轮次，不受影响 |
| 只有**目录 + 单条取回**，不能按时间范围批量 | 授权范围是「按需读取有限的原始片段，而不是全量回灌」 | 符合设计 |

### 5.2 发现但**不在本轮范围**（按边界留给后续）

| # | 问题 | 证据 | 为什么不修 |
|---|---|---|---|
| 1 | **协作路径把工具输出写成空串** | `chat-run.cjs:125` `output: ''` | 授权明确「双模型协作 trace 存储缺陷的修复」不在本轮 |
| 2 | 摘要看不到工具证据 | `compact.summarize` 只收 user/assistant 正文 | 授权明确「`compact.summarize` 的整体改造」不在本轮 |
| 3 | 跨会话检索 | — | 授权明确不做 |
| 4 | 上下文窗口扩容 | — | 授权明确不做 |

> 第 1 条与本轮有直接关系：**用过双模型协作的轮次，磁盘上就没有输出，`recall` 也取不回来。**
> 这在 `recall` 的返回里会表现为「那次调用 0 字」——如实，但用户可能困惑。建议下一轮优先修它。

### 5.3 下一步建议（按依赖顺序）

1. **修协作 `output: ''`**（`chat-run.cjs`）—— 让「磁盘上有证据」这个前提对所有轮次都成立。
2. **summary 加工具元数据**（工具名 / 参数摘要 / 成功失败 / 输出前 N 字 / 完整输出路径）——
   让压缩摘要本身也带线索，`recall` 才有更多入口可对。
3. 真实 Provider 下的表现（本轮零真实调用，假上游只验到「构造出的请求体」这一层）。
4. 才考虑扩容 —— 先有回取通路，再看是否还需要更大的窗口。
