## 0. 结论先说

1. **五项里没有一项需要换掉 Agent Loop。** 瓶颈全在「事实记录 / 身份归属 / 判定与批准」，不在调度引擎。
2. 五项推荐的分布是：**1 项借机制自行实现（记忆）**、**1 项借机制 + 复用现有代码（审批）**、**1 项纯新增最小注册表（可信验证）**、**2 项借机制、不引运行时（暂停恢复 / 经验检索）**。
3. **直接复用**成熟的 Node 运行时（Temporal / LangGraph-sqlite / DBOS / Inngest / Mem0 / Letta / Zep）在四项硬约束上全部撞墙：原生依赖、外部服务、数据出 `data/`、以及「模型调用不确定 → 确定性重放无意义」。
4. 评估过程中查到 **一条真实的生产数据缺陷**（可直接作为最小切片的收益）：项目级记忆在当前代码里**写不进归属、也检索不到**，`data/memory.json` 里已有 11 条因此变成死条目。证据见 §2。
5. 按「收益 ÷ 迁移风险」排序，最小可验收切片建议做 **跨对话记忆的归属闭环**（3–4 个文件，零数据迁移）。详见 §7。

## 2. 一条真实缺陷（本节是后续切片的主要收益来源）

**因果链（每一环都有源码证据）：**

1. `electron/core/loop-tool-context.cjs` 构造的工具上下文**没有 `projectId` 字段**（只有 `workdir` / `sessionId` / `taskId`）。
2. `electron/core/tools/remember.cjs` 写记忆时只传 `sessionId`（第 53–58 行），**不传 `projectId`**。
3. `electron/core/tools/memory_search.cjs` 检索时读 `String(ctx?.projectId ?? '')`（第 69 行）→ 因为 (1)，**永远是空串**。
4. `electron/core/memory-scope.cjs` 的规则是：`scope === 'project'` 且 `ctx.projectId === ''` → **返回 false（不可见）**。
5. 于是：模型选 `scope: 'project'` 记下的记忆，`projectId` 落成 `''`，之后**永远不会被注入、也搜不到**。
6. 生产数据已中招：11 条 `scope='project'` 条目全部 `projectId=""`（2026-11-02 实测快照）。

**而自动注入这条路径是对的**：`loop-prompt.cjs` 第 130 行传的是 `options.projectId`（来自 `chat-run.cjs` 的 `payload.projectId`）。

所以这是教科书级的「同一份身份上下文，两个入口各说一套」——正是 AGENT.md 硬约束 9 要治的病，也是蓝图 §3 表格里最后一句「写入、自动注入和主动检索必须使用同一份身份上下文」。

> **旧数据边界**：修好写入与检索链路后，只有新写入且带有效 `projectId` 的项目记忆能在同项目对话中生效。生产库现有 11 条 `projectId=""` 的旧条目仍然不可见；它们的项目归属未知，不能按内容、`sessionId` 或当前工作目录猜测归属，也不能升级为全局记忆。本切片不迁移这 11 条记录；交付时应说明“以后记得对”，而非“旧记录被救活”。

## 3. 逐项评估

### 3.1 暂停与恢复

**Harbor 已具备**

- `task-resume.cjs`：`canResume`（只认 `paused` / `waiting_user`）、`reopen`（**复用同一条任务**，`resumeCount+1`，清 `pauseReason/budgetHit/loopHit`）、`checkEnvironment`（`changedFiles` 的 mtime 晚于 `task.updatedAt + 2000ms` 容差 → 报 `envChanged`）。
- `task-recovery.cjs`：`scan()` **纯读**，附加 `envChanged/progress/canResume/replay`，**刻意不自动执行**。
- `task-intent.cjs`：**先落意图再执行**（`markIntent` 写 `intent + completed:false` → 执行 → `markCompleted` 写 `ok/outcome`）；`isPending` 判「结果不明」；`REPLAY_UNSAFE` 白名单判「重跑会不会做两份」。2026-11-02 已补 `reasonCode/exitCode` 落盘。
- `loop.cjs`：**只在轮次边界**检查 `pauseRequested`（第 111 行），AbortError → `paused`。
- `changeset`：一个任务一个事务 + 检查点回退（含 `dryRun`）。

**本质定性**：Harbor 是「**意图账 + 轮边界暂停 + 软恢复**」——恢复时把 `plan` / 进度 / `envChanged` / `replayRisk` 注入提示，由模型自己接着做（`task-context.cjs` 注入计划与进度）。**不是确定性重放。**

**成熟项目机制**

| 项目 | 机制 | 链接 |
|---|---|---|
| Temporal | Event History 全量持久化；Command → Event 映射；worker 崩溃后**重放代码重建状态** | https://docs.temporal.io/encyclopedia/event-history · https://docs.temporal.io/activities · https://docs.temporal.io/develop/typescript/workflows/message-passing |
| LangGraph JS | checkpointer（thread 级快照）+ `interrupt`（人在环断点）+ store（跨线程长期数据） | https://docs.langchain.com/oss/javascript/langgraph/persistence · https://docs.langchain.com/oss/javascript/langgraph/interrupts |
| Restate / DBOS / Inngest | durable execution：每步落 journal，恢复时**跳过已完成步骤** | https://docs.restate.dev/foundations/key-concepts#durable-execution · https://docs.dbos.dev/typescript/tutorials/workflow-tutorial · https://www.inngest.com/docs/durable-execution/durable-workflows |

**直接接入成本**

- **Temporal**：`@temporalio/worker@1.25.0` 依赖 `webpack` / `@swc/core` / `@temporalio/core-bridge`（Rust 原生桥），且**必须有 Temporal Server**（自托管要 Postgres）。→ 撞「不引入新的原生依赖」+「数据只落 `data/`」。
- **LangGraph**：`@langchain/langgraph-checkpoint-sqlite@1.1.0` **依赖 `better-sqlite3`（原生）**。
- **DBOS**：`@dbos-inc/dbos-sdk@5.4.0` **依赖 `pg`（Postgres）**。
- **Inngest**：`inngest@4.26.2` 带 `@opentelemetry/*` 全套 + 需要 Inngest 服务。
- **迁移**：三者都要求把 `loop.cjs` 改造成「纯确定性 workflow + 副作用全走 activity」——等于重写内核。而且**模型调用本身不确定**（同输入不同输出），确定性重放对它没有意义；Harbor 里真正不确定的部分（模型、命令、网络）本来就在「activity 位」，且已有意图账兜底。

**借鉴成本**

- 借「每步落账、恢复时跳过已完成」：`beginShell` 现在**只覆盖 `run_shell`**，泛化成 `beginTool`（覆盖 `REPLAY_UNSAFE` 那一组）≈ 1 个文件 + `tools/index.cjs` 一处调用点。
- 借「interrupt 显式化」：`decisions.cjs` 的 `DECISION_TYPES` 加一种 `resume` 型（它的设计就是「新增一种决策 = 在这里加一条」）。
- 借「恢复前环境校验」：`checkEnvironment` 已有，缺的只是**把 `envChanged` 变成硬门**（现在是提示）。

**推荐：借鉴机制，不引运行时。** 理由：现有 `intent/completed/isPending/replayRisk` 已经是「durable execution 的账」的 80%，缺的是覆盖面（只服务 `run_shell`）和硬门。引 Temporal/LangGraph 的代价是「重写一个已经跑着 49 条任务台账的内核」，收益却只是「换一种记录方式」。

### 3.2 跨对话记忆

**Harbor 已具备**

- `memory-store.cjs`：结构化条目，`type/scope/source/confidence/status(superseded·expired)/seq/expiresAt`，完全相同内容去重，总量上限，**忘 ≠ 删**。
- `memory-scope.cjs`：**可见性唯一判定**（`projectId`/`sessionId` 的「键在不在」本身是语义：`undefined`=管理视图，`''`=fail-closed）。
- `memory-recall.cjs`：检索（范围/类型/重要度/新鲜度/关键词重合）+ 注入 + `lastInjection()` 账 + 「像在回忆」触发提示。
- `memory-explain.cjs`：权重表**唯一来源**，解释分 = 排序分。
- `memory-similarity.cjs`：冲突取代（同类型 + 同 scope + 高相似）。
- 已如实记录的差距：`docs/Memory设计.md` §6 列了 14 项「目标 vs 现状」。

**成熟项目机制**

| 项目 | 机制 | 链接 |
|---|---|---|
| Mem0 | LLM 抽取事实 → 去重 → 向量；检索融合 语义/关键词/实体/时间 四路；**必须**用 `user_id/agent_id/run_id` 做 scope | https://docs.mem0.ai/core-concepts/how-it-works |
| Letta | memory blocks（常驻可编辑块）+ archival memory（向量召回） | https://docs.letta.com/v1-sdk/concepts/stateful-agents · https://www.letta.com/blog/memory-blocks/ |
| Zep / Graphiti | 时序知识图谱（bi-temporal，能回答「那时是什么」） | https://help.getzep.com/concepts · https://github.com/getzep/graphiti |
| LangMem | 抽取 + prompt 优化 + 语义检索 | https://langchain-ai.github.io/langmem/ |

**直接接入成本**

- `mem0ai@3.3.1`（我解包看过 `dist/index.d.ts`）导出的是 **`MemoryClient`（托管平台 API 客户端）** + 错误类；**没有本地 OSS 实现**。要自托管得另起服务。
- `@letta-ai/letta-client@1.12.1` 是 **API 客户端**，需要 Letta Server。
- Zep 需要 Graphiti 服务 + 图数据库。
- 共同前提是**向量库**；Node 侧现实选项（`sqlite-vec` 等）都是原生扩展 → 撞硬约束 6。
- 还多一笔**每轮一次的 LLM 抽取调用**（token 成本 + 延迟），而 Harbor 现在的 95 条记忆是纯本地规则维护的。
- 迁移：把 95 条（其中 11 条归属残缺）搬进新库，要重做 scope 语义（`workspace` 这个自造 scope 在四家里都没有对应）。

**借鉴成本：低。** Mem0 的四路检索里，「scope 过滤」「关键词」「时间」Harbor 已经有；缺的两项**都不用引依赖**：
1. 归属写对（§2 的缺陷）；
2. `lastUsedAt` 参与打分 —— 数据**已经记了**（`memory-store.touch`），只是 `memory-explain` 不消费（`Memory设计.md` §6 第 10 行「记而不消费」）。

**推荐：借鉴机制 + 自行实现，零新依赖。** 顺序：先修归属（最小切片）→ 再让 `lastUsedAt`/`source` 进打分 → 最后才谈 evidence 字段。上下文预算方面：`injectLimit` 现在是 12 条，Mem0 的做法是「先检索 20–50 再重排」，Harbor 的 12 条是**注入预算**，两者不冲突，别混。

**Harbor 已具备**

- `error-observer.cjs`：原始错误 → 按天 `data/errors/YYYY-MM-DD.jsonl`，只追加、去重只涨计数、**整行二次脱敏**、定时器 `unref()`、自检期不装。
- `error-reader.cjs` + `error-rules.cjs`：只读 + 严重性/去重/合并**与 CLI 共用一份规则**。

### 3.4 人工审批

**Harbor 已具备（五项里最完整的一项）**

- `tools/approval.cjs`：统一入口 · `requestId` · `scope(once/session/permanent)` · `GRANT_WINDOW_MS=2min` · `REMEMBERED={write,mcp}`（`risk` **刻意不记**）· `freshApproval` 逐次审批 · **超时 fail-closed** · 写进 `task.permissions`（只留 50 条）· `list()` 读口 + 旧记录归一化。
- `confirm-bridge.cjs`：pending / 自然超时 / `settleAsTimeout` / `settleAllFor(owner)`。
- `decisions.cjs`：`approval` / `clarify` 两型，`timeoutPolicy` 是核心语义（`reject` vs `accept-default`），公共字段一处生成（僵尸卡就是漏 `sessionId` 来的）。
- `capability.cjs`：路径授权三档 + 敏感路径表 + `realpath` 防软链绕过。
- `risk.cjs`：四级 + **理由给用户看** + `decide()` 完全按策略（2026-09-29 起不再偷偷降级）。
- `ask_user({gate:true})` + `PermissionBar` + `AboveInputCards`。

**两个真实缺口**

- **A：没有档位。** `approvalLevel` 全仓零命中。现在的粒度是「全局 `tools.permission`（full/ask/readonly）+ 每类 risk 策略」，表达不了「保守 / 标准 / 激进」。
- **B：「高危永远保留」目前没有实现基础。** `risk.cjs` 的 `decide()` 会让配置把 `high`/`critical` 设成 `allow`。蓝图 §7 表里「任何档位下 `critical` 仍拦截」这句话，**必须先建立独立的最低保护线**，否则就是只改文案。

**成熟项目机制**

| 项目 | 机制 | 链接 |
|---|---|---|
| OpenAI Agents SDK | 工具审批回调 + interruption 状态**可序列化**（能持久化后恢复） | https://openai.github.io/openai-agents-js/guides/human-in-the-loop/ |
| HumanLayer | 审批请求是一等对象、**外发到人所在的通道**（approve/reject/edit 三动作） | https://www.humanlayer.dev/ |
| OPA / Cedar | 策略即代码，**decision 与 enforcement 分离** | https://www.openpolicyagent.org/docs/policy-language · https://docs.cedarpolicy.com/auth/authorization.html |

**直接接入成本**：HumanLayer 要外部服务/网络（违背本地优先）；OPA 的 `@open-policy-agent/opa-wasm@1.10.0` 依赖只有 `yaml`/`sprintf-js`（**无原生**，是三项里唯一技术上可行者），但把单机应用的风险策略外置成 Rego，是为一个开关引入一门语言。Cedar 的 `@cedar-policy/cedar-wasm@4.14.0` 无依赖，同样属过度设计。

**借鉴成本：低-中。** 借用「decision 与 enforcement 分离」这一条就够：档位 = **一期一层配置**（`assistant.approvalLevel`）+ 对话级覆盖 + **每轮开头快照**；最低保护线 = 在 `risk.decide()` **之外**加一道不可配置的 floor。

**推荐：借鉴机制 + 复用现有 `approval` / `decisions` / `risk`，档位自行实现。** 理由：现有审批链已经解决了「重复弹窗」「超时 fail-closed」「永久授权可撤销」「逐次审批」，这些正是成熟方案要解决的问题；缺的只有一个「频次旋钮」和一条「地板」。

### 3.5 可信验证

**Harbor 已具备的「验证器雏形」（但没登记）**

| 已有实现 | 它其实是什么 |
|---|---|
| `run_project_test` 的 `toolOk` | 断言失败的独立信号（正文正常但 `ok=false`） |
| `changeset` 的 `dryRun` | 「预览说撤几个，真撤就是那几个」 |
| `apply_test_fix` 写入前**复核文件哈希** | 防覆盖别人改动的完整性校验 |
| `ext-gate.judge` + ext 的 `verify` | 提交类按钮先确认；点击靠 URL/标题/节点数/字数**前后对比**判定 |

**缺口**：这些验证器**没有 ID、没有版本、没有批准者、没有失效条件**，也没有「模型不可写」的存放边界（全仓 `validator` 零命中）。

| 标准 | 机制 | 链接 |
|---|---|---|
| in-toto | attestation：谁、用什么材料、执行了什么、产出什么 | https://in-toto.io/ |
| SLSA | provenance 的分级与不可伪造要求 | https://slsa.dev/spec/v1.0/provenance |
| Sigstore | 签名 + 透明日志，验证方独立于生产方 | （官方站点本轮 curl 超时，未核实，故不作为依据） |

**直接接入成本**：Sigstore 要 OIDC + 透明日志 + 网络（`@sigstore/sign@5.0.0` 还带 `make-fetch-happen` 等）；对单机本地应用是过度设计，且与「本地优先」冲突。in-toto 是**规范**不是运行时，本来就要自己实现。
**借鉴成本：低。** 只需借它的**形状**：`id / 适用操作 / 版本 / 内容 sha256 / 批准者 / 允许读取的证据 / 可执行动作 / 失效条件`。Node 内置 `crypto` 就够，不需要任何依赖。

**推荐：借鉴机制 + 自行实现最小注册表。** 放 `data/validation/` 下，与「模型可写区」物理分离；运行前校验 sha256，版本一变批准状态即失效（这正是 SLSA/in-toto 的核心约束，代价只有一次哈希）。

## 6. 明确不推荐（及理由）

1. **不换 Agent Loop。** `loop.cjs` 的状态语义（`paused`≠失败、`waiting_user`、意图账、一任务一事务）已是 Harbor 数据契约的一部分；替换要动 49 条 task 台账、8 条会话、全部内核自检组，而五项里没有任何一项的瓶颈在调度层。
2. **不引 Temporal / DBOS / Inngest / Restate。** 全部需要外部服务或原生桥；且「模型调用不确定」使确定性重放的收益接近零。
3. **不引 Mem0 / Letta / Zep 的运行时。** npm 侧拿到的是托管客户端；自托管要额外服务 + 向量库（原生扩展）。
4. **不引 Sigstore。** 需要 OIDC + 透明日志 + 网络，与「本地优先、数据全在本机」直接冲突。
5. **不引 OPA / Cedar**（本轮）。技术上 OPA-wasm 无原生依赖，但对一个「三档开关」而言是为一颗钉买一把锤子。若将来策略数量真的多到需要外置，再评估。

## 7. 下一阶段最小可验收切片（建议）

**切片：跨对话记忆的「归属闭环」**（决策表第 1 项）

**要做什么（一句话，可验证）**：模型用 `scope: 'project'` 记住的内容，在**同一个项目的任意对话**里都能被注入和搜到；换到别的项目则一条都不出现。

**预计改动的文件（3–4 个，会触发 AGENT.md 硬禁区 1 的「3 个以上」，需你点头）**

| 文件 | 改什么 |
|---|---|

**怎么验证（命令 + 预期）**

   - 读 `data/memory.json` → 该条 `projectId` **非空**；
