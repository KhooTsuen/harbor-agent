## 1. 目标、边界与现状

目标是在 Harbor 自举开发版的终端中启动 `harbor-test`，用 TUI 看测试进度与结论。测试实现仍放在源码仓库并从自举版调用；自举版是控制台，不作为这两类被测目标的替身。TUI 默认用人话回答“这次能不能用、哪里退步、哪里没测到、需不需要你动手”，并保存机器可读证据。它调用既有脚本，不改变它们的判据；单个新代码文件不超过 300 行，使用 Node 内置模块和现有依赖，不改 `electron/main.cjs`、`electron/ipc-channels.cjs`。

| 资产 | 已核实的入口 | 当前发现 |
| --- | --- | --- |
| 自检 | `npm test` → `scripts/selftest.mjs` | `harness.mjs` 按组打印 `✅/❌/⚠️`，末尾打印通过/失败总数；项目上轮实跑为 5953 项，不固定写进工具。 |
| 单测 | `npm run test:unit` | Vitest 可读末尾 `Test Files` / `Tests`，上轮实跑为 223 文件、2039 项。 |
| 全链 | `npm run verify` | 串联静态检查、规则、单测、自检、安全、构建；一个阶段失败后后续阶段不会运行。上轮实跑在安全 `SEC-073` 失败。 |

真机输出并不统一：多数打印 `PASS/FAIL` 和 `x/y 通过`，`accept-regen-real.mjs` 使用 `✓/✗`，`accept-host.cjs` 只给一条 `PASS/FAIL`。脚本使用固定 profile 名和固定端口，且多条脚本改同一个 `com.harbor.agent` 注册表键。`harbor-edge/README.md` 明确要求注册表相关脚本串行；即使串行，前一个 Edge 退出慢也会抢焦点。部分脚本在 `finally` 内删除 profile 和临时文件，失败后现场可能已经不存在。

**只读发现的现存风险：**`accept-ownership.cjs` 末尾调用 `S.restoreRegistry(regSnap)`，共用实现却要求 `restoreRegistry(name, value)`；该调用没有检查返回值。它可能无法把原值恢复回来，也可能使脚本在判据全绿时把环境留在错误状态。实施前应在隔离环境单独核实；本设计不改该脚本的判据。

## 2. 两批交付的真实边界

**第一批：统一 CLI + TUI 报告器。**可做到从自举版统一启动、目标选择、严格串行、原始日志与退出码归档、结构化 JSON、可选 HTML、基线差异、默认 TUI 人话报告，以及已存在证据的收集。第一批**不宣称**提供每个脚本的独立 profile/端口，也不宣称失败后能保留被脚本自身删除的现场。首次运行没有上一轮基线时，退步与耗时比较写“暂无上次数据”。没有重试时，“真红/环境抖动”写“本次失败，尚未复测”，不能猜成代码坏了。

**第二批：真机隔离。**实施前须处理现有脚本写死端口、profile、`data/unit-test-data`、注册表键和自行清理现场的问题。仅传环境变量无法覆盖这些常量；只在外层包一层进程也无法阻止脚本在 `finally` 删除失败现场。建议第二批采用**隔离副本 + 受控配置注入**：每次在 `data/harbor-test/<run-id>/<script-id>/` 建源码/产物隔离副本，按审计过的常量位置生成临时副本，只运行副本，不改仓库原脚本；每个脚本只允许明确列出的端口/profile/数据根替换。生成前比对源文件 SHA-256 与适配清单，脚本变了就标“适配待复核”并停止，绝不静默继续。注册表仍需外层排他锁、运行前快照、运行后 32/64 位回读，恢复失败时停止队列并报“环境未恢复”。失败现场保留的前提是临时副本的清理动作能由受控配置跳过；这属于第二批需要单独评审的适配方案，不能在第一批承诺已实现。

如果用户坚持“连临时运行副本也不得变更原脚本逻辑”，第二批的**完整**独立端口和失败保留现场无法同时保证；设计验收时必须先决定采用临时副本适配，或允许对共用驱动与脚本做最小配置接线。无论采用哪种方案，断言表达式、判据名称与预期值均不得更改。

## 3. 控制端、被测目标与第一批 CLI 规格

自举版是**操作入口**：用户在 Harbor-Dev 的终端里看 TUI、启动/停止测试、阅读结果。运行器本身来自源码仓库；这样工具更新不需要先覆盖正在使用的自举程序。TUI 只使用 Node 标准输入/输出的 ANSI 与键盘事件，不依赖 Electron 新窗口或 IPC。Harbor 内置终端若不支持 raw mode、光标定位或颜色，则自动退化为逐行人话报告。退出 TUI 不终止已保存报告；运行中按 `Ctrl+C` 则记录取消状态与已完成阶段。

**启动端选择（用户已确认）：推荐 PowerShell，TUI 由 Node 实现。** 在 Harbor-Dev 的 PowerShell 终端中切到 `E:\CodexWorkbench`，再运行 `npm run harbor-test -- ...`。PowerShell 负责启动与必要的 Windows 环境诊断；屏幕刷新、颜色、键盘交互和人话报告由 Node 统一处理，不依赖 PowerShell 专有的界面组件。`cmd` 保留为兼容启动端，`node tools/harbor-test.mjs ...` 在 cmd 中也应可运行；现有 native host 的 `.cmd` 包装器不改。无交互终端或重定向输出时自动使用纯文本模式，不输出 ANSI 控制序列。Windows 路径作为进程参数传递，不拼接成 shell 命令字符串。

| 被测目标 | 第一批可如实执行 | 第一批不能冒称已覆盖 |
| --- | --- | --- |
| `source`：`E:\CodexWorkbench` | `unit`、`self`、`verify`、源码树的 `test:app`，以及现有脚本实际指向源码/仓库打包产物的自动 e2e | 不能把仓库 `dist-portable` 的结果当作 `E:\Harbor` 结果。 |

对 `installed` 请求 `unit`/`self` 时，TUI 明示“这是源码测试，不能证明安装包可用”，提供转到 `source` 运行的操作；若请求 `all`，安装版只执行能真实指向安装包的检查，其余项目以 `NOT_APPLICABLE` 或“第二批待接线”列出，**不显示全绿**。打包态 `paths.cjs` 明确忽略 `HARBOR_UNIT_TEST`，直接对 `E:\Harbor\Harbor.exe --self-test` 会使用真实 `E:\Harbor\data`，所以第一批必须在无 `data/` 的程序副本中做自检；副本结果称“安装程序文件的隔离自检”，不声称覆盖真实用户数据。第二批通过受控适配让真机脚本指向指定安装版，并验证 host 及扩展实际加载的路径与目标一致，才可把 e2e 归到安装版。每条结果保存 `targetId`、绝对路径、EXE/关键资源哈希、源码 commit/dirty 标记，`--diff` 只比较同一目标身份；不能跨目标拿源码成绩对照安装版。

建议入口：在自举版终端打开 `E:\CodexWorkbench` 工作目录，运行 `npm run harbor-test -- <unit|self|e2e|all> --target=<source|installed> [--diff] [--html] [-v]`；`--target=installed` 指向 `E:\Harbor`，可用 `--installed-path` 显式指定其他便携目录。源码仓库 `package.json` 增加 `"harbor-test": "node tools/harbor-test.mjs"`。空参数在交互终端显示目标与套件选择 TUI，不自动启动真机；非交互环境打印帮助并要求显式目标。`--diff` 单独使用时只读最近两份历史结果，不重新跑；跟子命令连用时将新结果与上一次**同范围且可比较**的结果对照。

| 子命令 | 实际调用 | 说明 |
| --- | --- | --- |
| `unit` | `npm run test:unit` | 解析 Vitest 汇总和逐项失败；退出码与解析结果都入报告。 |
| `self` | `npm test` | 按 `── 组 ──` 与 `✅/❌/⚠️` 提取组和判据。 |

TUI 主屏固定显示：**目标路径/版本**、当前阶段与脚本、进度、耗时、结论（人话）、待人工事项数、可疑信号数。测试运行时逐项刷新但不让原始日志刷屏；按 `l` 看当前日志尾部、`r` 看六节报告、`e` 打开证据目录、`q` 退出报告。红色表示已证实失败，黄色表示未跑/可疑/需人操作，绿色仅表示有证据的通过；所有颜色旁均有文字。交互可只用于导航与启动选择，报告本身在无交互模式仍须完整可读。

## 4. 结果模型与判定

每次运行生成 `run.json`（schemaVersion、runId、时间、控制端路径、被测目标身份与哈希、源码 commit/dirty 状态、命令范围、平台、阶段列表、判据、证据路径、人工事项）。判据键为 `suiteId + scriptId + 组名 + 原始判据名 + 重复序号`；仅名字相同不足以当同一项，且重复序号出现时单列“锚点冲突风险”。脚本的 stdout/stderr 原文保留，解析层不把未识别行当通过。

| 结果 | 口径 | 默认人话 |
| --- | --- | --- |
| `PASS` | 退出码 0、汇总可信、判据数量非零、无未标注跳过 | “这部分跑通了。” |
| `FAIL_ASSERTION` | 明确判据失败且证据齐 | “某项功能验收失败。” |
| `FAIL_INFRA` | Edge 启动、端口、注册表、host、脚本崩溃或超时等执行问题 | “这次没有测成，原因是……；暂不能判断功能是否坏了。” |
| `SUSPECT` | 退出码与输出矛盾、零判据、汇总缺失/数量骤降、同名锚点、无证据重试等 | “结果可疑，不能按通过处理。” |
| `NEEDS_HUMAN` / `BLOCKED_ENV` | 人工操作或前置条件缺失 | “还需要你做……”，不计通过或失败。 |
| `NOT_RUN` | 上游阶段失败后未启动 | “本次没跑到”，不计通过。 |

“真红”只在第二批**两次独立尝试都明确 `FAIL_ASSERTION` 且环境完整性检查通过**后使用。一次失败且复跑通过记“环境抖动候选”，但若第二次缺证据或判据数量不一致，归 `SUSPECT`。两次基础设施故障归 `FAIL_INFRA`，不叫代码坏了。失败原因的“同一类问题”只能从受控规则词典映射到模块（如 M04 下行、凭证健康态），无规则时列原判据名称并说“原因尚未定位”，禁止凭日志一行就猜根因。

`--diff` 只比较**同脚本、同判据键、同运行模式、同判据源文件哈希**的结果。上次 PASS 本次 FAIL 才叫退步；上次 PASS 本次未跑叫“覆盖缺口”；判据已改/脚本新增单列“不可直接比较”；上次疑似假绿不当可靠基线。耗时比对按脚本与阶段，默认 ≥3 倍且绝对增量 ≥10 秒报异常，低样本量只说“本次慢了”，不直接称性能回归。

## 5. 默认人话报告

默认在 TUI 首屏显示人话结论、各阶段状态、退步/可疑信号和“下一步”；可用键盘切换六节、打开对应证据、按 `q` 退出。无 TTY、`--plain` 或 CI 时输出同内容的纯文本，不依赖颜色。每次仍写 `report.md`，保证离开 Harbor 后也能阅读。开场 **3–5 句**：先说这次是否能用于判断，再说最影响使用的失败、有没有退步、还有哪些没测到；只有完整覆盖且无可疑信号才可说“这次全绿”。然后固定六节，每节第一句是人话，细节用列表或表格：

1. **总体状态**：这次能不能用；哪些阶段真跑到，哪些因上游失败没跑到。
2. **退步清单**：上次通过、本次失败的判据及模块；没有则明确“没有可确认的退步”；无基线则写“还不能比较”。
3. **真红与环境抖动**：第一批明确写“未复测，无法归类”；第二批列两次都红的项，抖动只报数量并保留证据链接。
4. **可疑信号**：零判据、同名锚点、输出/退出码冲突、跳过无理由、判据数量骤减、恢复校验缺失或异常、重试证据缺失。静态扫描无法证明判据没有硬编码 `true`，所以报告只能说“检测到的风险”，不能保证“无假绿”。
5. **需要你手动做的事**：具体到脚本、按钮/确认动作、超时和是否已有前置，不把“未跑”藏在总数中。
6. **耗时异常**：与可比基线比较，列模块、上次/本次秒数和倍数；无基线时如实说明。

结尾一句建议下一步，例如“先核对注册表恢复，再单独复跑 M04d；在此之前不要用这次结果判断扩展已恢复正常。”技术细节放 JSON 和 `-v`；终端用绿/红/黄，但颜色不能是唯一信息，重定向时禁 ANSI。

## 6. 证据、隐私和历史

每轮目录建议放在源码仓库的 `data/harbor-test/runs/<run-id>/`，按 `source`/`installed` 分开保存基线；运行器不得向 `E:\Harbor\data` 或自举版 `data/` 写报告。，包含 `run.json`、`report.md`、可选 `report.html`，每个脚本的 `stdout.log`、`stderr.log`、`exit.json`、`evidence/`。当前脚本已产出的截图、DOM 快照、host stderr、主进程日志可复制到这里；没有产出的标 `notCaptured`，不伪造。第一批可在失败时从**本次隔离数据根**取日志尾部和存在的图片/DOM 文件；不得扫描或复制 `E:\Harbor\data`、真实凭证、完整 session/配置、浏览器 cookies。所有可展示文本先过现有脱敏逻辑；原始输出也可能带 URL、网页内容或密钥，需限制访问并设置保留期，HTML 只嵌脱敏摘要。

历史基线写在 `data/harbor-test/history/<target-id>/`，只在运行**完整且可比较**时更新 `last-complete.json`；中途崩溃或被阻断的运行仍保存 `run.json`，不覆盖可靠基线。JSON schemaVersion 升级时必须兼容读取旧记录或清楚标“不可比较”。
