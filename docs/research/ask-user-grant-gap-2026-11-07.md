# 已核实缺陷：ask_user 卡片里的授权不更新运行时约束

> 记录日期：2026-11-07 · 状态：**未修**（用户明确要求本轮先做 Changeset，这一项单独核实修复）
> 性质：运行时约束机制的缺陷，与 Changeset 无关

## 现象（真机两次）

用户在 `ask_user` 卡片上明确选了「放开约束，按最小方案修」，卡片答复回来了，
但**后续的写操作仍然被拦**：

```
错误：本轮对话的运行时约束是「只分析，不修改」，edit_file 被拒绝。
错误：本轮对话的运行时约束是「只分析，不修改」，remember 被拒绝。
```

同一句话写在消息正文里（「本轮授权修改源码、跑测试」）就立刻放行。

## 根因（源码确认，L1）

`electron/core/user-constraints.cjs` 里的 `allowWrite` / `grantsWriteIn` 判的是
**最后一条用户消息的正文**（`lastUserText`），而 `ask_user` 卡片答复走的是
`chat-confirm` / `confirm-bridge` 那条通道 —— 它把选择结果交给**调用方**
（工具返回值），**没有回写 `lastUserText`，也没有单独的「卡片授权」通道**。

所以：

| 授权来源 | 会被 `user-constraints` 认吗 |
|---|---|
| 消息正文里写「本轮授权修改源码」 | ✅ 认（`grantsWriteIn` 命中） |
| 用户在 `ask_user` 卡片上点「放开约束」 | ❌ **不认** |

## 影响面

- 用户看到的是「我明明点了同意，它还说不行」—— 与「最小必要打扰」正好相反
  （多问了一遍，而且点了也没用）。
- `142fc0d` 那条「授权属于会话」（`user-grants.cjs`）解决的是**跨轮**问题，
  解决不了**卡片**这条来源 —— 两者是不同的洞。

## 修法方向（未实施，供后续决策）

不要为此新建一套授权语义，最小改动是**让卡片答复进入同一个判据**：

1. `ask_user` 的答复里带一个结构化的「授权意图」字段（不是靠解析用户选的那句中文）；
2. `loop-tool-context.cjs` 每轮记 `noteGrant` 时，把「上一轮卡片答复里的授权意图」
   也算进 `granted`（判据仍只有 `user-constraints` 一处，不新写正则）；
3. 撤销口径不变：正文里说停手 / 这轮只读，照旧清掉。

风险点：不能让**任意**卡片答复都算授权（那等于绕开「开工前先问清楚」）——
只认「卡片本身就是问授权这件事」的那几种 kind。
