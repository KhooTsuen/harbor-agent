# 发布检查 —— 发 beta / 正式版逐条勾

> 流程位置见 [`开发流程.md`](开发流程.md)。
> **发版工具在仓库里**（`package.json` 的 `release:*`），不再靠 `tmp/` 里的一次性脚本。
>
> ⚠️ 2026-10-06 修了一次：这套流程原来写的是「复制上一轮的 `tmp/*.cjs` 改版本号」——
> 而 `tmp/` 有卫生检查（条数 / 体积超限会被清），那批脚本**已经丢了**，照本文发版第一步就报
> 「找不到文件」。**发版是反复要跑的事，工具进仓库、有名字**；一次性脚本别再往文档里写。

## 版本号规矩（自检 54 组会拦）

- 源头：`package.json`；同步 `package-lock.json`（两处 version）；`CHANGELOG.md` 第一条标题**逐字一致**；`README.md` 不写 x.y.z。
- 一把核对：`npm run check:rules`（含「改了代码必须升版本号」）＋ 内核自检 54 组（版本号四路一致）—— 不绿不发布。
- **通道规矩（1.20.0 正式版起）**：小改动走**补丁号**（`1.20.1`、`1.20.2` …），
  新功能走**次版本号**（`1.21.0`）。正式版一旦发出，`data/` 的字段与迁移在这个次版本内**冻结**
  （要变就带迁移 + 回退路径，见 [`更新与数据迁移.md`](更新与数据迁移.md)）。
  beta 通道只在正式版之前用：一个次版本发正式版时，最后那版 beta 就是它的前置（内容相同、只差版本号）。

## 发一个 beta（标准 9 步）

1. **源码全绿**：`npm run verify`（typecheck → lint → 格式 → 行数 → 单测 → 自检 → 构建）。
2. **升号 + 写 CHANGELOG**：四处版本号；CHANGELOG 一节写清**为什么** + **验证数字**（单测 / 自检项数、真机对照）+ **诚实写遗留**（「还没做」）。
3. **提交 + tag + push**：普通 git 命令，没有包装脚本：`git add -A` →
   `git commit -F <信息文件>`（多行中文走文件，别往命令行里塞）→ `git tag -a v<版本> -m "Harbor <版本>"`
   → `git push origin main` → `git push origin v<版本>`。
4. **打包**：`npm run package`（typecheck + build + 组装便携版）→ `npm run release:zip`（打 zip）。
   产物 `dist-portable/harbor-<版本>-win-x64.zip`（约 147MB，**不含 data/**）。
   两个脚本各自会校：包内版本和 `package.json` 一致、zip 里真的没有 `data/`、`Harbor.exe` 在里面。
5. **GitHub Release**：`npm run release:upload`（Pre-release 加 `--beta`，只看打算做什么加 `--dry`）。
   token 走 `git credential fill`（和 push 同一份）；正文直接取 `CHANGELOG.md` 里这一节；
   **幂等**：Release 已存在就用它、同名资产已存在就跳过 —— 重跑安全。上传要几分钟。
6. **更新安装版 E:\Harbor**：先确认应用没在跑，再用 robocopy（**两边都排除 data/**）：
   `robocopy <开发仓库>\dist-portable\Harbor E:\Harbor /MIR /XD data`，退出码 < 8 算成功。
   （原来那两个 `tmp/check-running.cjs` / `tmp/update-harbor.cjs` 已经不在仓库里）。
7. **真机核对**：关于页必须显示新版本号（也可以直接看 `E:\Harbor\resources\app\package.json`）。
8. **看 CI**：新的 commit push 之后，CI 要 `success` 才算完（本地 `npm run verify` 与 CI 的步骤逐条一致，
   但历史上 CI 独有的红都是环境类：Linux 编 node-pty / jsdom / 钩子状态）。看运行状态用
   <https://github.com/KhooTsuen/harbor-agent/actions> 或 `gh run list`。
9. **收尾 + 版本保留**：按下面的《Release 保留策略》把旧版删掉（只留 1 个 beta + 1 个正式版）；
   新版本补进 [`更新历史.md`](更新历史.md) 的索引表；仓库记忆更新；历史 zip / 截图攒多了移进 `E:\Harbor-归档资料`（04-开发仓库留档）。

## 发正式版与 beta 的差异

- tag / 标题去掉 `-beta.N`；`prerelease: false`；其余步骤相同。
- 发正式版前，让用户用 beta 真机走过一轮验收（`npm run acceptance` + 个人版测试指南）。

## Release 保留策略（1 个 beta + 1 个正式版）

- **规矩**：GitHub 的 Releases 与 tags 永远只留 **最新 1 个 beta + 最新 1 个正式版**；新版发布成功后，删掉被替下的那个。
- **为什么不靠手删**：2026-09-26 一天连发了 16 个 beta，攒到 31 个版本。现在用的是仓库脚本
  （原来那个 `tmp/gh-clean-releases.cjs` 已经丢了）：
  ```
  npm run release:prune -- --keep=v<新版本>,v<新 beta> [--tags] [--apply]
  ```
  **默认 dry-run**（不 `--apply` 只打印打算删谁，一个请求都不发）；`--keep` 是必填的
  （不给就什么都不删，避免手滑把 Releases 清空）。
- **本地 tag 也要删**（否则下次 `git push --follow-tags` 会把旧 tag 复活）：`git tag -d <旧版本>`。
- **删除只影响「版本入口 + zip」**：代码提交都在 git 历史里；需要旧版本号可
  `git tag <版本> <SHA> && git push origin <版本>` 回建标签（zip 无法恢复）。
- **更新内容不会丢**：正文只写一份，在 [`CHANGELOG.md`](../CHANGELOG.md)；
  归档索引（含已删除版本）在 [`更新历史.md`](更新历史.md)。
- 归档索引（含已删除版本）在 [`更新历史.md`](更新历史.md)。
- 原来还有一份 `tmp/releases-manifest-all.json`（tag → SHA → 一句话）—— **也已不在仓库里**；
  tag → SHA 现在用 `git show-ref --tags` 现查（tag 没删的话）。

## 硬规矩与已知坑

- 打包会把 `dist-portable/Harbor/data/credentials.json` 搬进 `data/backups/<时间戳>/` ——
  **设计行为**（密钥不跟便携包走），不是丢失。
- 本机 `npm.ps1` 被策略挡：用 `npm.cmd`，或直接 `node <脚本路径>`。
- 多行中文 commit 信息：`git commit -F <文件>`，不要往命令行里塞。
- 更新完的 E:\Harbor 首次启动自己跑数据迁移；`data/` 永远不手工动。
- 回滚：程序文件盖回旧版即可（`data/` 不动）；数据出问题用 `data/backups/` —— 见 [`更新与数据迁移.md`](更新与数据迁移.md)。
