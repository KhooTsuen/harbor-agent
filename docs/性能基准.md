# 性能基准

> 规范《开源发布前检查》第 21 节要的是**有数字**，不是"感觉不卡"。
> 这份是当前版本的实测结果与**复现方法**。数字都是相对值（不同机器会差），
> 关心的是**规模变化时会不会退化**（O(n²) 才是「越用越卡」的根）。

测量机器：Windows 10 · Node 24 · 开发机（非专用测试机，数字偏保守）。

## 零、真机十场景（1.20.0-beta.22 实测，隔离副本 + CDP 驱动）

跑法（先在隔离副本里备好夹具，脚本见 `tmp/perf/`）：

```bash
node tmp/perf/run-all.cjs --runs=2      # 十场景 × 2 轮，结果落 tmp/perf/final-*.json
node tmp/perf/analyze-final.cjs         # 生成对照表
node tmp/perf/diag-scroll.cjs           # 需要热点归因时：CPU Profile 抓自耗时最高的函数
```

夹具：`sess_perf1000.jsonl`（1004 条消息 / 456 次工具调用 / 1821 个代码块）+
「一条回答含 50 次工具调用」「5 条各含 220 行代码块」「10 层分叉」三条。
两个大夹具由 `tmp/perf/gen-fixture.cjs` 按固定种子生成（口径可复现）；
场景 3 / 5 / 6 的数字**取决于尾部那几条消息的重量** —— 换一套夹具重测数字会差，
别把两套混着比。

| 场景 | 目标 P95 | 现在 P50 / P95 | longtask 数 / 最大 |
| --- | --- | --- | --- |
| 1 空闲状态 | <17ms | 16.7 / 16.9 | 0 / 0 |
| 2 长会话滚动 | <25ms | 16.7 / 16.9 | 0 / 0 |
| 2b 全量渲染滚动（压力） | <25ms | 16.7 / 16.9 | 0 / 0 |
| 3 流式渲染中（1000 条会话 + 真实 4000 字回复） | <33ms | 16.7 / 17.0 | 9 / 87ms |
| 4 展开 50 次工具调用 | <25ms | 16.7 / 17.0 | 2 / 84ms |
| 5 展开 5 个 220 行代码块 | <25ms | 16.7 / 17.1 | 1 / 97ms |
| 6 切换对话 | 瞬时 <200ms | 首屏 135ms / 16.9 | 1 / 79ms |
| 7 侧栏搜索输入 | <17ms | 16.7 / 16.9 | 0 / 0 |

**探针自身开销**：按帧记账的自采样回调约 **2–5µs/帧**（空场景对照：开/关探针 p50 都是 16.7ms、
DOM 变更数 0）。

### beta.22 修掉的三处（改前数字来自同机同夹具的基线）

| 项 | 改前 | 改后 | 依据 |
| --- | --- | --- | --- |
| 长会话滚动（14.3 万节点） | P50 33.3 / P95 50.1 | P50 16.7 / P95 16.9 | CPU Profile：`elementFromPoint` 自耗 1545ms / 3975ms 采样 |
| 切换对话（1000 条） | 首屏 4334ms，一次 3820ms 长任务 | 首屏 135ms，最大 79ms | Profile：建 14.3 万节点占 4.5s 里的 3.2s |
| 长会话里流式 | **渲染进程卡死**（求值 5s 超时） | 流式 44s 全程求值 7–35ms | 用未改动的 beta.21 同样复现；`persist` 每次 set 序列化 9MB |

### 还没解决的（有数字）

- 一次性挂载类长任务：切千条会话 79–117ms、分支树 111ms、任务中心滚动 110ms、展开大代码块 80ms。
- 主进程读 9MB 会话约 700ms（切换首屏已达标，但会话越大越吃亏）→ 会话尾读 / 分页。
- 真正的虚拟滚动仍未做：当前是「窗口 24 条 + 载入更早」，靠**实测高度**而不是估算高度
  （0.57.2 关掉虚拟滚动就是因为估算高度不准，见 git 历史）。

## 一、渲染层（jsdom 基准）

跑法：

```bash
npx vitest run src/components/chat/__tests__/rendererPerf.test.tsx \
               src/components/chat/__tests__/rendererPerfList.test.tsx
```

断言盯的是**规模有界**（节点/行数不随数据线性爆炸）与**不退化**（耗时大致线性），
耗时只在真的退化成平方时才红 —— 所以下面这些数字每次跑都会打出来，可以横向对比。

| 场景 | 耗时 | DOM 节点 |
| --- | --- | --- |
| 空列表 | 8 ms | 20 |
| 一条消息 | 9 ms | 34 |
| **1000 条消息（首屏只画最近 12 条）** | **0 ms** | **364** |
| 1000 条消息（后台分片补满 24 条） | — | 725 |
| 点「载入更早」（补到 48 条） | — | ~1400 |
| 20 次滚动事件 | 1 ms | 364 |
| **10000 个工具事件（收起）** | 5 ms | **10** |
| **10000 个工具事件（展开到底）** | 72 ms | 1223 |
| 10000 步任务时间线 | 9 ms | 50 |
| 3000 段 Markdown | 735 ms | 9001 |
| **2 万行代码块（默认折叠）** | 199 ms | 224 |
| 2000 次流式更新 | 65 ms | 2 |

**怎么读**：`DOM 节点` 那一列才是关键。1000 条消息首屏只 364 个节点（旧版是 6005 个 ——
一次画 200 条）；10000 个工具事件收起时只占 10 个节点；2 万行代码块只占 224 个 ——
说明「该折叠的折了、该截的截了、该分片的分了」。

## 二、Electron 层（真机）

| 指标 | 实测 |
| --- | --- |
| 进程启动 → 调试端口可用 | **898 ms** |
| 渲染层 DOMContentLoaded | **369 ms** |
| 界面可用（输入框出现，含启动动画） | **≈ 2.8 s** |
| 渲染层 JS 堆（空闲时） | **9.5 MB**（total 11.3 MB） |
| 空闲时 DOM 节点数 | 486 |
| 进程工作集合计（4 个进程，含 GPU / 工具进程） | **471.9 MB**（最大单个 146.4 MB） |

启动动画占了大头（可跳过：启动页上有「跳过」）。

怎么复现：

```bash
# 启动耗时：起进程，轮询 --remote-debugging-port，算时间差
"dist-portable/Harbor/Harbor.exe" --remote-debugging-port=9336 &

# 内存：另开一个窗口跑
powershell -Command "Get-Process Harbor | Measure-Object WorkingSet64 -Sum"
```

界面内的启动指标走截图工具的自定义脚本：

```bash
node tools/shot-electron.mjs --exe=... --js-file=tmp/probe-boot-timing.js
```

## 三、Agent 执行（内核）

- **背景执行隔离**：`tools/bench-isolation-probe.js` —— 任务索引把「每次工具调用通读全表
  240 ms」降到 **38 ms**
- **分段计时**：`electron/core/perf-marks.cjs` 记「上下文 / 模型 / 工具 / 搜索」四段与首字上屏，
  界面在右栏「状态 → 性能」；这是设计里"能看见慢在哪"的那一环
- 单轮 10+ / 25+ 次工具调用、长时间 Shell、多次搜索：走的是同一条循环与预算闸
  （五项预算见 `budget.cjs`），没有单独的基准数字

## 四、**还没测**的（不装作测过）

| 项 | 为什么没测 |
| --- | --- |
| 长时间运行（几小时~几天） | 需要挂着跑很久，没做 |
| 休眠 / 唤醒 | 同上，且要人工干预 |
| CPU 占用曲线 / 火焰图 | 没做采样分析，只有分段计时 |
| 多窗口 | 应用是单窗口设计（`main.cjs` 只开一个），没有这个场景 |
| macOS / Linux 上的性能 | 只验过能构建能跑，没测性能 |

需要哪一项就说 —— 每一项都不难，只是要花真实时间挂着跑。
