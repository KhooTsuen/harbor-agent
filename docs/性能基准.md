# 性能基准

> 规范《开源发布前检查》第 21 节要的是**有数字**，不是"感觉不卡"。
> 这份是**实测结果与测量口径**。数字都是相对值（不同机器会差），
> 关心的是**规模变化时会不会退化**（O(n²) 才是「越用越卡」的根）。

> ⚠️ **这是一份快照，不是当前版本的基准**（2026-10-06 标注）：下面的数字测于
> **1.20.0-beta.22（2026-09-27）**，此后到 `1.29.0` / `1.30.0-beta.2` 没有再重测；而且当时的探针脚本
> （`tmp/perf/*`、`tmp/probe-*.js`）**都已不在仓库**（`tmp/` 有卫生检查，条数 / 体积超限会被清）。
> 结论：**「怎么量」的口径仍然有效，里面的具体数字当历史看**；要出新基准得照下面的口径重写探针。

测量机器：Windows 10 · Node 24 · 开发机（非专用测试机，数字偏保守）。

### 还没解决的（有数字）

- 切会话仍有**一个 69–76ms 长任务**，发生在消息落进 store 那一刻：真机时间线显示它是
  **布局**成本（消息区 + 侧栏一起重排），不是 JS —— 首屏条数从 12 降到 6 也几乎不动它。
  要再往下压得动「整份会话进渲染进程」这条路：会话尾读 / 分页（真机时间线：24 条补完
  ≈10k 节点）。
- 主进程读 5.5MB 会话 + 渲染进程反序列化 1004 条是这一下的另一半（时间线上它就在长任务前）。
- 真正的虚拟滚动仍未做：当前是「窗口 24 条 + 载入更早」，靠**实测高度**而不是估算高度
  （0.57.2 关掉虚拟滚动就是因为估算高度不准，见 git 历史）。

## 一、渲染层（jsdom 基准）

跑法：

```bash
npx vitest run src/components/chat/__tests__/rendererPerf.test.tsx \
               src/components/chat/__tests__/rendererPerfList.test.tsx
```

断言盯的是**规模有界**（节点/行数不随数据线性爆炸）与**不退化**（耗时大致线性），
耗时只在真的退化成平方时才红 —— 所以下面这些数字每次跑都会打出来，可以横向对比。

| 场景 | 耗时 | DOM 节点 |
| --- | --- | --- |
| 空列表 | 8 ms | 20 |
| 一条消息 | 9 ms | 34 |
| 1000 条消息（首屏只画最近 6 条） | **0 ms** | **184** |
| 1000 条消息（后台分片补满 24 条） | — | 725 |
| 点「载入更早」（补到 48 条） | — | ~1400 |
| 20 次滚动事件 | 1 ms | 364 |
| **10000 个工具事件（收起）** | 5 ms | **10** |
| **10000 个工具事件（展开到底）** | 72 ms | 1223 |
| 10000 步任务时间线 | 9 ms | 50 |
| 3000 段 Markdown | 735 ms | 9001 |
| **2 万行代码块（默认折叠）** | 199 ms | 224 |
| 2000 次流式更新 | 65 ms | 2 |

**怎么读**：`DOM 节点` 那一列才是关键。1000 条消息首屏只 364 个节点（旧版是 6005 个 ——
一次画 200 条）；10000 个工具事件收起时只占 10 个节点；2 万行代码块只占 224 个 ——
说明「该折叠的折了、该截的截了、该分片的分了」。

## 三、Agent 执行（内核）

- **背景执行隔离**：`tools/bench-isolation-probe.js` —— 任务索引把「每次工具调用通读全表
  240 ms」降到 **38 ms**
- **分段计时**：`electron/core/perf-marks.cjs` 记「上下文 / 模型 / 工具 / 搜索」四段与首字上屏，
  界面在右栏「状态 → 性能」；这是设计里"能看见慢在哪"的那一环
- 单轮 10+ / 25+ 次工具调用、长时间 Shell、多次搜索：走的是同一条循环与预算闸
  （五项预算见 `budget.cjs`），没有单独的基准数字

## 五、2026-11-01 重测（v1.32.0 打包版，隔离副本）

> 上面「零 / 一 / 二」都是 **1.20.0-beta.22（2026-09-27）** 的快照，探针 `tmp/perf/*` 已不在仓库。
> 这一节是**重新测的**，口径与「二、Electron 层」对齐，脚本是一次性的（`tmp/p4/perf.mjs` /
> `tmp/p4/perf2.mjs`，按 `tmp/` 卫生规矩不进仓库，要复现照下面「怎么复现」重写）。

**测的是什么程序：** `data/harbor-test/runs/phase2-pkg/Harbor/Harbor.exe`
（打包版隔离副本，自带 `data/`，`build-info.json` 记 `version 1.32.0` / commit `34b6aaa`）。
**没碰** `E:\Harbor`（用户正在用的那份），也**没碰**源码树 `data/`。

| 指标 | 本次实测（v1.32.0） | beta.22 旧数字 |
| --- | --- | --- |
| 进程启动 → 调试端口可用 | **1173 / 1183 ms**（两次运行） | 898 ms |
| 进程启动 → 输入框出现 | **2085 / 1796 ms** | ≈ 2.8 s（含启动动画） |
| 进程启动 → 开机动画消失 | **3053 / 3126 ms** | —— |
| 空闲时进程工作集合计（起实例前后的差集，4 个进程） | **453.4 / 456.3 MB** | 471.9 MB |
| 渲染层 JS 堆（空闲） | **8.5 MB**（上限 10.3 MB） | 9.5 MB |
| 空闲时 DOM 节点数 | **1947**（文档 2 个） | 486 |
| 布局次数 / 样式重算（此刻累计） | 40 / 14 | —— |

**常用操作（longtask 口径）：** 在页面里挂 `PerformanceObserver({type:'longtask'})`，
跑一串真实操作，数「主线程被阻塞 >50 ms」的次数。

| 操作 | 结果 |
| --- | --- |
| 空闲基线（静置 3 秒，不操作） | 0 次 longtask |
| 打开设置 | 0 次 |
| 设置里切到「对话」 | 0 次 |
| 设置里切到「模型」 | 0 次 |
| 关闭设置 | 0 次 |
| 新建单独对话（单独复测，300 ms 粒度） | 响应恢复 < 330 ms，0 次 longtask |
| 切换对话（连切 4 次） | 21 / 671 / 294 / 296 ms（从点击到选中态出现），**4 次全部 0 次 longtask** |

> 切会话那组数字波动大（21 → 671 ms），原因是隔离副本里几个会话的消息量差很多，且每次点的是
> **另一条**会话（来回切）。**结论只取 longtask 那一列**：没有一次主线程阻塞超过 50 ms，
> 也就是说清单里记的「切会话有一个 69–76 ms 长任务」在 v1.32.0 这个副本上**没有复现**
> —— 但样本只有 4 次、夹具不是那个 1000 条消息的压力会话，不能当「已解决」。

**这次换了口径，原因是旧口径在这台机器上量不准**（记下来免得下次又踩）：
一开始按「点击 → 下一帧」计时，量出来每一步都是 ~1590 ms、而且几乎一模一样 ——
那是**隔离实例不在前台时 Chromium 节流 rAF / 定时器**的结果，加上脚本里等待循环跑满，
量的是节流而不是产品性能。改用 longtask（由主线程真实阻塞产生，不受节流影响）才有意义。
同理，DOM 节点数从 486 涨到 1947 是**口径不同**（那次量的是空会话，这次左栏有历史会话 +
右栏开着），不是「变慢了 4 倍」，不要横向比。

**没测到的（本次明确未覆盖）**：内存与启动数字只取了一个实例的一次空闲态，
没有做「跑一段时间后是否增长」；也没有 CPU 火焰图。多窗口、休眠唤醒仍同第四节。

怎么复现（命令口径，脚本要按这个重写）：

```bash
# 起打包版隔离副本（它自带 data/，与用户正在用的那份互不影响）
data\harbor-test\runs\phase2-pkg\Harbor\Harbor.exe --remote-debugging-port=9340

# 启动三段：spawn → /json/list 可用 → textarea 出现 → .harbor-boot 消失
# 内存：起实例前后各取一次 tasklist /FI "IMAGENAME eq Harbor.exe"，用 PID 差集认领本次实例
# 操作：页面内装 PerformanceObserver({type:'longtask'}) 后跑操作序列，读回条目
```
