# 自举开发流程：用 Harbor 开发 Harbor

> ⚠️ **历史快照**（2026-10-06 标注）：本文是 2026-10-04 那轮的实测记录，**结论仍成立**
> （打包那一步不能在 Harbor 里跑 / 起副本的手法），但正文里的 `tmp/tok/*`、`tmp/b2-machine-probe.cjs`
> 等路径**已不在仓库**（`tmp/` 会被卫生检查清），要复制做法得自己按现况搭副本。

> 2026-10-04 实测。**结论先说**：改源码 + 测 + 构建 可以在 Harbor 里一条龙做完；
> **但「打包」这一步不能在 Harbor 里跑** —— 打包脚本会按镜像名杀掉所有 `Harbor.exe`，
> 包括发起它的那一份（实测：副本 4 个进程 → 打包后 0 个）。

## 0. 三条验证的结论

| 验证 | 结论 | 关键证据 |
| --- | --- | --- |
| ① 单实例锁 | ✅ **不挡**（两个实例可并存） | 锁只在**同一个 data 目录**内互斥；开发版 `data/` 与装机版 `data/` 天然不同 |
| ② 打包流程 | ⚠️ **能跑，但会自杀** | `npm run package` 实测 20.8s；`build-portable.mjs` 第 0 步 `taskkill /F /IM Harbor.exe` |
| ③ 长任务 | ✅ 前三步跑通、❌ 打包步中断 | 实测 4 次工具调用 / 5 轮：write ✓ edit ✓ vitest ✓ → 打包把应用杀了 |

---

## 1. 验证①：单实例锁

### 实现（读代码）

`electron/main.cjs`：

```js
const HEADLESS = SELF_TEST || SCREENSHOT          // --self-test / --screenshot
const gotLock = HEADLESS || app.requestSingleInstanceLock()
if (!gotLock) app.quit()                           // 第二个实例直接退出
else app.on('second-instance', …)                  // 加锁成功那个：聚焦已有窗口
```

```js
app.setPath('userData', path.join(DIRS.data, 'chromium'))   // ← 锁跟着这个目录
```

所以锁的粒度是 **data 目录**（Electron 的 ProcessSingleton 在 userData 里放锁）：

- 同一份 data 目录里启动第二次 → 第二个进程**立刻退出**（退出码 0，连「启动：」日志都不写）；
- data 目录不同 → **互不影响**，两个窗口可以同时开。

### 实测（隔离副本，不碰 E:\Harbor\data）

| 动作 | 结果 |
| --- | --- |
| 起副本 `tmp/tok/lock1`（实例 A） | 进程数 4、日志出现 1 条「启动」 |
| **再起一次同目录**（实例 B） | 15s 后：退出码 **0**、进程数仍 4、启动日志仍 **1 条** → **被挡住** |
| 起**开发版** `electron .`（data = `E:\CodexWorkbench\data`） | 开发版写出自己的启动日志，副本仍活着（4 个进程）→ **两者并存** |
| 开发版再起一次（同 data 目录） | 退出码 0、启动日志不涨 → 自己挡自己 |

### 结论与绕过办法

- 「在 Harbor 里启动开发版验证改动」**成立** —— 装机版 `data/` 在 `E:\Harbor\data`，
  开发版在 `E:\CodexWorkbench\data`，本来就是两个锁。
- 想再开一份同目录的：`--self-test` / `--screenshot` 会**跳过锁**（代码里 `HEADLESS`），
  但那两种模式跑完就退出，不是拿来日常用的。

## 2. 验证②：打包流程

### 实测数字（本机，`E:\CodexWorkbench`）

| 命令 | 耗时 | 退出码 |
| --- | --- | --- |
| `npm run build`（`tsc --noEmit` + `vite build`） | **15.6s** | 0 |
| `node scripts/build-portable.mjs`（组装便携版） | **10.2s** | 0 |
| `npm run package`（= 上面两步） | **20.8s** | 0 |

产物：`dist-portable/Harbor`（394 个文件 / 356 MB，其中 `data/` 占 2 MB，更新时要排除）。

### 工具超时够不够

`run_shell` 的超时口径（`electron/core/tools/run_shell.cjs`）：

```js
const timeoutSec = Math.min(600, Math.max(5, Number(args.timeout) || ctx.shellTimeout || 60))
```

- 默认取设置里的 `tools.shellTimeout`（出厂 **60s**，可夹 5–600）；
- 调用时可以逐个命令给 `timeout`（AI 也能自己带）；
- **硬上限 600s**。

**打包 20.8s，默认 60s 就够**；但建议在台词里显式带 `timeout: 300`，防止以后构建变慢时踩线。

### ★ 致命点：打包会杀掉正在运行的应用

`scripts/build-portable.mjs` 第 0 步：

```js
const APP_NAME = 'Harbor.exe'
await spawn('taskkill', ['/F', '/IM', APP_NAME])   // 按镜像名杀，不看路径
```

**实测对照**：

| 场景 | 结果 |
| --- | --- |
| 起一份隔离副本（4 个进程、CDP 答话），在**别处**跑打包 | 打包成功（10.8s、产物在）→ **副本进程数 0、CDP 断线** |
| 同样起副本，改跑 `npm run build` | 15.2s 结束 → 副本**照样活着**（4 个进程、CDP 在线） |

后果（在 Harbor 里跑打包时）：

1. 发起打包的**那份应用自己被杀** → 界面没了；
2. 这一轮的工具结果**永远回不来**（子进程还在跑，父进程已经没了）→ 会话卡在「执行中」；
3. 用户装的那份 `E:\Harbor` 只要开着，**同样被杀**（按名字杀，不看是哪一份）。

### 绕过（按推荐度）

1. **打包放外面做**（推荐，今天就能用）：Harbor 里只做「改源码 + 测试 + `npm run build`」，
   打包 + 同步装机版用一个 cmd / PowerShell 窗口跑（这两步本来也是「发布动作」，一天没几次）。
2. **给 `build-portable.mjs` 加保护**（要改代码，**待拍板**）：把 `taskkill /IM` 换成
   「只杀占着产出目录的进程」，或加 `--no-kill` 开关。改了之后 Harbor 内打包才安全。
3. 只更新装机版代码、不重新组装运行时（**不用** `build-portable`）：
   把 `dist/` 与 `electron/` 覆盖进 `E:\Harbor\resources\app\`（**先关掉应用**，再覆盖）。

### 打包产出 → 装机版

```bat
:: 关掉应用（两个都不能开着），然后：
robocopy E:\CodexWorkbench\dist-portable\Harbor E:\Harbor /MIR /XD E:\CodexWorkbench\dist-portable\Harbor\data E:\Harbor\data
:: 退出码 < 8 都算成功；data/ 两侧都排除
```

本次已实测成功（robocopy exit=3）。更新前后**必须核对 `data/` 指纹**（见第 5 节）。

## 3. 验证③：长任务

### 一个「改源码 → 测试 → 打包」要几轮

实测（假模型脚本化，但内核/工具/shell/台账全是真的）：**4 次工具调用 / 5 轮模型**。

| 轮 | 动作 | 结果 |
| --- | --- | --- |
| 1 | `write_file src/lib/bootProbe.ts` | ✅ 文件真的写出来了 |
| 2 | `edit_file` 改它一处 | ✅ 内容真的变了（`n + 1` → `n * 2`） |
| 3 | `run_shell` vitest 单跑一个测试文件 | ✅ 测试结果回到模型，驱动了第 4 轮 |
| 4 | `run_shell` `npm run package` | ⚠️ 应用在这一步被杀（见验证②） |
| 5 | 收尾 | 没跑到（父进程已经没了） |

### 界面会不会被长命令卡住

不会。工具是主进程里 `exec()` **异步**跑的（输出按字节回收），渲染层不受影响：

- 实测：`npm run build` 那 **15.2s** 里，应用一直能答话（CDP 在线、进程数不变）；
- 变慢的是**那一轮**：工具没返回之前，这轮对话就是「执行中」，模型也拿不到结果。

### 对话被裁剪后，AI 能靠进度文件恢复吗

能，而且这是本项目的既有做法：

- **`AGENT.md` 每轮都注入**（`electron/core/project.cjs` 读它 → 系统提示的项目层）——
  硬约束、硬禁区、验收纪律不依赖对话历史；
- **进度台账是文件**（如 `docs/收尾与maxTokens拆分.md`）：被裁剪掉之后，AI 只要
  `read_file` 就能拿回「做到哪、下一步是什么」；
- 裁剪本身会留痕（`context-builder` 的「〔…上下文已按预算裁剪…〕」），
  所以 AI 知道自己少看了东西、可以去重读；
- 实践证据：本批任务（收尾 + 拆 maxTokens + 自举验证）就是跨多轮、靠
  `docs/` 台账 + `git log` 恢复上下文完成的。

**给自举的启示**：长任务开工前先让 AI 建一份进度文件（一行一步 + 勾选状态），
每完成一步就落一次盘 —— 这比「指望上下文不被裁」可靠。

### ★ 在 Harbor 里验界面时，**不要跑 `npm run package`**（正确做法：覆盖进副本）

第 2 批做真机验证时踩实了这条：`npm run package` = `npm run build` + `build-portable.mjs`，
而 `build-portable.mjs` 第 0 步是 `taskkill /F /IM Harbor.exe` —— **按镜像名杀，不看路径**。
所以在 Harbor 里发起打包 = 杀掉发起方自己（工具结果永远回不来，会话卡在「执行中」），
用户装的那份 `E:\Harbor` 只要开着也一起被杀。

**正确做法（实测可用，2026-10-04）**：把刚构建的产物**覆盖进隔离副本**，再起副本：

```js
// ① 拷贝前先杀干净副本里的老进程（残留实例会让 cpSync 只拷一半、还不报错）
// ② 覆盖 dist/ 与 electron/（只这两样，不动 data/ 与运行时）
fs.rmSync(join(APP_DIR, sub), { recursive: true, force: true })
fs.cpSync(join(SRC, sub), join(APP_DIR, sub), { recursive: true })
// ③ 拷完自检：缺文件就当场报错，别等「应用起不来」再去猜
// ④ 起副本（HARBOR_APP 要在 require 探针库之前设，那个库在加载时就把 APP 定下来了）
process.env.HARBOR_APP = 'E:/CodexWorkbench/tmp/tok/s2'
```

现成脚本：`tmp/b2-machine-probe.cjs`（连带 CDP 连 webview guest 的写法）。
它验的是「新代码在**真机**里跑不跑得起来」—— 单测与自检都在纯 Node 里，碰不到 Electron 的
`session` / `webview` / 通知这些只在真机上才存在的东西。

## 4. 推荐流程（今天就能用）

### 日常改代码（在 Harbor 里做，全程不碰打包）

1. 在 Harbor 里打开仓库目录当工作目录（`E:\CodexWorkbench`）。
2. 让 AI 改源码 → 跑 `npm run test:unit`（~20s）/ `npm test`（内核自检 ~12s）/
   `npm run build`（15s，**不会杀进程**）。
3. 要看界面效果：另开一个 cmd 跑 `npm run dev`（Vite 热更新 + Electron 开发窗口，
   data 目录是 `E:\CodexWorkbench\data`，与装机版**不冲突**，实测两个可并存）。
4. 收工前：`npm run verify`（全链，含内核自检；这是提交前的门禁）。

### 发布到装机版（放到外面做）

1. 关掉**所有** Harbor 窗口（装机版 + 开发版）。
2. 一个 cmd 窗口里：
   ```bat
   cd /d E:\CodexWorkbench
   npm run package            :: 20.8s
   robocopy dist-portable\Harbor E:\Harbor /MIR /XD dist-portable\Harbor\data E:\Harbor\data
   ```
3. 核对 `data/` 没被动过（见第 5 节），再打开 `E:\Harbor\Harbor.exe`。

### 一句话总结

> **改码、测试、构建 → 在 Harbor 里（不用切窗口）；打包、装机 → 在外面的 cmd 里（一天一次）。**

## 5. 兜底方案

### 崩了怎么办

- **一定要保留一个外部入口**（命令行或 VS Code）：Harbor 崩了之后，
  「用 Harbor 修 Harbor」这条路是断的 —— 至少要有 `npm run verify` / `git` 能在外面跑。
  VS Code 不是必须的，但**命令行是必须的**。
- 崩溃现场：`data/crash/`、`data/logs/`、`npm run errors`（错误观察哨）。
- 撑不住时的降级顺序：① 换个 data 目录重开一份（`--self-test` 可跳过锁）/ ② 命令行跑验证链 / ③ 回 VS Code。

### 数据怎么备份（更新装机版之前必须做）

1. **先关应用**（不然文件可能正被写）。
2. 抄一份 `E:\Harbor\data`（或至少 `config.json` / `credentials.json` / `sessions/` / `memory.*`）。
3. 记下 `data/` 指纹三件套：**文件数 / 总字节 / 最新 mtime**；更新后逐个核对必须一致。
4. 更新前顺手确认装机版版本号（`E:\Harbor\resources\app\package.json`）与
   `dist-portable\Harbor` 一致 —— 一致就是「已是最新」，**什么都不用做**。
5. 更新只动 `E:\Harbor`（`data/` 两侧都排除），不要在别处写东西。

### 什么情况下必须切回 VS Code

- 要**调试主进程**（断点 / Inspector）：`npm run dev` 有 `DEV_INSPECT_PORT`，
  但在外面用 VS Code 更顺手；
- Harbor 起不来 / 界面白屏：那时只能在外部看日志、跑测试；
- 要改**打包脚本 / 自举流程本身**（比如给 `build-portable.mjs` 加 `--no-kill`）——
  这类改动会影响 Harbor 自己的运行环境，**先在外面改、验证完再进来用**。

## 6. 还没解决 / 需要拍板

1. **要不要给 `build-portable.mjs` 加保护**（`--no-kill` 或按路径过滤）？
   不加 → 打包永远得在外面跑；加了 → Harbor 内可以一条龙（但改的是发布脚本，风险在那 20 行）。
2. 打包那一步的「工具结果丢失」：**即使加了 `--no-kill` 也还在** —— 同步装机版要求
   「先关掉正在运行的应用」，而发起方往往就是那份应用（自己更新自己）。
   真要做到「一条龙」，得改成两段式：应用内只负责 `npm run build` + 落一份待发布产物，
   外部脚本负责关应用 → 组装 → 同步。
3. 自举时的**权限档位**：验证用的是 `permission: full + fileScope: workspace`。
   日常用建议保持 `workspace`（工作目录内免授权、外面才问），别长期开 `full`。
