### ★ 真缺口：流里的错误被静默丢弃（最高优先级）

`llm.cjs` 的 reader 循环是这么写的：

```js
const chunk = parsed.json
const choice = chunk?.choices?.[0]
...
const delta = choice?.delta
if (!delta) continue          // ← 错误就死在这一行
```

**OpenRouter 会在 HTTP 200 的正常流里发错误**：

```
data: {"error":{"code":402,"message":"Insufficient credits. Add more using ..."}}
```

这行没有 `choices` → `delta` 是 undefined → `continue` 静默跳过。
**症状是「回答空白、不报任何错」** —— 比直接 500 难查得多。
`chunk.error` 现在完全没被检查过。

**必须修**：见到 `chunk.error` 或「既没有 choices 也没有 usage」的 chunk，
把 `error.message` / `error.code` 抛出来。这条比参数适配更该先做。

### 模型名带命名空间 —— 参数适配必须兼容

两家都用带前缀的模型名：`openai/o3-mini`、`google/gemini-2.5-pro`、
`deepseek-ai/DeepSeek-R1`、`Qwen/Qwen3-32B`。

所以 P0-3 里「o 系模型要改名 `max_completion_tokens` 并丢 `temperature`」
的正则**必须处理 `vendor/` 前缀**：

```
/(^|\/)(o1|o3|o4|gpt-5)/      ← 不能只写 /^(o1|o3|...)/，否则 OpenRouter 上的 o 系照样 400
```

### `extraBody` 在这两家上的实际用途（说明它为什么值得做）

- **OpenRouter**：`{"provider":{"order":["DeepInfra","Together"],"allow_fallbacks":true}}`
  —— 选后端、控制回退，我们可以不去实现这些概念，用户自己塞
- **硅基流动**：Qwen3 系列的 `{"enable_thinking":false}`、`{"thinking_budget":...}`
  —— 关掉思考省 token，只有它自己的端点认

**这正是「万能兜底」的价值**：这些参数我们不该挨个做进代码。

## P0-3 参数写死

**现状**：`llm.cjs:76-88`，只发 `temperature` / `top_p` / `max_tokens` / `tools`。

**改什么**（三件事，按收益排序）：

1. **`extraBody`（万能兜底，最该先做）**
   provider 加 `extraBody: object`，直接 merge 进请求体。
   怪站点要什么字段，用户自己塞就行，**不用等我们改代码**。
   冲突时以 `extraBody` 为准（用户显式配置优先）。

2. **模型族自动适配**（治 o1/o3/gpt-5 的 400）
   ```
   /^(o1|o3|o4|gpt-5)/  →  max_tokens 改叫 max_completion_tokens
                          丢掉 temperature / top_p（官方端点会 400）
   ```
   放在一个纯函数 `adaptBody(body, model)` 里，好测。

3. **`omitParams: string[]`** —— 明确不发哪些字段（和自动适配互补，兜住没预料到的模型）。

**顺带**：`reasoning_effort` 从已有的 `assistant.reasoning`（low/medium/high）映射过去；
`response_format` 透传（JSON 模式）。

**工作量**：小。`llm.cjs` 一个纯函数 + provider 字段 + UI 三个输入框。

**风险**：低。默认行为不变（不配就不发）。

## P0-2 鉴权

**现状**：4 处各写一遍 `if (apiKey) headers.Authorization = \`Bearer ${apiKey}\``。

**改什么**：抽一个 `buildAuthHeaders(provider, apiKey)`，四处都调它。provider 加：

```js
authStyle: 'bearer' | 'api-key' | 'none' | 'custom'   // 默认 bearer
authHeader: 'Authorization'                            // api-key 风格填 'api-key'
authPrefix: 'Bearer '                                  // api-key 风格填空串
extraHeaders: { 'X-Foo': 'bar' }                       // 额外头
```

**⚠️ 密钥纪律（必须处理，否则违反项目铁律）**：
`extraHeaders` 里很可能出现密钥。必须让 `config-secrets.cjs` 的 `absorb()`
把 extraHeaders 里的敏感值搬进凭证库，只在 config.json 里留 `ref`；
`redact.cjs` 也要认识这种形态。**这条不做就等于把密钥写进 config.json。**

**工作量**：小（4 处替换 + 3 个字段 + 密钥搬运）。

**风险**：中 —— 密钥搬运要仔细，改错就是「密钥落盘」或「头部带 ref 字符串发出去」。

## P0-5 `stream_options.include_usage`

**改什么**：`if (provider.streamUsage !== false) body.stream_options = { include_usage: true }`

**必须可关**：有些站点对未知字段直接 400。
建议再加一层保险：**收到 400 且错误文本里提到 `stream_options` 时，去掉该字段重试一次**
（只重试一次）。这条能省掉一堆「为什么这个站点不行」。

**工作量**：极小。

## P1-4 代理

**第一步（推荐先只做这个）**：环境变量。用 undici 的 `EnvHttpProxyAgent`，
读 `HTTPS_PROXY` / `HTTP_PROXY` / `NO_PROXY`。用户设了就用，没设就完全不影响。

**第二步**：provider 级 `proxy: 'http://127.0.0.1:7890'`，
在 `fetch(url, { dispatcher })` 里传 `new ProxyAgent(provider.proxy)`。

**⚠️ 标记「待实测」**：Electron 主进程的 `fetch` 是 undici，
但 `setGlobalDispatcher` / `dispatcher` 选项在 Electron 里是否完全生效**我没有实测过**。
做的时候第一件事是写个 5 行脚本验证，别直接假设。

## P1-1a Gemini 原生格式（要做的）

**现状**：只发 OpenAI chat 格式。Gemini 官方端点不吃这一套。

**端点与鉴权**（和 OpenAI 完全不同，是三处不一样）：
```
POST {baseUrl}/v1beta/models/{model}:streamGenerateContent?alt=sse
x-goog-api-key: <key>          ← 不是 Authorization: Bearer
```
- **`?alt=sse` 是必须的**。不加的话返回的是一整个 JSON 数组而不是流，reader 循环会卡住。
  （踩过类似的坑：SSE 解析器只看 `data:` 行，非 SSE 响应会静默什么都不吐。）

**请求体映射**（OpenAI → Gemini）：
| OpenAI | Gemini |
|---|---|
| `messages[{role:'system'}]` | `systemInstruction: { parts: [{ text }] }`（**不在 contents 里**） |
| `role:'user'` | `contents[].role = 'user'` |
| `role:'assistant'` | `contents[].role = 'model'` ← 名字不一样 |
| content 字符串 | `parts: [{ text }]` |
| `tools[].function` | `tools: [{ functionDeclarations: [...] }]` |
| `temperature` / `top_p` / `max_tokens` | `generationConfig.temperature` / `topP` / `maxOutputTokens` |

**响应流映射**：`data: { candidates[0].content.parts[].text }`；
用量在 `usageMetadata.{promptTokenCount, candidatesTokenCount, totalTokenCount}`。

**⚠️ 两个真坑**：

1. **Gemini 的 `functionDeclarations` 不接受完整 JSON Schema。**
   `additionalProperties`、`$schema`、`default` 这些会直接报错 400。
   必须写一个 `sanitizeSchema()` 只保留它认的子集（type / properties / required /
   description / enum / items）。**这个坑一定会踩，先写好。**
2. **工具结果要包一层 `response`**：
   `{ role:'user', parts:[{ functionResponse:{ name, response:{...} } }] }`。
   而且 `functionResponse.name` 必须和之前的 `functionCall.name` 对上 ——
   我们现在的 messages 里只有 `tool_call_id`，**没有工具名**，
   这段映射要额外处理（在 adapter 里维护 id→name 的小表）。

**做法**：和下面那条一样，走协议适配层，不要在一个函数里 if/else 堆。

**建议分两批**：
- **第二批**：文本 + 流式（能让 Gemini 先聊起来，覆盖大部分使用场景）
- **第三批**：工具调用（上面那两个坑都在这批）

## 协议适配层（Gemini 落地的方式）

新增 `electron/core/llm/protocols/`：
- `chat.cjs` —— 现状搬过来（OpenAI 兼容，绝大多数中转站走这条）

## 验收怎么做

1. **不需要联网的单元测试**（放 `scripts/selftest/`）：给定 provider 配置 + 模型名，
   断言最终请求体 —— 覆盖 `extraBody` 合并、`omitParams`、o 系模型改名/丢温度、
   `include_usage` 开关、四种鉴权头的形状。**这是主要防线**，便宜且能防回归。
2. **`provider:ping` 要回显上游原文**：现在报错会被包一层，用户看不出到底哪不对。

3. **真机至少过一遍**：一个标准中转站 + 一个 Azure 风格（`api-key` 头）
   + 一个 o 系模型（验证改名）。**我没法自己弄到这些端点，需要你提供。**
4. 密钥纪律：配一个带密钥的自定义头，然后**检查 `config.json` 里没有明文**
   （`grep` 一下就够），`data/audit` 和日志里也没有。
