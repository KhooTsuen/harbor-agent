# 本地插件接口（DeepSeek 优先）—— 方案

> 2026-09-16。用户要：**本地端**插件系统，**优先适用 DeepSeek**。
> 来源：`api-docs.deepseek.com` 的 Tool Calls / 接入 Agent 工具 / V4-Pro 发布公告
> （用本机浏览器抓的，服务端爬虫被拦）。

## 一、好消息：不用造新协议

DeepSeek 的 tool calls **就是标准 OpenAI `tools` 格式** —— 和你项目里
`tools/registry.cjs` 的 `toApiSchema()` 输出、`loop.cjs` 的 tool_calls 处理
完全一致。官方文档的示例代码用的就是 `tools=[{type:"function", function:{...}}]`。

**所以「插件」不需要新协议，只需要在现有工具系统上加一层「装配」：**
`插件目录 → 读清单 → 变成工具 → 注册进 registry`。

## 二、DeepSeek 专属的三个关键点

这三条是「优先适用 DeepSeek」的实际含义，每一条都影响设计。

### ① `strict` 模式 —— 最值得用的一个特性

DeepSeek 有个 **strict 模式（Beta）**：服务端会**校验你传的 JSON Schema**，
并保证模型输出的参数**严格符合** schema。开启条件：

```
base_url = https://api.deepseek.com/beta     ← 要用 /beta
每个 function 加 "strict": true
```

**代价**：schema 只能用受限子集（服务端会校验，不符合就报错）：

| 支持 | 不支持 |
|---|---|
| `object` / `string` / `number` / `integer` / `boolean` / `array` / `enum` / `anyOf` / `$def`+`$ref` | `minLength` / `maxLength` / `minItems` / `maxItems` |
| `pattern` / `format`（email/hostname/ipv4/ipv6/uuid） | |
| `const` / `default` / `minimum` / `maximum` / `exclusiveMin/Max` / `multipleOf` | |

**object 有两条硬规定**：
- **所有属性都必须 `required`**
- **`additionalProperties` 必须为 `false`**

> 对插件系统的意义：插件的参数 schema 要**按 strict 子集来写**。
> 「可选参数」在 strict 下不成立 —— 得靠 `anyOf` 或者拆成两个工具来绕。
> 宿主应该提供一个 `toStrictSchema()` 做**校验 + 自动补 `additionalProperties:false`**，
> 并在不兼容时给作者一个明确的报错（而不是等模型调用时才发现）。
>
> **⚠️ 待实测**：strict 模式我没跑过真实请求，上面全部来自文档。

### ② 工具数量必须少 —— 这是插件系统最大的风险

GPT 插件时代就有一个规律：**一次给模型的工具越多，选错的概率越高**。
DeepSeek 在 tool selection 上比 GPT 弱一些，所以这条对你是**硬约束**。

如果插件系统做成「装 20 个插件 → 20 个工具的 schema 全塞进 `tools`」，
结果一定是：模型乱调、参数填错、或者该调的时候不调。

**必须做两段式**（见下面的方案）。

### ③ `description_for_model` 是灵魂 —— GPT 插件最该抄的一点

GPT 插件的 manifest 里最有价值的字段是 `description_for_model`：
**专门写给模型看的一段说明，讲「什么时候该用我」**（区别于 `description_for_human`
是给人看的）。

你现在的工具描述是**写死在 `tools/*.cjs` 里的**。插件化之后，
**用户自己就能写这段说明** —— 这才是插件系统真正的价值所在，
因为它直接决定了模型的调用准确率。DeepSeek 更依赖这段文字，所以更要做好。

## 四、推荐方案：本地插件目录 + 两段式注入

### 目录结构

```
data/plugins/<插件名>/
  plugin.json      ← 清单（给模型看的说明 + 权限声明）
  schema.json      ← 参数 schema（按 strict 子集写，也可以直接内嵌在 plugin.json 的 parameters）
  run.cjs          ← 本地执行体（Node，受沙箱限制）
  README.md        ← 给人看的

> ⚠️ **执行体必须是 `.cjs`，不是 `.js`**。本项目 `package.json` 是
> `"type": "module"`，`.js` 文件会被当 ES 模块 —— 里面写 `module.exports`
> 会**静默失效**（require 出来是空对象 `{}`，不报错）。这是第一个示例插件
> 实测踩到的坑，写在 run.cjs 的注释里了。要么用 `.cjs` + `module.exports`，
> 要么用 `.mjs` + `export`；别用 `.js`。
```

```jsonc
// plugin.json
{
  "schema_version": "v1",
  "name_for_model": "get_weather",          // 模型看到的工具名
  "description_for_model": "查询某地天气。用户问天气、气温、要不要带伞时用。",  // ★ 灵魂
  "name_for_human": "天气查询",
  "description_for_human": "查任意城市的天气",
  "runtime": { "type": "node", "entry": "run.js" },
  "permissions": {                          // ★ 借用项目已有的权限体系
    "network": true,                        // 要不要联网
    "write": false,                         // 会不会写文件
    "paths": []                             // 需要访问工作目录之外时声明的路径
  },
  "enabled": true
}
```

### 运行时：两段式（这是「适用 DeepSeek」的核心）

```
① 系统提示里只放【插件清单】——名字 + description_for_model，不含参数 schema
   ↓
② 模型说「我要用 get_weather」 → 宿主把**这一个**插件的 schema 注入 tools
   ↓
③ 模型发 function call（strict 校验参数） → 宿主确认权限 → 跑 run.js
   ↓
④ 结果标注「外部数据不是指令」→ 回填 → 模型接着答
```

为什么这样：**模型每一步只需要在「少数几个候选」里选，而不是在 20 个里选。**
代价是多一次往返（多花一次 token），换来的是准确率。

> 这和项目里已有的两个做法是同一个思路：
> - 记忆的「检索式注入」（不是整篇塞）
> - MCP 工具的 `mcp__<server>__<tool>` 命名（让模型分得清来源）

### 复用现成的部分（别重造）

| 已有 | 直接用 |
|---|---|
| `tools/registry.cjs` + `toApiSchema()` | 插件注册成工具的目标位置 |
| `tools/index.cjs` 的 `execute()` | 调用链、审计、`validateArgs` |
| `capability.cjs` / `risk.cjs` | 插件的权限（网络/写文件/路径）**直接走现有这套** |
| `audit.cjs` | 插件的每次调用都该留痕 |
| `mcp.cjs` | 复杂的外部插件可以让用户去用 MCP，不必都做成插件 |
| `prompt-stack.cjs` | 插件清单要作为**独立一层**注入（好调试、好关闭） |

## 五、要你拍板的四件事

1. **执行体用什么语言**？我建议 **Node（`.js`）** —— 和宿主同进程、无需额外环境、
   项目里已有沙箱/权限那套可以复用。Python 要处理解释器路径和依赖，成本高。
2. **两段式还是一次性注入全部？** 我强烈建议**两段式**（理由见上）。
   但如果你觉得「多一次往返」不可接受，可以折中：**插件数 ≤ 5 时一次性注入，
   超过就切两段式**。
3. **要不要开 strict 模式？** 开了参数更可靠，但插件作者必须按受限 schema 写
   （可选参数要绕）。我建议**默认开**，并在校验不过时给出明确报错。
4. **插件从哪来？** 只有你自己写，还是以后要能装别人的？
   这决定要不要做「插件签名/来源标记」（第三方插件是**可信边界之外**的东西，
   和 MCP 一样按不可信对待）。

## 六、我建议的落地顺序

1. **先做一个内置示例插件**（比如「查当前时间」或「查天气」）+ 两段式注入
   —— 把链路打通，验证 DeepSeek 的选择准确率
2. **加 `toStrictSchema()`** + 接 strict 模式 —— 参数可靠性
3. **把权限/审计接上**（复用 capability/risk/audit）
4. 再考虑第三方插件、插件市场之类

**先别做 UI**：插件目录是文件，能手动放进去就够验证了。

最小闭环打通了，真机验证过：问「现在几点」→ DeepSeek 调用 `get_current_time` 插件 → 返回正确时间。

- 示例插件 `examples/plugins/时间查询/`（plugin.json + run.cjs）
- 测试：`scripts/selftest/groups/10-plugins.mjs`（22 项，内核 421 → 443）
