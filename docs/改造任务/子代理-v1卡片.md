## 1. v1 要解决什么

v0 让「派子代理」这件事**能跑**，但跑起来之后用户什么都看不到 —— 内核里写着：

> 子代理的事件**不**转发给父的流：v0 只在任务台账里可见（界面不画树）。

于是用户看到的只有父任务最后那段结论。可子代理的**全部价值**是「父上下文里不留原文」，
用户更需要看见「它到底读了什么、跑到哪一步了」——否则那就是个黑盒。

v1 就是补这一层：**子代理内部每一步实时上界面**。

## 2. 这一版做了什么

- **内核把子代理的每一步转出去**：`subagent.cjs` 不再只往数组里攒，改成把每次工具调用
  （`agent.tool.started` / `completed` / `failed`）实时转给界面。
  ★ **只转这三种** —— 不能按 `agent.tool.` 前缀一把捞：`agent.tool.progress`（长任务自报进度）
  也吃这个前缀，捞进来会变成一条没有 id、tool 为空的**假「完成」步**。
- **对话流里多一张「只读子代理」卡**（`src/components/chat/SubagentCard.tsx`）：
  标题 + 状态（进行中 / 完成 / 失败）+ `n/m 步 · n 轮 · 耗时`，下面逐条列出每一步。
  视觉跟「执行计划」卡（`PlanCard.tsx`）对齐 —— 2026-09-30 拆掉旧工具卡片就是因为
  「两张卡长得不一样，接缝一眼可见」，不再犯第二次。
- **起止都有边界事件**（`kind: start / done`）：子代理一个工具都没调时，界面照样知道它开过、
  结束了，不会出现一张什么都不说的空卡。
- **卡片里不存子代理读到的原文**：`SubagentStep` 只有 `tool` + `args`（+ 成败/耗时）。
  两个理由：① 那些原文本来就不该进父上下文（上下文隔离正是子代理的意义）；
  ② 全存下来会把会话文件撑爆（一次读 7 份文档就是几百 KB）。
- **没新增 IPC 通道**：复用现有的 `chat:event`。

## 3. 为什么这么接（两处关键决策）

**① 用注入，不用新通道。** 项目里早有先例：工具自己**不该知道**自己的 `toolCallId`
（那是 runner 的事），由 `tool-runner` 注入 `ctx.progress` 时贴上。v1 照抄这一招，
多注入一个 `ctx.subagentEmit`：子代理产生的载荷由 `tool-run-ctx.cjs` 贴外壳
（补事件名 + 父侧那次调用的 `toolCallId`）。于是：

```
tool-runner → buildRunCtx(ctx, { emit, toolCallId, toolName })
            → tools.execute('spawn_subagent', args, runCtx)
            → subagent.spawn({ task, ctx: runCtx })
            → ctx.subagentEmit(payload)   ← 子代理每步都走这里
```

**② `tool-run-ctx.cjs` 是被逼出来的。** `tool-runner.cjs` 原本**正好 300 行**（AGENT.md
硬约束 2 的红线），新的注入塞不进去 → 把「这次调用专用的 ctx」整块搬出去。
这是**搬家**，不是顺手重构（顺手重构是禁区）；搬完 tool-runner 净减 19 行。

## 4. 怎么验证的

| 项 | 命令 | 结果 |
| --- | --- | --- |
| 全链 | `npm run verify` | 绿（typecheck → lint → lint:kernel → 格式 → 行数 → 规则 → 单测 → 内核自检 → 构建） |
| 单测 | `npm run test:unit` | 全过（新增 2 个测试文件；卡片用自搭的 `createRoot` + jsdom 渲染器） |
| 内核自检 | `npm test` | 全过（新增「子代理 v1 / 每一步转给界面」一组；组数看输出，这里不写死） |
| 内核 no-undef | `npm run lint:kernel` | 0 未定义 |

**新增的钉子钉的是「归位」，不是「画得好不好看」**（这类毛病单测照不出来，
AGENT.md 第 9 条）：

- 内核那一组是**真跑**（桩模型喂一次 `read_file`）：断言 start / step / done 都到、
  每条都带 `subagentTaskId`、**转出去的东西里没有文件原文**（隔离没破）、
  没注入 `subagentEmit` 时退化成「只攒不发」也照常跑完。
- 渲染层那一组：`toolCallId` 对不上时**不新建**记录（宁可什么都不显示）；
  `started → completed` 认成**同一行**；id 对不上时**不张冠李戴**；
  没有轨迹的老会话**不长出空卡**。
- 跨层形状用**源码守卫**钉住（内核发的事件名 / `kind` 取值 / 三个字段名，
  渲染层都认）。**字符串契约要从源码里抠出来验**，不能两边各信各的 —— 这是 AGENT.md
  第 9 条点名要的。

## 5. 诚实写的遗留

- **真机截图这一步没做**（2026-10-07）。原因不是代码，是环境：这个应用的**主进程**要
  重启才会加载新内核，而当时没有一条「不打断正在用的窗口」的路子。你下次在 beta.5 里
  跑一次就能看到卡片；想验的话，让父任务派一次子代理（提示句见 v0 验收步骤那份）。
- **子代理的 token 用量仍然是 0**：v0 就记下这条（不并回父 `tokens` 是因为父循环每轮
  覆盖写入），连「记在子任务自己台账上」这个替代方案也**没落地**。
  所以「上下文隔离到底省不省」这个问题，**这一版还是答不了** —— 要正确归因得改
  `loop-run.cjs` 的用量基座，属于单独一件事。
- **v0 那个「父的约束原样变成子的约束」的坑没治**：测试时提示句里那句
  「你自己不要 read_file、只能调 spawn_subagent」被原样传进子代理，害它去试派孙代理
  （被深度上限拦下）。这属于**提示词的角色分层**，是另一件事。
- 卡片只在**父那条消息**上；没做「点开跳去任务中心看那个子任务」。
