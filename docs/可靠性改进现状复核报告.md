### 2.4 故障注入方案（**本轮只设计，不执行**）

> 原则：在**隔离副本 `test-env/` + 隔离 `data/`** 上做；**绝不碰真身**（不 `taskkill /IM`，只杀自己起的 PID）。

1. **截断注入**：写盘前/中让目标文件只写一半（可用「把 `writeFileSync` 用 wrapper 包成先写 half 再抛」的探针，仅在副本里生效）→ 断言：读回是否「报错可见」或「静默丢」。
   - 验收：任务台账 → 应能被 `data-doctor` 报出；凭证 → 应能留坏文件（**当前不会，暴露缺口**）。
2. **写失败注入**：把目标目录临时设为只读 / 用文件句柄占住目标（模拟 `EPERM`）→ 断言：`safe-write` 该重试成功；裸写该**抛错且不静默**。
3. **断电模拟**：在 rename 前 `process.abort()`（子进程里）→ 断言：原子写路径下目标文件**要么旧要么新**（无半截）；裸写路径下可能出现半截（对照证明差异）。
4. **备份覆盖检查**：造一批 tasks/credentials → 跑 `backup.create()` → 断言：它们**不在**备份里（证明 §2.2 的缺口）。

## 4. 任务四：E1 环形依赖复核

> 复算：`tmp/_v4-cycles.mjs`（缩进判软边）+ `tmp/_v5-cycles2.mjs`（大括号深度判软边，交叉验证）。口径：`electron/core/**/*.cjs`。

**复算结果（快照 2026-10-13）**：

| 指标 | 值 |
|---|---|
| 模块数 | 222 |
| require 边总数 | 524 |
| 顶层（硬）边 | 457（缩进判）/ 446（最保守：两判据都说硬） |
| 函数内（软）边 | 67（缩进判）/ 47（深度判） |
| **去重环数** | **23**（缩进判） |
| **未破的环（无软边）** | **0** |
| **纯顶层硬边图里的环** | **0** |

**核查结论**：

1. **环确实存在** —— 推翻审计 §9.2 的「没发现环形依赖」。**未破的环 = 0**（每个环至少含一条函数内 `require`）。
2. **数字为何与清单的「11」不同**：清单用「最短环去重」，本轮用「节点集合去重 + 全起点枚举」，会数出更多变体（7/8/9/10 边同一条工具链上的不同闭环）。**方法不同，实质一致**：都存在、都靠惰性 require 破、都无自检。
3. **误报核查**：两种软边判据（缩进 vs 大括号深度）有 **42 处分歧** —— 抽查全是**多行解构的 `require`**（`const { a, b } = require(\n './x.cjs'\n)`），其 `require(` 行有缩进但深度为 0 → 缩进判**误报成软边**。用**最保守口径**（两判据都说硬才算硬）复算，**纯硬边图仍是 0 环** ⇒ **结论稳健，不因判据选择而变**。
4. **真正的事实**：`electron/core` 的**顶层 require 图是无环 DAG**；所有环都是「顶层 + 函数内」混合形成的，靠惰性 require 破解。
5. **最要命的缺口不变**：**没有任何自检盯「环」**。新增一条顶层 `require` 造出「纯硬边环」、或把某条破环的软边挪到顶层，**没人报红**（后者会把「运行期 undefined」变成「加载期直接崩」）。

**只读监控方案（不拆环）**：

- **M1（零风险）**：把 §4 这套扫描做成**只读报告**（像 `npm run map`），只列出：环清单 + 每环的软边位置 + 「未破的环」计数。**不进 verify、退出码恒 0**。
- **M2（补钉）**：加一条断言 **「纯顶层图里的环 = 0」** —— 这是**当前事实、也是安全底线**（真出现就是加载期崩溃）。**未破的环 ≠ 0 时立刻红。**
- **M3（防回归）**：若某条「软边」被挪到顶层造成新环，M2 就会红 —— 这正好堵住「破环的线被搬回顶层」这个最危险的改动。
