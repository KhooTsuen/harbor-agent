# 让 AI 写代码，怎么才不会被它自己骗过

> 这是 Harbor（一个本地优先的个人 AI Agent 工作台）在开发过程中攒下的约束机制。
> 不是方法论，是一堆被真实事故逼出来的检查。可以直接抄。

## 一、那个让我改了整套做法的 bug

2026 年 9 月，我给一个面板加了新功能。TypeScript 编译通过，lint 干净，单元测试全绿，内核自检也过了。我点了「发送」，什么都没有发生。

不是报错，是**静默不更新**。拆文件的时候切多了一段，主流程里留了个空函数占位。tsc 看不出差别——函数签名还在，类型对，返回类型对。单元测试也看不出，因为测试覆盖的是那几个被搬走的函数，它们各自工作正常。

坏的只有**层与层之间的接线**。而接线，测试照不到。

同一周还有一次更离谱：有个浮层组件少写了 `forwardRef`，真机上**永远不会显示**。测试全绿。因为测试跑在 jsdom 里，它不关心这个东西在真浏览器里能不能被定位到。

两次都是同一个形状：**机器说没问题，人一摸就坏。**

## 二、结论只有一句

> 能机械查的，不许靠自觉。

AI 编程工具最大的问题不是写不出代码，是它**写完会说「已完成」**。而「已完成」这个判断，它自己是靠什么下的？靠 tsc 过了、测试绿了。

所以真正要建设的不是「让它写得更好」，是**让它骗不过你**。

下面这些是 Harbor 里实际跑着的东西。都不是什么高深设计，全部来自「这次被坑了，下次别再被坑」。

## 三、第一层：能写成命令的规矩

`AGENT.md` 里每一条硬约束，都必须带一列「**检查方式**」，写成能跑的命令。写不出检查方式的，那条就不算约束，只是愿望。

实际的检查清单（`npm run check:rules`，接在 git pre-commit 上）：

| 检查 | 为什么它在 |
| --- | --- |
| 单文件 ≤ 300 行 | 这条规矩原本只写在文档里，靠自觉。结果某天被破了 3 个文件，**没有任何东西会报出来** |
| `package.json` 与 lock 文件依赖两侧一致 | 「我装了但没进 lock」，换机器就炸 |
| 密钥扫描 | 硬编码的 key 一旦进了 git 历史，改一次不够 |
| 明文 TODO / FIXME 残留 | 半成品的味道 |
| `AGENT.md` 还在、且没被整段覆盖 | 有次批量替换**吞掉了两节**，是我提交前读回改动才发现的 |
| **改了代码必须写 CHANGELOG** | 见下面第四节，这条的演化最有意思 |
| 仓库卫生（根目录条目数、tmp 体积） | 临时脚本会无限堆积 |
| 会涨的数字不许写死 | 文档里写的「六条硬约束」和实际条目数**对不上过一次** |

最后一条值得单独说：**只要一个数字会随版本变化，就不许写进文档**。IPC 通道数、自检项数这类，文档里只能说「看输出」。这个项目在这方面漂过三次，最后还是靠一条机械检查才焊住。

## 四、第二层：规矩自己也会腐坏

「改了代码必须升版本号」——这条规矩本来是对的，而且很早就写在发布检查文档里。

问题是它只在**发版那天人工核对**。平时忘了升，没人拦，一直要到发版才发现，中间那些提交的版本号全是假的。

于是改成「每次提交必须升版本号」。解决了「忘了升」，但顺手把**版本号变成了提交计数器**。几个月后代价显出来：CHANGELOG 攒到 234 个版本段，一天之内发过 16 个 beta；其中连续 7 个版本代码提交了、版本号升了、CHANGELOG 也写了，但 Release 和 tag 一个都没建。

再后来才改对：**版本号只在发布时升，平时只需要在 CHANGELOG 顶部写一笔 `## [未发布]`**。

三次改口径，每次都是「发现旧做法在制造新问题」。教训是：**规矩不是一次写对的，它是被事故一次次磨出来的，所以必须留出改它的通道。**

## 五、第三层：同一件事只许写一处

这是我在这套东西里最贵的一条经验。

有一天连着栽了四次，全是同一个形状——**两边各自都对，接起来什么都不发生，而且谁也不报错**：

- 一个模块搬走了确认表，还引用着旧名字 `pendingConfirms` → 每轮结束抛一次未处理拒绝
- 巡查器挂了计时，但没人把那条往返结算掉 → 任务干等 5 分钟兜底
- 巡查器读 `timeoutMs`，配置给的是 `clarifyTimeoutMs` → `undefined` **静默退回默认 10 分钟**
- 渲染层写 `event.threadId`，主进程事件里带的是 `sessionId` → 静默不落盘、不显示

四次都过了 tsc、lint、单测、自检，全绿。

**为什么四道全绿的门都拦不住？**因为每一道门都在问「你这一侧对不对」，没有一道门在问「你两侧是不是在说同一件事」。

后来补的闸门也都是照着这个形状来的：

- 内核的 `.cjs` 文件不参与 tsc，`node --check` 只查语法。所以另写了一个 `no-undef` 扫描（`lint-kernel.mjs`），带允许清单，而且**清单过期也报红**——不删过期条目等于把闸门焊死。这个扫描加完当天第一次运行，就逮到 `electron/handlers/shell.cjs` 里引用了未定义的 `inspectCommand`。
- 跨模块的事件名、字段名、时序，靠自检组钉「**形状对齐**」：测试夹具直接吃生产方的输出，不手写一个「差不多」的对象。

一句话：**测试要钉「两边接得上」，不能只钉「各自能跑」。**

## 六、第四层：检查脚本自己也要有测试

这条听起来像没问题找问题，但它是被现实逼出来的。

第一版检查脚本 358 行——被它自己的第一条规则（≤300 行）抓住了。检查脚本的测试文件 338 行，同样超线。两个都得拆。

更阴的一次：跑检查脚本的测试，用 `node --test "scripts/check-rules*.test.mjs"`。**实测 Node 不展开这个通配符**，一个都没匹配到时，退出码仍然是 0，输出 `tests 0 / pass 0 / fail 0`。

**看着全绿，其实一个都没跑。**

所以现在有一条：测试脚本如果**一个用例都没找到，必须报红**。

## 七、第五层：验证链只有一处

这个项目曾经在一件事上吃过很大的亏：本地全绿，CI **连红 15 次**，前 13 次没人发现。

根因不是某个 bug，是**CI 和本地各写了一份步骤清单**，而 CI 那份多了一个本地没有的格式检查。两份都「看起来对」，接起来就对不上——和第五节说的完全同一种病。

解法很朴素：**CI 不再自己抄步骤，只跑 `npm run verify`。**步骤清单的唯一真相源就是 `package.json` 里那一条链，本地的 pre-push、CI、一键 preflight 全部指向它。结构上漂不了。

## 八、最后：机器判不了什么，必须说清楚

这套机制的天花板很清楚，写文档时也一起写进去：

- **真机能不能用**：钩子跑的是 Node 侧的东西，装不了「窗口里点一下能不能发出消息」。改 UI、会话、发送、权限，必须真的跑一遍，而且要用截图或 DOM 读数留证据。
- **需求自相矛盾**：两条要求互相打架，脚本看不出来。
- **有没有偷偷扩大范围**：「顺手重构一下」这种事，只能靠代码 review。
- **代码 review 本身**：单人项目，没有第二个人看，所以「自己举报自己」成了硬性规定。

所以这个项目有一条规矩：**不输出任何未验证的「已完成」**。报告里必须给命令、数字，或者一次真实观察。说「看不到」是允许的；把猜测当事实不允许。

## 九、如果你只想抄三样东西

按投入产出排：

1. **一条 `verify` 链**（typecheck → lint → 行数 → 单测 → 自检 → 构建），让本地、pre-push、CI **全部指向它**，别各写一份。
2. **一个 pre-commit 钩子**跑「能机械查的规矩」，并且每条规矩都带一句能跑的命令。写不出命令的，不算规矩。
3. **一张「改了什么 → 必须补什么验证」的表**，写进给 AI 看的说明文件里。比如「改了 UI → 真机走一遍 + 截图」「改了数据结构 → 拿旧数据文件实测能读」。

第 3 条最容易被忽略，但它决定了 AI 是「交了差」还是「交了个能用的东西」。

---

这套东西不能保证代码没 bug。它保证的是另一件事：

**当 AI 说「做完了」的时候，你有办法知道这句话是不是真的。**
