## 二·补、两套工具执行器：谁在用、差在哪（2026-11-05 · P2）

## 这一节回答「同一个操作从不同入口发起，会不会一个拒绝、一个绕过」。

### 1. 执行器层面只有一处真实差异 —— 已修

`electron/core/` 里有**两份**执行器：

| 执行器 | 谁在调 | 说明 |
|---|---|---|
| `tool-runner.executeToolCalls` | `loop.cjs`（唯一生产路径） | 并行 + 部分成功检测 + 结构化失败摘要 |
| `loop-tools.executeToolCallsSerial` | **没有调用方** | 保留作回退路径；`loop-tools.cjs` 只把它当第二份导出 |

实测差异（探针跑真命令 `node -e "process.exit(1)"`，修前 / 修后）：

```
               ok      facts             事件
串行（修前）   true    null              agent.tool.completed   ← 绿勾
并行（修前）   false   {exitCode:1}      agent.tool.failed
串行（修后）   false   {exitCode:1}      agent.tool.failed      ← 与并行一致
```

根因：`tools.execute` 的契约是「`ctx.wantMeta === true` 才返回 `{ text, toolOk, … }`，
否则返回字符串」。串行那份没传，于是拿到纯文本 `…[退出码 1]`，前缀不是「错误：」，
`isToolOk` 判成成功。同一族还漏了 `ctx.action` / `ctx.progress` / `ctx.subagentEmit` / `run.facts`。

**钉它的判据**：`209-exec-parity`。它跑**真命令**、比对两份执行器的 `ok` / `facts.exitCode` /
`reasonCode` / 事件名 / 喂给工具的 ctx 形状 —— 不是查源码里有没有某个字符串
（只钉正则的话改个变量名就骗过去了）。

### 2. 入口层面没有发现权限绕过，但有两处「看着像」

`tools.execute()` 是唯一咽喉，四个入口各自造 ctx：Agent 主循环（`loop-tool-context.cjs`）、
Codex MCP 桥（`codex-mcp-bridge.makeCtx`）、项目测试（`project-test-run.cjs`）、协作执行器。
同一批操作在**主路径 vs 桥**上实测结论一致：

| 操作 | 主路径 | 桥 | 结论 |
|---|---|---|---|
| `write_file` · ask 档 · 同意 | 放行（问 1 次） | 放行（问 1 次） | 一致 |
| `write_file` · ask 档 · 拒绝 | 拒绝（问 1 次） | 拒绝（问 1 次） | 一致 |
| 敏感文件 `.env` · 拒绝 | 拒绝（问 1 次） | 拒绝（问 1 次） | 一致 |

两处**看着像缺陷、核对后不是**：

- **桥在 `runId` 查不到时 `allowWrite` 兜底成 `true`**。但写类调用由审批层拦住
  （`codex-mcp-approval.cjs` 拿不到对话上下文就返回 false），探针实测界外文件确实没被创建。
  `codex-mcp-lifecycle.cjs` 的注释写的就是「不注入 → 写类调用被拒」，所以
  「未登记时只读仍可用」是**有意设计**。不准的是 `codex-mcp-context.cjs` 文件头那句
  笼统的「查不到就拒绝」—— 它只对需要审批的动作成立。
- **`ctx.permission` 的三元归一写法**。取值已被 `config-normalize.cjs` 收窄到三档，不是隐患。

### 3. 留下的设计问题（本阶段不做）

两份执行器**没有合并**。串行那份零调用方的状态保持不变 —— 合并属于架构调整，
要动 `loop.cjs` 与全部判据链，风险远大于收益。但它「永远跟着并行版走」这件事
现在只靠 `209` 一条测试保证，没有机制强制。

## 二·补二、任务与模型调用的关联追踪（2026-11-05 · P2 第二阶段）

### 1. 三种标识，各管一段（这是理解全节的前提）

| 标识 | 谁生成 | 长什么样 | 存在哪 |
|---|---|---|---|
| `sessionId` | 渲染层线程 id | `sess_…` / 线程 id | 会话文件、任务台账 |
| `requestId`（= `phaseKey`） | 每次发送新生成 | `req_…` | 事件外层 `taskId`、指标行 `trace`、状态机 key |
| `taskId` | `loop-run` 建 / 复用任务时 | `task_…` | 任务台账 `data/tasks/*.json` |

`chat.cjs` 的 `phaseKey = payload.taskId || requestId`，而**渲染层从不发
`payload.taskId`**（只有 `resumeTaskId`）→ 生产环境里 `phaseKey` 恒为 `req_*`。

### 2. 改前：关联在持久层里查不回来 —— 已修

唯一能连 `req_*` 与 `task_*` 的，是 `loop-run.cjs` 发的那条
`emit({ type:'task', taskId: task.id, … })`（外层 `taskId` 是 `req_*`，
`payload.taskId` 是 `task_*`）。但它**不落盘** —— `events.cjs` 只持久化
`name.startsWith('agent.')` 的事件，而 `metrics.timeline` 是显式 `persist: true` 才进去的。

真实数据实测（用户数据根，改前）：

```
data/logs/token-metrics.jsonl   4182 行 = 4042 行 trace=req_* + 140 行 trace 空
data/tasks/                     100 条台账，含 req_ 字样的 0 条
data/events/*.jsonl             153828 条 / 11 种类型；task 类型 0 条
                                （同文件里 metrics.timeline 有 1041 条 → 确实是按前缀判的）
```

**交叉验证不可能**：指标行里的 trace 在台账里搜不到，台账里也没有反向指针。

**修法**（净增约 4 行逻辑）：`loop.cjs` 给 `callModel` 多传一个 `taskId`（台账 id）→
`llm.cjs` 落指标时带上 → `token-metrics.logLlm` 落 `taskId` 字段。
`trace` 保留不动：一个是运行实例，一个是任务台账，**两个都记、谁也不替代谁**。

### 3. 五类场景的实测结论（`210-llm-attribution` 钉着）

| 场景 | 改前 | 改后 |
|---|---|---|
| 一个任务连续多次调用 | 两行 trace 相同，但落不到任务 | 同一个 `taskId` 两行 |
| 两个任务并发 | 各一行、trace 正确，但落不到任务 | 各一行，`trace ↔ taskId` 配对 0 错 |
| 失败后重试 | 只有成功那行（`retryIndex=1`） | 同上，`taskId` 仍对 |
| 降级换供应商 | 只有 `model`，看不出换了 provider | 指标行 `providerId=备份家`，`taskId` 不变 |
| 辅助调用（起标题/建议/预热/压缩） | `trace` 空、`providerId` 空 | 仍然空，但 `taskId` 是空串（**不瞎填**） |

★ 这一组的判据是**写进磁盘又读回来**的字段（`210` 直接读 `token-metrics.jsonl`），
不是源码里有没有 `taskId` 这个字符串 —— 只钉字符串的话，传错参数照样绿。

### 4. 尚未覆盖的追踪能力（如实登记，别当成已修）

| 缺什么 | 影响 | 为什么本阶段不动 |
|---|---|---|
| **失败的调用一行都不记** | 重试前的失败尝试、彻底失败的调用在 `token-metrics.jsonl` 里看不见；「这次失败花了多少 token」答不出来 | `llm.cjs` 只在成功收流后写指标。要修得改成「一进一出成对落盘」的记录模型 |
| **CLI 后端（codex-cli）完全不写指标** | 用本机 ChatGPT Codex CLI 当后端时，指标文件里一行都没有 | 它与 `llm.cjs` 同形契约，但没接 `logLlm`；补它要动 `codex-cli.cjs` 的收尾段 |
| **台账没有 provider 字段** | 降级换过供应商，事后从 `data/tasks/` 看不出来（指标行里有） | 加字段要过 `task.cjs` 的 `update()` 白名单 + 老任务兼容，属数据结构改动 |
| **子代理的归属只能靠前缀反推** | `subagent.cjs` 的 trace 是 `sub_<childTaskId>`，能反推出子任务，但**父任务**记不下 | 子任务有 `parentTaskId`，父子关系在台账里是全的；缺的是「哪次调用属于哪条」的直连字段 |
| **定时任务 / 协作执行器没有 trace** | 这两条入口调 `loop.run` 时没传 `traceId`，于是退化成 `taskId` 当 trace | 结果仍能归属（trace 就是 taskId），只是「第几次运行」分不出来 |

### 5. 最低回归标准（这一块以后不管怎么改都要维持）

1. `npm test` 里 `210-llm-attribution` 必须全绿 —— 它钉的是「指标行带 `taskId` 且
   `trace ↔ taskId` 配对正确」，这条一红就说明归属又断了。
2. 动 `llm.cjs` / `token-metrics.cjs` / `callModel` 的入参时，
   `kernel-types-baseline.json` **只许降不许升**（`chatStream` 的入参形状靠它兜）。
3. 往指标行加字段时，新字段必须同时满足：① 不记正文 / 密钥 ② 缺值记空或 null，**不填 0 冒充**
   ③ 老记录读出来是缺字段仍能用（`summarize()` 不炸）。

## 五、尚未被任何自动测试覆盖的真实场景

按「出了问题最难看」排序：

1. **真 Edge 里加载扩展 → 侧边栏真的能对话**：`154`/`156`/`157`/`160` 验的是协议与内核，
   `202` 验的是装得上；**「装上之后在真浏览器里点一下能用」没有任何自动证据**。
2. **真模型的行为质量**：所有自动测试的模型都是假的。工具选得对不对、话说不说得清，
   只有 `npm run preflight -- --acceptance`（花 token）能覆盖。
3. **多窗口 / 多会话并发授权**：`206` 有并发断言，但那是同进程内的并发；
   两个真窗口同时点「允许」没有验过。
4. **真 MCP 服务器**：全部用例用假 MCP（只验调用计数）。真实服务器的超时、重连、
   返回畸形数据都没验。
5. **断电 / 磁盘满**：只在下载链做过真注入；任务台账、会话文件、改动事务没做过。
6. **打包版升级 / 迁移**：`54-version-sync` 验版本号一致，但「旧版数据被新版读」没有自动化。

## 六、后续版本的最低回归标准

发版前**至少**跑完这些（缺一项就不算发得了）：

```bash
npm run preflight                 # verify（含内核自检 + 前端单测 + 安全默认档）+ 应用自检
npm run security:gate             # 严格档：P0 不许 FAIL / BLOCKED / NOT_RUN
```

改了下面这些，**额外**必须补：

| 改了 | 必须补 |
|---|---|
| `electron/core/tools/**`、`capability*`、`approval` | 真机走一遍授权链（`node tools/e2e-sensitive-grant.mjs`） |
| 工具结果形状 / 失败判定 | `node tools/e2e-tool-failure-visible.mjs`；**两份执行器的一致性**看 `209-exec-parity`（已在 `verify` 里） |
| 渲染层交互卡 / 选择器 | `node tools/e2e-clarify-card.mjs`（它自己会点卡） |
| 扩展 / Native Host | `node tools/e2e-*` 里与扩展相关的；再人工在 Edge 里点一次 |
| 失败恢复 / 重试 | `node tools/e2e-retry-rollback.mjs` |
| 并行 / 批量执行 | `node tools/e2e-fail-streak.mjs` |
| 任何 UI | 截图（`npm run shot:electron -- --dev`），别只看测试绿 |

> 一句话：**自动测试绿 + 至少一条真机链路走过**，才算这一版「验过」。
> 只跑 `verify` 就发版，等于把 CI 的覆盖范围当成产品的覆盖范围。

## 七、加一条新断言时

- 判据**优先用计数 / 行为**，别用文案：`204` 的教训是「只断言返回里有没有『拒绝』两个字，
  一个先拒了又照跑的实现照样全绿」。
- 别写 `check(name, true)`。真要表达「不抛异常」，就把可能抛的那句包起来并断言别的东西。
- 隔离数据一律走 `env.mjs` 的 `SANDBOX` / `paths.DIRS.data`（自检时是 `data/selftest-data`），
  **绝不**写 `join(ROOT, 'data', …)` —— 会落进用户真数据且不清理。
- 新组要在 `scripts/selftest/groups.mjs` 的 `GROUPS` 里注册。**没注册 = 没跑**，
  而「没跑」和「跑过了」在输出里长得一模一样。
