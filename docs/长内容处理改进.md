## 第一步：查清 `assistant.maxTokens` 与 `budget.conversation` 的真实语义

**结论：`assistant.maxTokens` 是「一物二用」——既是输出上限，又是上下文预算的基准。** 这是历史耦合，
`context-builder.cjs` 的注释里自己也写明了（2026-09-29 那次没拆）。

| 参数 | 当前值（`E:\Harbor\data\config.json`） | 作用 | 影响范围 | 改它的风险 |
| --- | --- | --- | --- | --- |
| `assistant.maxTokens` | **0**（默认也是 0；`config-normalize` 会把 4096 归一成 0） | ① **输出上限**：>0 时作为 `body.max_tokens` 发出去（`llm-body.cjs` 的 `resolveMaxTokens`）；0 = **不发这个参数**（= 不限）<br>② **上下文预算基准**：`loop-prompt.cjs` 把它传给 `context-builder.assemble()`，内部 `Math.max(2000, x \|\| 4096)` × 3 = 总字符预算 | 每一次对话请求的 body；每轮提示词的**全部**分层额度；渲染层的压缩提示线（`adviseCompact`） | 调大 = 同时给自己加一个输出上限（0 → 有上限），并且**所有层**（system/memory/project/task/tools）额度一起涨 → 每轮 prompt token 都变多（连短消息也涨）。**耦合，不干净** |
| `context.budget.conversation` | **30**（%） | 对话层（历史消息）能占多少字符：`floor(总字符 × 30%)` | 只影响对话层，**各层独立算**（`cap(name)` 各自算自己的，不互相挤） | 归一化时被 **clamp 到 0–90**（`config-normalize.cjs`）→ 单靠它最多到 90% = **11059 字符**，到不了 2 万 |
| `context.budget.{system,memory,project,task,tools}` | 10 / 5 / 15 / 10 / 20 | 同上，各层自己的额度 | 各层独立 | 调大 → 系统提示变长（每轮都涨） |
| `context.compactAt` / `autoCompactAt` | 0.4 / 0.6 | 压缩的提示线 / 自动线（**后端**口径） | —— | ⚠️ **当前没接线**：渲染层 `src/stores/thread/compact.ts` 把 0.4 / 0.6 写死成常量，不读这两个配置（既有不一致，记录不改） |
| `tools.fileScope` | `workspace`（默认） | 文件访问范围：工作目录内免授权；目录外要授权弹窗 | 附件要能被模型 `read_file`，**只能落在工作目录内** | —— |

推导（实测数字对得上）：`0 → 4096` × 3 = **12288 字符**总预算 → 对话层 `floor(12288 × 30%) = 3686` 字符。
这正是真机实测里「贴 96122 字符，模型只看到前 3646 字符」的由来（还有几十字符留给裁剪提示与格式开销）。

**它是不是 API 的 `max_tokens`？** 是（`llm-body.cjs:153`：`if (maxTokens > 0) body.max_tokens = maxTokens`）。
但**当前值是 0 = 不发**，所以「调大」的语义是「从『不设限』变成『设一个上限』」，不是「放开一堵墙」。
反向证据（仓库里已有的真机实测）：带 `max_tokens: 20000` 与不带，输出都超过 8192 —— 说明 8192 那堵墙是
**当时代码自己发的**，上游不卡这个数。任务里的停止条件「调大会让输出变长浪费 token」**不成立**
（调大反而给输出加了上限），但**「改它 = 顺手改输出行为」成立**。

**独立于 `maxTokens` 的硬上限（不跟着它变）**：

- `PROJECT_FLOOR`（`context-builder.cjs`）= `project.cjs MAX_CHARS` + `project-rules.cjs MAX_CHARS` + 1024 —— 项目层的**下限**（防止 AGENT.md 被百分比挤掉）；
- 每层 `cap(name) = Math.max(400, …)` —— 每层至少 400 字符；
- `trim()` 的截断说明固定吃掉 40 字符；
- 图片按 `IMAGE_COST = 800` 字符/张计预算（不按 base64 真长）；
- 渲染层输入框 `MAX_INPUT_LENGTH = 100000`（`src/constants/index.ts`）；
- 工具输出各自的头尾截断（`tools/_shared.cjs`）、网页正文截断（`browser-text.cjs`）、技能正文 `MAX_BODY`（`skill-pin.cjs`）。

**`shouldCompact()`（`core/compact.cjs`）当前没有调用方** —— 后端的自动压缩是**被动**的：只在收到上游
`context_overflow` 后压缩（`loop-model.cjs:110`）。渲染层的自动压缩则是主动的（见上面的 0.4/0.6 常量）。

**UI 入口**：`assistant.maxTokens` 有（设置 → 供应商面板「输出上限（0 = 不限…）」）；
**`context.budget.*` 没有 UI 入口**（只有任务级预算编辑器 `BudgetEditor`，那是另一回事）。

## 第二步：调预算（已做）

**改了哪一层**：只改**「0 / 没填」时的那个基准**，不碰用户的 `config.json`，也不碰 `budget.conversation`。

| 位置 | 改前 | 改后 | 说明 |
| --- | --- | --- | --- |
| `electron/core/context-builder.cjs` `DEFAULT_CONTEXT_TOKENS` | 4096（写死的兜底） | **16384** | `maxTokens` 为 0/没填时用它；**显式填了值一律照旧**（含任务级覆盖） |
| `src/constants/index.ts` `CONTEXT_BASE_TOKENS` | —— | **16384** | 渲染层压缩提示线用同一个数（`thread/compact.ts`）；`contextBaseDrift.test.ts` 读内核那边比一遍 |
| `src/stores/useThreadStore.ts` | 缺配置时按 4096 | 缺配置时按 0 | 让「0 = 不限」这条语义一路走到底，别在中途塞一个 4096 |

- 效果：总字符 `16384 × 3 = 49152` → 对话层 `floor(49152 × 30%) = **14745 字符**`（≈4.9k token）。一万多字符的粘贴能整条进上下文。
- **仍然是有限制的**：这一层的上限就是 14745 字符（不是把限制去掉）。
- **没动 `assistant.maxTokens` 本身**：用户值还是 0（= 输出不限，**不发** `max_tokens` 参数），所以「调大 = 顺手给输出加一个上限」这件事**没有发生**。
- 回滚：把 `DEFAULT_CONTEXT_TOKENS` 和 `CONTEXT_BASE_TOKENS` 改回 4096（两个文件两行）。
- 成本：一条 7000 字符粘贴的真机实测 prompt = **10578 token**（改前同样内容会被裁到 3686 字符、prompt ≈ 8468）。按 DeepSeek Flash 的输入价粗估，每轮多出的几千 token 是「用户主动贴了这么多内容」的直接后果，不是背景开销。
- 已知耦合（记录不改）：用户若显式填 `assistant.maxTokens`（如 20000），上下文基准会跟着变宽；`0` 这条新语义没这个问题。

## 第三步：长粘贴落文件（已做）

| 决策 | 取值 | 为什么 |
| --- | --- | --- |
| 阈值 | **8000 字符** | 对话层额度 14745 的**一半左右** —— 「开头 4000 + 指路行」一定塞得进，还留得出位置给别的消息；而且这个数用户能记住（比「额度减去已有消息」那种动态判据可解释） |
| 保留开头 | **4000 字符** | 够看清结构（标题、前几段、格式）；和阈值一起看：阈值 = 保留 + 4000 空间 |
| 文件位置 | `<工作目录>/.harbor/attachments/` | 模型对工作目录内文件**免授权** `read_file`；放 `data/` 里模型读不到（要读就得改文件范围权限或加工具 = 停止条件）。代价：工作目录里多一个隐藏目录 |
| 文件名 | `<会话id>-paste-<内容 sha1 前 8>.txt` | 幂等（同一条消息在后续每一轮都经过这里，第 2 次起只复用不重写）；会话 id 让用户一眼知道对应哪条对话；哈希防覆盖 |
| 大小上限 | 8 MB | 防呆：别让一次粘贴把磁盘写满 |
| 清理 | **不自动删**（跟工作目录走，用户自己管） | 后台偷偷删用户工作目录里的东西比留垃圾更糟；会话删除也不动附件（可能还有别的会话引用） |
| 界面提示 | 消息流里插一行系统提示：`长消息（20000 字符）已存为 <路径>。上面那条气泡仍是完整原文；发给模型的是开头 4000 字符 + 这个路径…` | 硬约束：所有自动处理必须看得见。**气泡本身的原文一个字不改**（用户贴的东西不许被悄悄替换） |
| 边界 | 带图（非字符串）不动 / 没有工作目录不落 / 写失败**不改消息**并且弹警告 / 超 8MB 不落并弹警告 | —— |
| 明确不做 | Map-Reduce（分段摘要汇总） | 落文件够用 |

## 途中踩到的三个坑（都改了，记下来）

1. **填充文本用随机字母** → 模型把它当密码去破译：回了 5 万字、还在工作目录里造了 12 个分析脚本（已清理）。改成一眼就是占位的普通句子，并在段首写「不要分析、不要写文件、不要调工具」。
2. **探针等待上限 80 秒，而那一轮跑了 91 秒** → 后续发送被排队、落到别的会话里（结果串台）。改成上限 150 秒 + 必须确认输入框已清空才发下一条。
3. **标记有规律可猜** → 换随机标记重跑，结论以随机标记那次为准。
