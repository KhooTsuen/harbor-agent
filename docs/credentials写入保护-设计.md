# credentials.cjs 写入保护 —— 下一阶段设计（**未实施，等批准**）

> **性质**：设计稿。回答「凭证文件损坏 / 解析失败 / 解密失败 / 读取权限错误时，怎么阻止
> 后续任意一次普通 `set()` 把原凭证静默覆盖掉」。**本文不改任何代码。**
>
> 背景与实测见 [`E2用户数据保护-故障注入与修复设计.md`](E2用户数据保护-故障注入与修复设计.md) §二。
> 基线：`HEAD = 9301ec8`（+ 本轮 task-io 修复）。
> 证据规矩同其它文档：每条结论指得住 `文件:行号` 或一次注入观察。

---

## 0. 一句话

现在 `credentials.load()` 用**一个 catch 吞掉所有失败**（`credentials.cjs:60-77`），把
「文件不存在」和「文件坏了」**变成同一件事**（都退化成空 `entries`）。于是下一次任何
`set()` 都会把空表 `persist()` 写回去 —— 用户的 API Key 无声无息消失，且**没有任何提示**。

**要做的不是「加个 .corrupt 副本」，是「让凭证库在状态不明时拒绝写」。**

> ⚠️ 明确边界（用户已定）：**仅增加 `.corrupt` 副本不足以证明凭证安全问题解决。**
> 留档只保住证据，**不等于**阻止覆盖。核心是「损坏 → 后续写被拒」。

---

## 1. 现状与证据

| 位置 | 现状 | 后果 |
| --- | --- | --- |
| `credentials.cjs:60-77` `load()` | 读 + `JSON.parse` 同一个 `try`，失败一律 → 空 `entries` | **区分不出**「全新」与「损坏」；`backend` 还会被按当前环境重定 |
| `credentials.cjs:79-83` `persist()` | `fs.writeFileSync(filePath(), …)` 裸写 | 写到一半失败 → 凭证文件截断，**所有凭证一起丢** |
| `credentials.cjs:92-105` `decrypt()` | 解密失败**抛错**（这条是对的） | 但 `load()` 读文件那层仍把坏文件当空 |

**实测（2026-10-13，隔离目录 + 虚构凭证，见 E2 报告 §二）**：

```
损坏前凭证: provider:alpha, provider:beta
（把文件改成非法 JSON）
损坏后 load() 读到: []            ← 静默退化成空
一次无关 set() 后，文件里的 ref: provider:gamma
旧凭证是否被覆盖: 是              ← alpha/beta 从磁盘消失
是否有 .corrupt 留存: 无
```

即：**一次损坏 + 一次无关的设置改动 = 用户所有凭证被抹掉、无提示、无证据。**

## 2. 设计目标（按优先级）

1. **不丢**：状态不明时**拒绝写**，原文件一个字节都不动。
2. **不谎报**：`set()` 不能返回 `ok:true` 而实际没保住（现状就是这么假的）。
3. **可诊断**：损坏留证据（`.corrupt-<时间戳>`），并有一条明确错误。
4. **可恢复**：用户能明确地「重新填一次 Key」或「确认重置凭证库」来脱离只读态。
5. **不误伤**：**首次启动没有该文件**是正常的，不能因此进只读态。

---

## 3. 状态模型（一处定义）

`load()` 返回缓存 + 一个**明确的健康态**（进程内，不落盘）：

| 状态 | 触发 | 允许写？ |
| --- | --- | --- |
| `ok` | 读到并解析成功 | ✅ |
| `missing` | `ENOENT`（从未建过 / 被显式删） | ✅（等同于全新） |
| `corrupt` | 读到了、但 `JSON.parse` 失败 | ❌ 只读，直到用户显式处理 |
| `unreadable` | 读失败且**不是** ENOENT（EPERM / EACCES / EISDIR…） | ❌ 只读（可能只是临时占用，但绝不覆盖） |
| `undecryptable` | 文件能解析，但某条 `decrypt()` 抛错（换了 Windows 账户 / 换机器） | ❌ **写该条目**（其它条目的改动也不落盘，避免整篇重写时把解不开的条目丢掉） |

> **关键区分**：`missing` 必须与 `corrupt` / `unreadable` 分开——「没建过」是**正常**的
> （首次启动，用户还没填 Key），绝不能因为读不到就进只读、更不能因为读不到就覆盖。

---

## 4. 行为设计

### 4.1 `load()`：先判存在，再判能不能解

```
读文件：
  ENOENT            → { entries: {}, health: 'missing' }        // 不报错、不留档
  其它读错误         → 保留原文件；health = 'unreadable'；log.error + 留档(尽力)
  读到但 parse 失败  → 保留原文件；health = 'corrupt'；keepCorruptCopy + log.error
  读到且 parse 成功  → health = 'ok'；entries 照旧（解密在用时做，失败的条目单独标记）
```

- **不再**在 `load()` 顶层 `catch{}` 里把 `backend` 重定 —— 只在 `missing` 时才按当前
  环境能力定 `backend`（现在这条逻辑是对的，要保留到「文件不存在」分支里）。
- `corrupt` / `unreadable` 时**不覆盖原文件、不 rename、不留 `.tmp`**。

### 4.2 `set()` / `remove()`：健康态不对就**拒绝**，并给出可操作的错误

- `health === 'ok' | 'missing'` → 正常：改内存 → `persist()` 走 `writeAtomic`。
- `health === 'corrupt' | 'unreadable' | 'undecryptable'` → **直接返回**
  `{ ok: false, error: '凭证库当前不可写：<原因>。请到「设置 → 模型」重新填一次 API Key，或确认重置凭证库。' }`，
  **不 persist、不动磁盘**。
- `set()` 的返回值原来就带 `ok`（见 `credentials.cjs`），这里让 `ok:false` 真正意味着「没写」。

### 4.3 显式恢复（唯一的出口，防止「只读死锁」）

- **重新填 Key**：`set(ref, value)` 在 `corrupt` 态下**默认被拒**；UI 上「重新填一次」
  走一个**显式**的 `reset()`（或 `set(ref, value, { force: true })`）—— 语义是「用户确认
  放弃旧文件、重建凭证库」，此时才允许覆盖（同样先 `keepCorruptCopy` 留旧文件）。
- **确认重置**：`reset()` 清空并重建 —— 必须由用户显式触发（UI 二次确认），不能是副作用。
- 恢复成功后 `health → ok`，并清掉留档标记。

> 这样「损坏」不会永久锁死：用户始终有一条明路；但**默认路径绝不覆盖**。

### 4.4 写入：`persist()` 改走 `writeAtomic`（reuse，不新增实现）

- 和 task-io 一样，**复用** `safe-write.writeAtomic`（内核唯一文本原子写；有自检 `118-safe-write`
  钉「只允许一个实现」）。
- 写失败**抛出**（`writeAtomic` 本来就会抛）——`set()` 捕获后返回 `ok:false`，**不假报成功**。

## 5. 逐项对照（用户要求回答的点）

| 要求 | 设计 |
| --- | --- |
| 故障触发条件 | 文件被外部改坏 / 磁盘写满 / 断电截断 / 换 Windows 账户致 DPAPI 解不开 / 文件被别的进程占用或权限拒绝 |
| 现有备份、恢复、容错 | **备份不含凭证库**（`backup-scan.cjs:20-27` 只备 config/memory/sessions/skills）；现有容错 = 退化成空（**这是 bug**） |
| 是否需要原子写 | **需要**（`persist` 现在是裸写，截断即全丢） |
| 写失败后是否覆盖旧数据 | **现状：会**（空表写回）。**设计后：不会**（状态不对直接拒写，磁盘一字不动） |
| 如何保留损坏证据 | `keepCorruptCopy(filePath())` → `.corrupt-<时间戳>`，**原件不删不覆盖**；去重同 task-io |
| Windows 文件替换行为 | `writeAtomic` 用「临时文件 + `renameSync`」，撞 EPERM/EBUSY 退避重试（`safe-write.cjs:43-53`）；凭证文件同理 |
| 对既有格式 / 迁移的影响 | **零**：文件格式不变（仍是 `{version,backend,entries}`）；只加进程内 `health` 态，不落盘、不需要迁移 |
| 最小测试 | 注入：①坏 JSON ②EPERM ③ENOTDIR；断言 `set()` 返回 `ok:false` 且**原文件字节不变**；④ENOENT（首次）仍可写；⑤`reset()` 后恢复可写 |
| 回滚 | 单文件改动（`credentials.cjs`）+ 测试；回滚 = 还原该文件，无数据迁移 |
| 验收标准 | 损坏态下任意 `set()` 不导致原文件字节变化；留档恰好一份；首次（无文件）仍能正常保存 |

## 7. 明确不做（本设计边界）

- 不改凭证**文件格式**（不需要迁移）。
- 不改 `decrypt()` 的报错口径（它已经是抛错、够清楚）。
- 不给凭证库加进**备份范围**（那是另一项独立决定，见 E2 报告「备份不含关键三样」）。
- 不新增「凭证损坏」UI 状态/角标。
- 不碰 `config.cjs` 的 `.broken` 逻辑（它已经比凭证这边更完善，是参照物，不是改动对象）。

## 8. 与 task-io 那一项的关系

两项**同型**：都是「写用户数据用裸写 + 读失败静默当空」。task-io 先做（已批准、已实施），
它立了模板：**状态分清 → 状态不对拒写 → 留档不删原件 → 原子写 → 负向测试**。
credentials 照同一模板做，但**多一层**：它还有「解密失败」这个凭证特有的第三态，
以及「必须给用户一条显式恢复出口」的要求。
