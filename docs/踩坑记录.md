| 坑 | 症状 | 教训 |

| **模块名被同名参数遮住** | `config.hasKey is not a function` —— 发消息直接失败 | 函数形参叫 `config` 会把 config **模块**遮住。内核里模块要另起名（如 `configCore`）。`tsc` 查不到（`.cjs` 不过类型检查） |
| **Python heredoc 里 `\n` 会变成真换行** | 改完 JS/TS 报 `Invalid or unexpected token` | 写文件内容时别用 `\\n`，用 `chr(92)` 拼，或改完立刻 `node --check` / `tsc --noEmit` 验一遍 |
| **grep 品牌名要大小写不敏感** | 以为清干净了，用户截图里还有「Codex」 | `grep codex` 匹配不到 `Codex`。清理品牌一律 `grep -i` |
| **残留检查会变成挡路的门** | 单人对话发不出消息，弹「找不到项目」 | 一个变量取出来检查完就再没用过 → 说明那个条件已经失效。重构时要问「这个检查现在还代表真实约束吗」 |
| **按行切片重构容易切多** | 一次 `python` 替换把相邻的 5 个函数一起搬走了 | 切之前先看首尾锚点之间**有什么**，切完立刻跑 typecheck |
| **React state 同帧不更新** | 键盘连按箭头只挪一步 | 连续输入的场景要用 ref 累加当前值，别读 state/props |

| **`Partial<Store>` 当返回值** | store 合起来报「类型不可赋值」 | 返回 `Partial<AppState>` 会让动作变成可选，和必选声明对不上。用 `Pick<AppState, '分支动作名...'>` |
| **gitignore 写 `/* */` 注释** | 差点把根目录所有文件都忽略掉 | `.gitignore` 只认 `#` 注释；`/*` 是一条**模式**（匹配根目录下所有东西） |
| **真机探针跑在启动动画上** | 探针返回全是 `false`，DOM 里 `buttonCount: 0`，正文只有 `HARBOR / LOCAL AGENT SIGNAL` | `BootSequence` 覆盖整屏（`fixed inset-0 z-[90]`）且要 **~8 秒**才让出界面，而真机工具 2500ms 就执行脚本。**探针要先轮询等 `.harbor-boot` 消失**，别点一下就往下走（点它只记一条 click，动画照样要走完）。判断「是不是卡住了」看 `data/logs/actions-<日期>.jsonl` —— 那里面能看见渲染层每一步 IPC |
| **中文后面不能写 `\b`** | `^(设置)\b` 这条正则**永远不匹配**，设置按钮就在眼前却点不到 | JS 的 `\b` 按 `\w`=`[A-Za-z0-9_]` 算，中文字符不是 word char，所以中文后面的 `\b` 两端都是「非词」→ 没有边界。**匹配中文用精确选择器或 `^…$`，别用 `\b`** |

| **CI 红了 15 次（前 13 次没人发现）** | GitHub Actions 从 v1.11.0 起一路红叉，本地 `npm run verify` 却全绿 | 本地验证链和 CI **不是一套**：CI 多一步 `prettier --check`（一开就报出 23 个文件格式不符）。两边的清单必须逐项对齐 —— 已把 `check:format` 接进 `verify`。**「本地绿」只说明本地绿** |

| **测试里两条任务落在同一毫秒** | 同一个提交 CI 时红时绿（#56 绿、#57 红）：自检的 `报告里指出「之前跑过一次」` 失败 | `findPrior` 只认**严格更早**的 createdAt —— 同毫秒创建的两条互不算「之前」。真实使用不会踩（两次跑至少隔几秒），但**测试得自己隔开时间**（`await sleep(5)`），别赌机器速度。本地复现：`--freeze` 把 Date.now 冻住，报告尾和 CI 一模一样 |
| **上游的流会「挂住」** | 真机验收 24 次里 3 次整轮对话永远停在「运行中」：请求发出去了、一个字节都不回来，也不报错（连"停止"都靠外部 180 秒判超时才收场） | 流式请求需要一个**空闲看门狗**：两个数据块之间超时（现定 45 秒）就主动放弃、报成可重试的 `timeout`，交给既有重试/降级链路（见 `electron/core/llm-idle.cjs`）。`http.cjs` 有意不设**总**超时（正常流可以跑几分钟）—— 看门狗管的是「卡住」，不是「慢」。自检 `79-llm-stream` 用「吐一块就挂住」的假流钉住它 |
| **`cn()` 会把自定义字号类当颜色吞掉** | `Row` 标签写着 `text-dense`，真机量出来是 **15px 继承值** ——”写了字号却不生效“，样式看着像随机生效 | tailwind-merge 不认识 `tailwind.config.js` 里的自定义字号名（meta / body / title / dense），把 `text-dense` 归成**颜色类**，后面跟 `text-fg-primary` 时被覆盖。**自定义 scale 要注册进 twMerge 的 classGroups**（见 `src/lib/utils.ts`），并加单测钉住 |
| **设置页容器层不带 gap，卡片会贴死** | 数据与用量页四张删除卡间距 **0px**（肉眼像一整块）、扩展页技能卡 0~1px，而「通用」页好好的 8px | 这几页的 tab 组件包了 `<div className="py-1">`（无 gap），把 `.settings-body` 的 8px 弹性节奏切成普通块流；返回 Fragment 的页没这个问题。**设置页的容器层要么返回 Fragment，要么自带 `gap-2`**。探针 `tmp/parse-metrics.cjs` 能直接列出相邻卡片的间隙 |
| **重读会话会换掉消息 id** | 「切走再切回来它又自己生成」；真机日志里点一次「上一版」就紧跟一个 `chat:send`（连点四次 = 四次） | `openFromDisk` 重读后每条消息都是**新 uid**（`storedToUi` 里 `uid('msg')`）——拿重读前的 id 查必然失败，失败又被当成「这一版没回答过」而自动重跑。**跨重读的引用一律按签名找回**（内容 + 版本表，timestamp 消歧）；写盘要写回**磁盘 key**（`Message.diskKey`），写新 uid 会在文件里多一条同名提问副本（真机探针逮到的）。jsdom 里 `loadSession` 返回 null → 不重载 → id 恰好没变，**单测照不到**：要 mock「重载且换 id」的形状 + 真机对照（老构建复现 `chat:send`、新构建同操作安静） |
| **初始化期取循环导入的绑定 → TDZ** | 只有「直接 `import` 某个子模块」的测试报 `Cannot access '__vite_ssr_import_6__' before initialization`，其他测试/构建/CI 全绿 | `useThreadStore ↔ turns` 本来就是循环；新加的 `regenerate` 让 `messageVersions` 在 **create(...) 执行路径上**碰了还没初始化的导出，导入顺序换个入口就炸。**循环图里的模块，导出只在调用期取**（别在模块初始化期调用/展开）；另外**留一个直接 import 子模块的测试口子**，不然这种问题只会在某一条入口上偶发 |
| **动作流里同一次 IPC 记两行** | 查「到底跑了几轮」时被行数误导：一次 `chat:send` 在 `actions-*.jsonl` 里是**两行**（preload 的 `call()` 记一行 + `register-handlers` 的 ipcMain 包装记一行），ms 也各测各的） | 计数历史事件时别数行数 —— **同 name、ts 相邻（<数十 ms）的两行就是一次调用**；判「是不是多跑了」看渲染层点击次数与成对行数。真实例：beta.4 一次版本切换的「chat:send ×2」其实是**一次**发送（bug 依然成立，但「×2」的口径错了） |
| **任务台账没按会话过滤** | 在对话 A 里跑任务、中途手动中断，新建对话 B —— B 会「接着把 A 的活干完」，仿佛任务状态是全局共享的 | `task-context.cjs` 的 `buildTaskState` 之前把**全局**未完成任务（本会话的 + 别人会话的）拼在一起注入，还附「接着计划里第一条没有 [x] 的往下做」——B 的第一轮请求里就躺着 A 的目标/计划/脚印。**任务上下文的每一处（注入/恢复/检查点/启动扫描/门禁）都必须按 `sessionId` 过滤**；「兜底注入别人的任务」是最像贴心设计的那种 bug（自检 82 组当场就红了）。真机验证用「paused 任务在盘上 → 新建对话」：`chat:send=0` 且任务文件逐字节不变。另有口径坑：**恢复入口**要按聊天列（`main`）统计 —— 右栏任务中心是显式全局管理器（AG-012），那里列出所有任务的「继续」不算泄漏；启动清单提示是 bootstrap 异步弹的，探针要 `await ~2.5s` 再抓（800ms 抓不到，会误报「没提示」） |
| **把「能力声明」当成「用户预算」发出去** | 「输出不限」之后长回复照样断，而且每次**正好卡在 8192** token（403 条请求里输出最大值就是 8192），用户连着 5 次看到「说到一半没了」，只能问「你怎么中断了？」 | `llm-body.cjs` 在「不限」（0）时**不是不发**，而是补上了 `provider-capabilities` 里那个 `max_output`（deepseek 系 = 8192）—— 于是每次请求都带 `max_tokens: 8192`。**能力表是「这家模型大概能写多少」的声明，不是该发给上游的上限**；拿它当上限发，等于自己砌一堵墙还怪上游。真机实测（同一条「写 1500 行」请求）：带 `20000` → out=**9341**、不带 → out=**8033**，两个都超过 8192 → 墙是自己砌的（旧注释「不发会退到 4096」也是错的）。**「不限」就是不**发这个参数。附带教训：`llm.cjs` 把 `finish_reason` 读出来返给上层，**全库没有一处消费它** —— 截断了也没人告诉用户；改这类「上限」时，必须同时检查「撞到上限时用户知不知道」 |
| **回答的版本标签被「重贴」** | 一条提问先答 A（重新生成 5 次），编辑成 B 后 B 的切换器显示 1/8、1/9（把 A 的 6 条也数进来），切回 A 又一条都不剩 | 编辑/重新生成时，旧回答交给新一轮（seedAnswers）前会被重贴 `answersVersion` —— 已标过的一律**只补缺、不重贴**（标签是它生成时就定下的）。同族还有两个坑：`allAnswers` 里「自己」跟着 `message.content` 漂（切走会把它盖成上一条的内容 —— 切走前要先把原文定格进台账）；`toAnswerRecord` 的 key 要用**磁盘 key**（重读会给消息换新 uid，用 uid 和台账里的自己对不上 → 重开后每个答案多一条 N+1）。真机对照：同一夹具旧构建 1/4、6/7，新构建 1/3、6/6（探针 `tmp/iso7-run.cjs`） |
| **「消息树 / parentId / activeLeafId」不是这套数据的形状** | 需求按「树形结构」描述（每条消息有 id 和 parentId、activeLeafId 记叶子）；照着去找/造这些字段会全部对不上 —— 这套代码里根本没有 | Harbor 的分叉对应物：**提问多版本** = 同一条用户消息的 `versions[]`/`versionIndex`；**回答多版本** = `answerRecords`/`answersVersion`/`answerIndex`；**后续链跟着当时那一版走** = 记录上的 `parentKey`/`parentVersion`（内核筛）。「激活路径」本来就持久化在这些字段里（每个提问记 versionIndex、每个位置记 answerIndexByVersion）—— **零迁移**。另一个边界：**内核只读激活路径**（非激活版本的后续轮次不在内存里）—— 所以「分支树」v1 只画当前路径上的分叉点 + 各分叉的兄弟分支，画全树要改读取口径（beta.9 已按此实现） |

### 图片被当文本切了：模型说「看不见图」，而我们以为它在不听话（2026-09-28）

用户报的是「DeepSeek flash 现已支持多模态，但它依然说没办法看图」。
第一反应很容易落在**能力声明**上（`provider-presets.cjs` 里 `deepseek-flash` 命中
宽规则 `/^deepseek/` → `vision:false`，贴图就弹「会失败」）—— 那确实是**另一半**原因，
但**真正让它瞎的是内核**：

`electron/core/context-builder.cjs` 的预算裁剪对每条消息做
`JSON.stringify(content)` 再 `slice(0, limit - 40)`。带图消息的 `content` 是
**多模态数组**，于是：

```
[{type:'text'},{type:'image_url',image_url:{url:'data:image/png;base64,iVBOR…20 万字符…'}}]
        ↓ JSON.stringify + slice(3646)
"data:image/png;base64,iVBOR…\n[…上下文已按预算裁剪…]"
```

模型收到的是一张**只有文件头的坏图**，于是它老老实实回答「我拿不到这张图」——
**它没撒谎，也没不听话**。判据不是我猜的，是它**自己的推理原文**（会话文件里就写着
`the image data is truncated ("[…上下文已按预算裁剪…]")`）。

同一条链路上还查出**第二个**断点：`images` 落盘时根本没写
（`useThreadStore.ts` 只写 `content: '（图片）'`），读回时也不认
（`stores/app/disk.ts` 的 `storedToUi` 没这个字段）—— 也就是说重开会话后，
**图在磁盘上压根不存在**，缩略图和「恢复任务」都拿不回来。一条 grep 就能证实：
会话文件里搜 `data:image` **零命中**。

**为什么能一路溜到真机：**

- `context-builder.cjs` 在 `scripts/selftest/env.mjs` 里被 `require` 了，
  却**一条断言都没有**（那个变量只在导出列表里躺着）—— 检查了 27xx 项，唯独漏它。
- 渲染层 `buildHistory` 那条「带图消息要换多模态格式」的规则写在注释里，**没有测试**；
  `storedToUi` 的测试也只覆盖到 interrupt/resume 那几个字段。
- 单测全绿、`tsc` 全绿、`npm test` 全绿 —— 而且**每一层看着都挺对**：
  裁剪逻辑对纯文本是正确的，多模态那一支从来没人走。

**规则三条：**

- 凡是「按字符切」的代码，遇到**非字符串 content**（多模态数组 / 附件）必须
  **只切文本、整块留图片**；图片**不要按 base64 真长算预算**（27 万字符 vs 一千 token，
  按真长算一张图就挤没整个对话），给个固定成本。
- 加一个会走网络/落盘的字段（这里是 `images`）时，**顺着三条链路各看一遍**：
  写（落盘）、读（重新打开）、发（请求体）。这次是「写了没存 + 存了没读」。
  一条 `grep data:image <session>.jsonl` 就能验，比读代码快。
- 用户说「整个软件里都会有类似情况」时，按**数据流**查（这张图从附件 → store →
  落盘 → 历史 → 请求体要过 5 个文件），**不要按关键词搜文件** —— 这类 bug 的症状
  在界面上（"它说看不见"），原因在离它很远的装配层。

### 「入口洗一次」不够 —— 数据会从**历史**里回来（同日，同一件事）

第一版把图片归整挂在「贴进来那一刻」。但发给模型的**不只是这条新消息**：
历史里的图会跟着每一条新消息一起发出去。用户那条会话里有一张旧巨图（上一个构建写进去的），
于是**之后每条消息都失败** —— 而我的单测、真机探针、甚至「贴一张 BMP 试试」全都是绿的，
因为那些路径都不经过历史。

**规则：凡是「发出去的东西」，在**真正发出去之前**再洗一遍（最后一米），别只在入口洗。**
入口洗是为了体验（贴进来就能看到缩略图、早点报错）；发送前洗是为了正确性。
发送前这一道还要注意两件事：
  · **带缓存**（同一张别反复解码，几 MB 的图解码一次很贵）；
  · **失败要中止并说清楚**，不能静默把图丢掉 —— 否则模型会回一句「我没收到图片」，
    用户又得从头猜一遍（这次的起点就是「它说看不见图」）。

**还有一个只写测试才发现的真 bug**：既然让解码器**边解边缩**（一亿像素整张读进内存会爆），
那缩过之后**必须重新编码** —— 我一开始写成了「解出来一看尺寸合规就透传原字节」，
等于**缩放完全没生效**（`{resizeWidth}` 白传了）。测试里那条断言（「缩过必须重编码」）
就是干这个用的：不写它，这个 bug 在真机上只表现为「还是被拒」。
### 配置项「写了」不等于「生效」—— 要顺着「写入 → 发送 → 内核读取」三段各查一遍（2026-09-28）

用户报：「新建对话选择 gpt 模型但还是使用的 Deepseek flash 模型」。

1. `src/stores/thread/turns.ts` 组装 payload 时**没带** `model`（选择的结果从没离开渲染层）；
2. `electron/handlers/chat.cjs` 也**从不读** `payload.model`，一路用全局默认。

### 修完这个 bug 的那个改动，**自己**又被真机逮了一次（同日，同一件事）

把「按会话级模型挑供应商」接到 `chat.cjs` 时，我把

```js
const provider = config.activeProvider()      // config 是**模块**
```

顺手改成了

```js
const provider = effective.activeProvider()   // effective 是**配置对象**
```

`activeProvider` 只活在 `core/config.cjs` **模块**上；`config.get()` 返回的配置对象里**没有**这个字段。
结果：真机一发消息就 `Error invoking remote method 'chat:send': TypeError: … is not a function`
（消息根本发不出去），而 **tsc 全绿、lint 全绿、2776 项内核自检全绿** ——
没有任何一组跑过 `chat:send` 这条路。

**三条规矩**：
1. **自检绿 ≠ 这条路跑过。** 内核自检大多直接调 `loop.run` / 调 core，
   而 `handlers/`（真正被 IPC 打进来的那层）几乎没人跑 —— 改 handler 必须真机跑一遍。
2. **别靠「记住」防这种错，靠通用钉子。** 现在自检里是全仓扫
   `X.activeProvider()`，X 只准是模块别名（`config` / `configCore`）—— 同类写法以后当场红。
   （写钉子时注意：**注释里也会被扫到** —— 我第一版把「错误写法」写进注释里，钉子立刻就红了。）
3. **探针自己也会骗人。** 同一轮里探针报「界面上没有报错」是绿的，可界面明明写着
   `Error invoking remote method 'chat:send': TypeError` —— 它的错误正则里没有这一句
   （Electron 会把主进程抛的错包一层）。**断言「没有错」时，口径要写全**；
   更稳的做法是**等物证**（日志行 + 统计数字），别等界面上的文字 ——
   流式占位（「正在分析任务」）会让「有文字就算回完了」立刻成立，于是探针在请求还没发完时就收工了。

### 「看似可用但实际无法正常使用」= 界面显示的是**配置**，不是**行为**（同日）

同一轮里用户还说用量闸「现在还是那种：看似可用但实际无法正常使用的状态」。
内核判定一直是对的（自检组 08 全绿），界面却只显示**配置的样子**：
`enabled: true` + 两个上限都是 `0` 时，看到的是「勾上了、框空着」—— 像在保护，
实际一个请求都不拦（`0 = 不限` 是我们自己的设计，用户不可能记住）。

**规则：状态类界面要显示「它现在在做什么」，而不是「它是怎么配的」。**
1. 判定只在内核做一份（`gateState()`），界面**不许**拿配置和统计再算一遍
   —— 这个项目已经因为「日期函数写了两份」让闸门永远算成 0 过一次；
2. 「开着但等于不限」必须是**显式字段**（`idle`）而不是让界面去推；
3. 改完配置要**重新拉**一次状态，否则数字旁边挂的还是旧结论（「看着是新的、其实是旧的」的同类）。

### 「失焦才保存」是个陷阱：面板可能是**隐藏**而不是卸载（同日，同一处界面）

治上一件事的时候顺手治出一个老毛病：那个输入框一直是「失焦才写回配置」
（`onBlur → patchLimits`）。真机走查里试了「填完上限**不失焦**，直接点 X 关掉设置」——
值没保住。原因是**设置面板关闭时是隐藏、不是卸载**，blur 不一定会来（就算是真卸载，
Chrome 也不会为被移除的聚焦元素补一个 blur）。

第一版修法我写的是「卸载时补交一次」—— **再跑真机还是没保住**（因为压根没卸载）。
最后改成**不依赖焦点**：改一下就排一次防抖提交（700ms），失焦 / 关面板只是提前触发；
「关面板时把没到点的草稿补交」也留着当兜底。

**规则：凡是「用户改了要保存」的输入框，别把保存拴在 blur 上。**
· 防抖提交是默认选择，交互上也更符合直觉（改完就是改了）；
· 也别猜「什么时候会卸载」—— 拿真机试一次比读代码快。

### 几段「各自超时」加起来比调用方的耐心还长（2026-09-28，AI 读网页读不到）

用户报：「AI 打开浏览器时网页不显示内容、AI 读不到，**我点一下它才能读**」。
日志里是这句：`工具 browse 失败：界面没有在 45 秒内回应（浏览器标签可能被关了）`。

真因不在「标签被关了」，在**算术**：渲染层为了等页面就绪分了三段等待
（等元素 12s + 等 dom-ready 15s + 等加载 20s），再加上给 SPA 的 1.2s ≈ **48 秒**；
而主进程那句「等界面 45 秒」是**另一条**独立的计时器。48 > 45，于是慢页面
**必然**先被主进程判超时 —— 而界面其实正在干活。用户手动点一下，各段等待立刻满足，
于是现象看起来是「点一下就能读了」。

**规则：跨进程/跨层的等待，必须有一条**总预算**，并且**里面那一层要小于外面那一层**。**
· 每一段等待都从同一条预算里切（`browseWait.ts` 的 `Budget.slice`），
  超时的**原因由最清楚的那一层回话**（「等页面就绪超时（已等 30 秒）」），
  别让外面的调用方用一个猜出来的原因替它发言 —— 那句话会把排查带偏（这次就偏了半天）。
· 这条不等式要**自动钉住**：自检组 88 把两个文件里的数字都读出来比大小，
  谁把预算调过头都当场红。

顺带两个真机上逮到的：`GUEST_VIEW_MANAGER_CALL: Script failed to execute`
（webview 的 guest 还没就绪，`executeJavaScript` 会抛）—— 要等 `dom-ready` 重试；
以及**空正文不等于「没有正文」**（SPA 加载完才填内容），空就再读几次。

**探针又骗了我一次（同一天，第二次）**：第一版探针用
`/(Example Domain|example\.com)/i` 判「读到了」—— 结果流式中间那一帧
`正在打开 {"url":"https://example.com"}` 就把它配上了，于是它**在工具还没跑完时就收工**，
报「全部通过」。改法：等正文**连续两次不再变化**且不含「正在…」；判据只认页面里的字样
（`Example Domain`），不认 URL。**「等一个稳定态」比「匹配一个字符串」可靠得多。**
另外，塞进页面执行的脚本要小心**模板字符串的转义**：`[^\n]` 会被插成真换行，
页面里的正则当场 `Invalid regular expression: missing /`。

## 风险分级：三个「模式表看着挺像样」的假象

2026-09-23 例行排查时随手写了个 21 条命令的探针，**14 条判错**。三个根因都不是
「黑名单少写了几条」——那种补不完，`risk.cjs` 开头自己就写着这句话。

**① 只审命令开头 = 后面跟什么都能过。**
`LOW` 白名单全是 `^\s*(ls|dir|find|grep|…)`，只匹配**开头**。
`find . -delete` 开头是 `find` → 整条判成 **low** → 在「中风险放行」的配置下
**静默递归删除**。21 条里最吓人的就是这条。
**规则：白名单的语义必须是「整条都像只读」，不是「开头像只读」。**

**② 一张模式表只覆盖一种 shell 方言。**
表里全是 cmd / unix 写法，于是 `format c:` 拦得住、**`Format-Volume` 拦不住**；
`shutdown /s` 拦得住、`Stop-Computer -Force` 拦不住（原正则要求参数带**斜杠**，
PowerShell 用的是 `-Force`）；`schtasks /create` 有、`/delete` 没有。
账户那几条更是**完全没有** —— 而 `net localgroup administrators x /add` 等于拿下整台机器。
**规则：写"危险命令"这类表时，先把同一个动作在 cmd / PowerShell / unix 里的写法各列一遍。**

**③ 兜底写在调用方，自己反而不说 → UI 会说谎。**
`decide()` 在 `high: 'allow'` 时返回 `allow`，真实确认全靠 `tools/index.cjs` 里
一条 `|| verdict.level === 'high'` 顶着。于是设置页的风险试算显示「**直接执行**」，
实际执行却弹确认框 —— 同一个判断，两个地方说法不一样。
**规则：一条规则要写在"拥有这条规则"的那个函数里，别让调用方替你兜。**
（顺带：这条也解释了一个 UI 文案 bug —— critical 显示成「危险**风险**」，
因为标签表给的是「危险」、调用处又字面拼了个「风险」。同一个道理：拼接发生在错的地方。）

**④ 把新逻辑提到更高等级，要连「别误伤」一起验。**
`grep -r`、`ls -f`、`find -name` 和破坏性开关长得很像。把 `-r` / `-f` 收进
「破坏性参数」表，就会误报一堆正常命令 —— 而**误报的代价是这个分级被用户整个关掉**，
那比不修还糟（人不会去改一个天天拦自己的东西，只会关掉）。
所以自检里「**没治过头**」和「治住了」是同等重要的验收项：
`npm install` 仍是中风险·直接执行、`grep -r` 仍是低风险·直接执行，都写进断言。

## 递归删盘根：曾经漏过的 28 条（2026-10-03）

接上面那节的后续。A2 收尾时要写一条自检「关掉规模层不能连带把危险度也关掉」，
随手挑了个写法 —— `Remove-Item -Recurse C:\ -Force` —— 结果它**不是 critical，是 high**。
顺着写了个 46 条的探针（`tmp/risk-probe.cjs`），**28 条漏判、0 条误判**。

**为什么漏：判据钉在了「参数顺序」上，不是钉在「目标」上。**
`risk-patterns.cjs` 那两条 PowerShell 正则要求盘根**恰好在最后一个参数**：

| 写法 | 当时判 |
|---|---|
| `Remove-Item -Recurse -Force C:\` | critical（盘根在末尾 ✓） |
| `Remove-Item -Path C:\ -Recurse -Force` | critical（`-Path` 那条专门管） |
| `Remove-Item -Recurse C:\ -Force`（夹在中间） | **high** |
| `Remove-Item "C:\" -Recurse -Force`（带引号） | **high** |
| `rm -rf /` ← 注释里一直拿它当参照 | **high** |

两件事比数字更值得记：

1. **注释在说谎。** 旧注释写着「目标盘根和 `rm -rf /` 是同一件事 —— 没有正当场景，
   直接 critical」，而 `rm -rf /` 自己**一条规则都没匹配上**。
   「注释里当参照的那条」要当场验一遍 —— 它往往是最容易漏的那个。
2. **掉一级的代价不是「多问一句」。** critical 是「不问直接拒」，high 是「问一下」；
   而用户选了「完全访问」那一档时 high 是**不问**的 —— 也就是同一件灾难只剩一次点击。

**现在怎么判**（`core/risk-targets.cjs`，自检组 `61-destructive`）：
先**归一化**（去引号、斜杠统一、转小写）再判**目标** —— 位置 / 引号 / 额外开关都无关。
动作认四种（`rm -r` / `del /s` / `rd /s` / `Remove-Item -Recurse`），
目标认四类（盘根 / 系统目录含子树 / 家目录本身及其一级标准目录 / 所有用户的父目录），
间接写法认三种（`find -delete` 看搜索起点、`xargs rm` 看管道左边、脚本里写死的字面量）。
**相对路径、再深一层、不在同一段里的目标一件都不算** —— 反向锁 17 条（`MUST_NOT_CRITICAL`）。

**曾经漏过的 28 条**（当时判 high，现在 critical）：

```text
rm -rf /                          rm -rf C:\                        rm -rf / --no-preserve-root
rm -rf "/"                        rm -rf C: -Confirm:$false          rm -rf C:\Windows
rm -rf $env:USERPROFILE           rm -rf ~                           rm -rf /*
rm -rf /usr                       rm -rf /usr/*                      rm -rf /home
rm -rf C:/                        rm -rf C:\\                        rm -rf %USERPROFILE%
del /s /q C:\                     del /s /q C:\Windows\System32\*.*
rmdir /s /q C:\                  rd /s /q C:\Windows
Remove-Item -Recurse C:\ -Force  Remove-Item C:\ -Recurse -Force
Remove-Item "C:\" -Recurse -Force  Remove-Item -Confirm:$false -Recurse C:\
Remove-Item -Recurse -Force C:\Windows  Remove-Item -Recurse -Force $env:USERPROFILE
Remove-Item -Recurse -Force ~
sudo rm -rf /                     bash -c "rm -rf /"
```

**教训：一条判据要钉在「它真正想表达的东西」上。**
这里想表达的是「递归删除一个删了就没了的目标」，那就该把**目标**抠出来判；
一旦写成「盘根出现在第几个参数」，同类写法就会像打地鼠一样一条条漏。
（同日的另一条：判据别钉在「当时机器上恰好是什么状态」—— 见上面那节。）

### 同一天自己举报自己两次（2026-10-03，收尾时）

缺陷修完写报告时，把「发现但没动」的两条也列了出来，随后一起收了：

**① 判据里的「漏一条」：`rm -f /`（不带 `-r`）只判 medium。**
新判据只认「递归删除」，而 `rm -f` 不递归 —— 于是它落到 medium，而 medium 在
「中风险放行」这个**真实配置**下是**静默执行**的。它其实删不掉目录（命令自己会报
`Is a directory`）—— 但**判据不该赌「命令会不会自己失败」**：那是运气的区别，
不是安全的区别。现在 `rm -f` + 危险目标一律 critical，反向锁 `rm -f ./build/file.txt`
仍是 medium（没有 `-r`、相对路径，不该升级）。

**② 自检里的「不自洽」：备份计数断言只在进入时 ≤7 份时成立。**
`04-reliability` 那组用「进入时数量 == 跑完之后数量」验证自己清干净了，
但它自己会造 3 份备份，而 `KEEP=10` —— **进入时 ≥ 8 份就会触发 prune（删最旧的，那是
设计行为）**，断言必红。第一次跑 full verify 就撞上了（本机恰好 8 份），单独跑 `npm test`
反而缓过 —— 典型的**随机红**。改成按会发生的算术断言（`min(进入时+3, KEEP) − 3`），
并单独断言「自己造的 3 份都清掉了」。
**教训：一个测试只要依赖「机器上恰好是什么状态」，它就会在最不该红的时候红。**
