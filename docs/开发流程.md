# 开发流程 —— 加新功能、修 Bug 各按什么走

> 硬规矩（红线、验证纪律、踩过的坑）在 [`../AGENT.md`](../AGENT.md)，冲突时以它为准。
> 本文是它的展开版：生命周期（§1）、开工前模板（§2）、开工三问（§3）、交付报告模板（§4）、
> 分级与两条主路（§5–§10）、真实违规案例（§11）、硬禁区展开（§12）、违规处理（§13）、自我更新（§15）。
> 发布动作单独一份：[`发布检查.md`](发布检查.md)。

一句话：**先分级 → 先固定现象 / 先写清任务 → 找根因或过约束闸 → 最小改动 → 留一个"能红的"护栏
→ verify 全链 + 真机 → 留档 → 发 beta。**

---

## 1. 任务生命周期（五个阶段）

每个阶段都有「责任人 / 必须产出 / 什么情况不允许进入下一阶段」。

| 阶段 | 谁负责 | 必须产出 | 不允许进入下一阶段的情况 |
|---|---|---|---|
| ① 需求对齐 | 双方 | 用户把 §2 模板发过来；AI 把 §3 三问答上来 | 三问任一条答不上；「允许改」清单为空；成功标准不可验证（“优化一下”这种） |
| ② 计划评审 | AI 出、用户拍 | 文件级改动清单 + 验证方式 + 回滚点 | 用户没说「可以动手」；计划里出现 [`../AGENT.md`](../AGENT.md) 第 3 节的硬禁区 |
| ③ 实施 | AI | 每改一步的验证痕迹（命令 + 结果） | 出现范围外改动；发现需求矛盾；测试红着继续改 |
| ④ 验证 | 双方 | `npm run verify` 全链 + `npm run test:app` + 真机结果/截图 | 任一项没跑；性能类没前后数字；UI 类没真机；用「应该没问题」代替结果 |
| ⑤ 交付 | AI 出、用户 review | §4 交付报告 + `CHANGELOG` 一节 | 报告里「是否违反约束」有 ✗ 且未说明；已知遗留被写成「已修复」 |

任一阶段的「停下」都要给**结论 + 选项**（让用户一句话能拍板），不是干等。

## 2. 开工前模板（用户复制）

```
【任务】
做什么：（一句话，可验证）

【范围】
允许改：
- 文件 A
- 文件 B

【成功标准】
1. （可验证的标准）
2. （可验证的标准）

【已知约束】
- 单文件 ≤ 300 行
- 不引入新依赖
- 不动无关文件

按 AGENT.md 的流程，先回答开工三问，等我确认再动手。
```

## 3. 开工三问（AI 必须答）

```
【开工三问】

1. 要做什么？（一句话，可验证）

2. 允许改哪些文件？（列表，含每个文件要改什么）

3. 怎么验证做完了？（命令 + 预期结果）

请确认后我再开始。
```

**AI 不回答三问，用户不允许它开始改代码。** 三问答完但用户没确认，也不允许开始。

## 4. 交付报告模板（AI 必须填）

```
【交付报告】

## 改了什么
- 文件 A：做了什么改动
- 文件 B：做了什么改动

## 为什么这么改（3–5 句设计决策，不是复述 diff）

## 怎么验证的
- `npm run verify`：全链结果（哪一步绿 / 哪一步红）
- `npm test`：通过 X 项，失败 X 项
- `npm run test:app`：channelsExpected / channelsMissing
- 真机验证：（具体做了什么、结果如何；UI 类附截图路径）
- 性能对比：（改前 vs 改后数字，没有就写“不涉及”）
- 数据结构：（用旧数据实测结果，没有就写“不涉及”）

## 已知遗留
- （没有就写“无”；半成品必须写清“哪一半没做”）

## 是否违反约束
- 单文件 ≤ 300 行：✓ / ✗
- 未引入新依赖：✓ / ✗
- 未改动范围外文件：✓ / ✗
- 未主动重构：✓ / ✗
- 未改数据结构：✓ / ✗

## 需要用户确认的事项
- （没有就写“无”）
```

## 5. 改动分级（决定流程重量）

| 级 | 什么算 | 例 | 必要动作 |
|---|---|---|---|
| **L0 小修** | 不看现象就能改的：文案、样式微调、注释 | 改错别字、调间距 | 直接改 → `npm run verify` → 并入最近一轮 beta |
| **L1 修复 / 小增强** | 「它坏了」或「现有模块里挪一步」 | 按钮点不开、弹窗不出现 | 走[修 Bug 流程](#6-修-bug-流程l1) |
| **L2 新功能** | 「它不会做 X」：新页面、新工具、新 IPC 组 | 设置页新增一页、新增一个工具 | 走[新功能流程](#7-新功能流程l2)（一页立项 + 文档三件套） |
| **L3 大改造 / 新项目** | 跨 3 个以上模块、带新数据形状或新协议 | Artifact 系统、插件系统 | 走[大改造流程](#8-大改造--新项目l3)（任务书 + PROGRESS 台账） |

拿不准时问一句：**这是修一个已经坏的行为（L1），还是让应用多一种行为（L2）？**

## 6. 修 Bug 流程（L1）

```mermaid
flowchart LR
  A[1 固定现象] --> B[2 收集证据]
  B --> C[3 全链路找根因]
  C --> D[4 最小修复+同类排查]
  D --> E[5 留护栏·先做红测]
  E --> F[6 verify全链+真机对照]
  F --> G[7 留档]
  G --> H[8 发beta]
```

1. **固定现象**：把「用户看到什么」变成一条可重复的命令或探针（`npm run shot:electron -- --js="…"` 截图 / 敲真键盘、
   `npm run errors --export=<文件>` 取错、或自己写一段探针，写法见 [`验证脚本检查清单.md`](验证脚本检查清单.md)）。
   **先别猜根因** —— 这一步没做完不许动手。（教训：曾对着"任务卡住"连试三个方向的补丁，全打在错的地方。）
2. **收集证据**：`data/logs/actions-*.jsonl`（渲染层每一步 IPC）、任务台账、会话文件、主进程日志；
   按[附录 A 模板](#附录-a缺陷报告模板)写 evidence 报告（存 `E:\Harbor-personal-test\evidence\`）。
3. **全链路找根因**：用户操作 → 渲染层 → IPC → 内核，一环一环过。同时回答：**为什么现有测试没抓住它？**
   —— 答案决定第 5 步护栏加在哪。
4. **最小修复 + 同类排查**：改到根，不贴症状补丁；顺手全库 grep 有没有同模式（「死按钮审计」就是这么一次扫掉一类的）。
5. **留护栏**：把修复**回退掉，测试必须变红** —— 红的才算护栏（同 CONTRIBUTING 的变异测试规矩）。
   位置：内核 → `scripts/selftest/groups/`；渲染层 → `src/**/__tests__/`；端到端 → `tools/acceptance-cases.mjs`。
   跨层接线类问题（测试照不到）**必须真机验证并留对照数字**（例：修前 140 秒不弹出 → 修后 2 秒弹出）。
6. **复核**：`npm run verify` 全链 + 真机复测同一现象，记修前/修后对照。
7. **留档**：CHANGELOG 写**为什么**坏、为什么这么修；新坑进 `docs/踩坑记录.md`；
   没修的部分写进「已知遗留」（诚实优先，别把部分修复写成"已修复"）。
8. **发 beta**：见 [`发布检查.md`](发布检查.md)。复发就回到第 2 步收新证据，别在旧结论上加补丁。

## 7. 新功能流程（L2）

1. **立项一页纸**（[附录 B 模板](#附录-b新功能立项模板)）：做什么 / 明确不做什么 / 怎么算做完 / 怎么验证 / 回滚点。
   放 `docs/改造任务/`，或在 `docs/improvement-checklist.md` 记一行。
2. **约束过闸**（动手前逐条自问，红线定义在 AGENT.md）：
   - 数据放哪？（只准 `data/`）
   - 有密钥/敏感内容吗？（走 credentials，落盘外发过 redact）
   - 改数据结构吗？（必须写迁移，保留旧数据）
   - 加 IPC 通道吗？（同步 `electron/ipc-channels.cjs` 的 `EXPECTED_CHANNELS`）
   - 要引原生依赖吗？（默认不要）
   - 新文件放哪？（单文件 ≤ 300 行，先想清楚住哪再写）
3. **实现**：新逻辑优先新文件；先找仓库里**同模式的参照实现**照着写。
4. **分层测试**：逻辑 → 单测；内核 → selftest 组（正常 / 被权限拦 / 参数非法 三条起步）；
   UI → 真机走一遍；能端到端建模的 → 加进 `tools/acceptance-cases.mjs`。
5. **文档三件套**：README 能力矩阵 / FAQ（能力有变化时）；对应测试指南加编号条目（如 `UI-SET-xxx`）；CHANGELOG 一节。
6. **发布**：同修 Bug 的第 8 步。

## 8. 大改造 / 新项目（L3）

1. **任务书先行**（做法与范例见 `docs/改造任务/README.md`）：做什么、**明确不做什么**（含"用不起所以不做"的理由）、怎么算做完。
2. **PROGRESS 台账**：逐条给「做了没有 / 落在哪个文件 / 怎么验证的」。
3. **拆批交付**：每批 = 一个 L2，独立走完整流程、独立发 beta；不攒大招。
4. **验收核对**：做完补一份逐条核对（参照 `docs/验收核对-通用.md` 的形式）。

## 9. 验证强度表（按「改了什么」查）

| 改了 | 必做（缺一不可） | 为什么会这样 |
|---|---|---|
| `electron/**/*.cjs` | `npm test`（内核自检）；打包后 `--self-test` 看 `channelsOk` | `.cjs` 不参与 tsc |
| IPC 通道增删 | 同步 `EXPECTED_CHANNELS` + `80-handlers` 自检组 | handler 中间抛错会**静默不注册** |
| 数据结构 / 迁移 | 写迁移、保留旧数据、用旧数据文件实测启动 | 用户已有真实数据，丢了不可接受 |
| UI / 会话 / 发送 / 权限 | **真机**走一遍 + 截图 | 两次「测试全绿但废」的事故都出在这 |
| 安全边界（权限 / 文件范围 / 命令 / 密钥） | 同步 `docs/安全模型.md`（含「没做什么」） | 边界会漂 |
| CI（`.github/workflows/`） | 回头同步 `npm run verify` 的步骤 | 曾差一步 prettier：连红 15 次，前 13 次没人发现 |
| 只动 `docs/*.md` | 无；但「规矩」只能改 `AGENT.md` 一处；**会涨的数字不许写死**（见 `AGENT.md` 硬约束 8） | 复制就会漂 |

## 10. 每个交付的收尾清单

```
npm run preflight 全绿（= verify 七步 + 应用自检；剩下的真机步骤它会把清单打出来）
→ CHANGELOG 一节（写为什么；附验证数字）
→ 相关文档同步（安全模型 / 测试指南 / README 能力矩阵）
→ 证据归档（shots/ 或 evidence/；旧件进 E:\Harbor-归档资料）
→ 仓库记忆更新（跨会话要点）
→ commit（一个改动一个提交，信息写为什么）→ 按《发布检查》发 beta
```

## 11. 常见违规案例（都是真实发生过的）

每条：现象 → 根因 → 应该怎么做。改之前扫一眼，这几条都是花过代价的。

1. **拆文件拆废功能**（踩坑记录里有两条）：一次替换把**相邻内容一起搬走**；或者主流程里留个空函数占位就以为拆完了。
   现象：tsc / lint / 全部测试全绿，但流式内容、工具过程全不更新。
   根因：**层与层之间的接线，测试照不到**；`tsc` 也管不了 `.cjs`。
   应该：拆完**读回全文核对边界**，并且真机跑一遍受影响的路径（不是只看「替换成功」）。
2. **宣称修好了，上一版其实没生效**（`CHANGELOG` 0.82.0：「AG-023 补：上一版滚动修复没生效」）：
   现象：上一轮写了「已修复」，用户一用还是旧行为，只能再发一版补。
   根因：验证不充分 —— 只看了单点数值/单一场景，没有覆盖真正的使用路径。
   应该：修完先把修复**回退掉看测试会不会红**；UI 类必须真机走一遍并留修前/修后对照。
3. **本地全绿、CI 连红 15 次**（`CHANGELOG` 1.11.0 那节）：
   现象：`npm run verify` 一直绿，CI 每次 push 都红；前 13 次**没有任何人发现**（用户先看见的）。
   根因：本地链比 CI 少一步 `prettier --check`（就是「本地绿 ≠ CI 绿」）。
   应该：动了 CI 步骤就回头同步 `verify`；格式化会把文件**展开**（`safetyApi.ts` 254 → 330 行顶破红线），
   所以行数红线要和格式检查**同一条链上跑**，发现顶破就按职责拆文件，不是把红线抬掉。
4. **引入原生依赖没算清代价**（`node-pty`）：装不上 / 打包漏拷 / ABI 不对，三个坑都踩过。
   应该：先问「Electron 内置的能不能做」（例如 `safeStorage`）；真必须引，先在 README 写清这三条怎么防。
5. **改了「允许改」之外的文件**（本条我在写这份文档时自己犯了一次）：
   现象：用批量替换时把另外两节的内容**一起吞掉**（替换「成功」了，但内容没了）。
   根因：批量替换的 oldString 边界没核对；只看「替换成功」不看结果。
   应该：改完**读回全文**核对边界（尤其批量替换后）；发现越界立刻就修、并且报告（不许默默改回去）。
6. **测试全绿但功能是坏的**（handler 没注册上）：注册块中间抛错，后面的 handler **静默不注册**（窗口照开）。
   应该：打包后看 `--self-test` 的 `channelsExpected` / `channelsMissing`；加通道同步 `EXPECTED_CHANNELS`。
7. **改数据结构没写迁移**：用户已经有真实数据（会话 / 记忆 / 配置）。
   应该：迁移**保留旧数据**；极端情况（比如解不开的行）宁可**跳过并告知**，也不许整批失败或静默丢。
8. **声称完成但没跑 `npm test`**：`.cjs` 不参与 `tsc` —— 只跑 typecheck 等于内核没验。
   应该：交付报告里那条命令的**输出数字**要贴出来；没跑就写「没跑」，不许含糊过去。

## 12. 什么时候必须停下来问（硬禁区展开）

| 硬禁区 | 判断标准 | 停下来问什么 | 怎么向用户报告 |
|---|---|---|---|
| 动多个文件 | 需要改 >3 个文件 | 要不要拆成几批？先做哪批？ | 列出文件 + 每个要改什么 + 为何必须 |
| 新依赖 | 要加 `dependencies` / `devDependencies` | 能否用现有依赖 / 内置能力代替？ | 依赖名 + 为什么必需 + 不用它的代价 |
| 改数据结构 | 字段增删 / 形状变化 | 要不要迁移？旧数据怎么保？ | 新旧形状对照 + 迁移方案 + 回滚点 |
| 需求矛盾 | 两条要求互相打架 | 哪一条优先？ | 把两条原话列出来 + 各自后果 |
| 测试绿但行为异 | 测试说好、真机说坏 | 以哪个为准？先固定现象吗？ | 真机现象 + 当前测试为何没拓住 |
| 之前改动引入回归 | 新问题出现在老功能上 | 回滚还是继续修？ | 哪个提交引入的 + 回滚代价 |
| 顺手一提 | 想做用户没要求的事（重构/优化/整理） | 要不要现在做？ | 只描述，不先动手；用户说要才做 |
| 内核关键文件 | 要动 `loop.cjs` / `task.cjs` / `session*.cjs` / `changeset.cjs` | 改动面有多大？怎么验证？ | 调用链 + 受影响的路径 + 验证方式 |
| 加/改 IPC 通道 | 新增或改名一个通道 | 能不能不加通道解决？ | 通道名 + 同步 `EXPECTED_CHANNELS` + 自检组 |
| 权限 / 安全模型 | 要动 `risk.cjs` / `capability.cjs` / `credentials.cjs` / `navigation-policy.cjs` / `net-policy.cjs` / `redact.cjs` | 边界怎么变？ | 旧边界 → 新边界 + 「这次没做什么」 |

## 13. 违规处理的流程

1. **发现自己违规** → 立刻停下（不许先做完再解释）→ 报告 → 等确认 → 修正。
2. **发现之前做错** → **不要偷偷改** → 说出来 → 一起决定怎么修（可能选「先回滚」）。
3. **想到「更好的做法」** → 只报告，不动手；用户决定要不要做。
4. 修正完要在交付报告里写清：**违反的是哪一条、怎么改回来的、以后怎么避免**。

**偷偷改比不改更严重。**

## 14. 反馈回路（用户试玩 → 修复）

- **入口**：试玩时把「什么时候看到什么」直接丢给会话；**截图最有用**，日志次之。安全漏洞走 `SECURITY.md` 的私密渠道。
- **编号**：缺陷用 `DEF-<域>-NN`（已有先例 `DEF-UI-03`、`DEF-P1`）—— **号不复用**，修没修都留着。
- **归档**：每条反馈 → evidence 报告（附录 A 模板）→ 走修 Bug 流程；
  反复出现的进 `docs/improvement-checklist.md` 或踩坑记录。
- **节奏**：beta 通道滚动发（`-beta.N`）；每轮收尾固定是「发布 → 更新 E:\Harbor → 真机核对版本号」，
  详见[发布检查](发布检查.md)。

## 15. 约束机制的自我更新

**每次出现新的违规类型（或新的坑），都要回来更新这四份：**

| 更新哪里 | 写什么 |
|---|---|
| [`../AGENT.md`](../AGENT.md) | 规矩（硬约束 / 硬禁区）—— 能落地检查的才加 |
| 本文（`开发流程.md`） | 案例（§11）+ 流程缺口（某阶段拦不住这类事） |
| `scripts/check-rules.mjs` | 能机械化的检查项（机械查不了的写进人工 review 清单） |
| [`踩坑记录.md`](踩坑记录.md) | 真实报错 + 当时的症状（给人看的“为什么”证据） |

约束不是一次写完的，是**每次踩坑后补一句**。只写文档不写检查 = 约束会漂。

## 附录 A：缺陷报告模板

```md
## DEF-<域>-NN <一句话>
- 现象（用户视角，何时看到什么）：
- 复现（命令 / 探针 / 步骤；稳定复现还是偶发）：
- 证据（actions.jsonl 片段 / 台账 / 会话文件 / 截图路径）：
- 根因（全链路哪一环；为什么测试没抓住）：
- 修复与护栏（改了什么；哪个测试会拦住复发；红试验证过再写"验过"）：
- 真机对照（修前 vs 修后）：
- 已知遗留（没修的部分，诚实写）：
```

## 附录 B：新功能立项模板

```md
## <功能名> —— 立项一页纸
- 做什么（一段话）：
- 明确不做什么：
- 怎么算做完（可测的验收标准）：
- 怎么验证（单测 / 自检组 / 真机 / 验收场景，各要哪几条）：
- 数据影响与回滚点（要不要迁移）：
- 风险与依赖（原生库 / 新 IPC / 安全边界）：
```
