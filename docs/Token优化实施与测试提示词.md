# Harbor Token 优化实施与测试提示词

> 本文档已拆分。后续执行以 [`AGENT_TOKEN_OPTIMIZATION.md`](./AGENT_TOKEN_OPTIMIZATION.md) 为入口，以 [`TOKEN_OPTIMIZATION_SPEC.md`](./TOKEN_OPTIMIZATION_SPEC.md) 为完整规范，以 [`TOKEN_OPTIMIZATION_CHECKLIST.md`](./TOKEN_OPTIMIZATION_CHECKLIST.md) 为验收记录。本文保留为历史增强稿，不再单独维护，避免两套规则漂移。

## 1. 用途

本文档依据最新提供的 token 优化任务文本重新整理，不参考此前附件版本。它用于交给开发 Agent，使其在 Harbor（Electron + React + TypeScript）中实施并验证上下文、缓存、输出、工具调用、重试、跨任务、预算和锚点优化，并在每个阶段完成问题发现、修复、回归、文档更新和用户确认闭环。

## 2. 使用前必须替换的参数

将下列占位符替换成当前测试环境的真实值：

```text
<TEST_DATA_DIR>      独立测试 data，禁止指向个人真实 data
<TEST_WORKSPACE>     可丢弃或可恢复的测试仓库
<MODEL_NAME>         实际模型名称
<MAX_COST>           单批次费用上限
<MAX_INPUT_TOKENS>   单次输入 token 上限
<MAX_OUTPUT_TOKENS>  单次输出 token 上限
<CACHE_FIELDS>       API 实际返回的缓存 usage 字段
<BASELINE_COMMIT>    优化前基线提交
<TARGET_COMMIT>      待测试提交
```

## 3. 可直接交给开发 Agent 的增强提示词

```text
你正在维护 Harbor，一个本地优先的 Agent 桌面应用，技术栈为 Electron、React 和 TypeScript。

你的任务是完成一次可测量、可回退、兼容现有数据的 token 优化。优化范围包括：
1. 输入上下文分层和稳定前缀。
2. API 上下文缓存命中率。
3. 输出长度和结构。
4. 工具调用次数、并行度和结果压缩。
5. 失败重试和检查点恢复。
6. 跨任务模板和可复用信息。
7. 预算调度。
8. 强锚点、弱锚点和临时上下文。

最高优先级约束：
- 任务成功率、文件修改准确率、安全边界和可恢复性不得下降。
- 模型声称成功不算成功；以文件产物、命令退出码、任务账本和日志为准。
- 不为了提高缓存命中率而注入过期项目状态、错误计划或无关记忆。
- 不删除或清空用户真实 data。所有破坏性测试使用 <TEST_DATA_DIR> 和 <TEST_WORKSPACE>。
- 不在日志、报告、请求快照或 Git 中输出 API key、Authorization header 和私人内容。
- 不引入新依赖，除非现有标准库和项目依赖无法满足，并先记录理由。
- 保持旧数据格式可读；新增字段必须有默认值、迁移和幂等测试。
- 改动保持在 token 优化相关模块，不重构无关代码。

开始前：
1. 阅读 AGENT.md、package.json、现有上下文组装、LLM 请求、任务账本、恢复、预算、工具缓存和自检代码。
2. 画出当前请求构造链路：用户输入 → 上下文收集 → 消息排序 → API body → 流式响应 → usage → 任务账本。
3. 找出会破坏稳定前缀的动态字段，包括时间戳、随机 ID、会话 ID、动态统计、对象键顺序和不稳定数组顺序。
4. 记录优化前基线，不凭估算填写 token 或缓存数据。
5. 先提出最小改动方案、影响文件、迁移方式和回退开关，再开始实现。

缓存事实约束：
- 缓存指标字段以 API 实际响应为准。若 prompt_cache_hit_tokens、prompt_cache_miss_tokens 或同义字段不存在，记录“供应商未提供”，不得填 0 冒充。
- 缓存命中受模型、端点、服务端生命周期和请求前缀影响。不同模型、不同供应商或不同端点的数据不得直接比较。
- 计算命中率前确认分母定义：hit / (hit + miss)。若字段语义不同，报告中写明换算方法。
- 后台预热会产生请求、token 和费用，默认关闭。只有用户明确启用并设置费用上限时才测试。
- 任何预热请求必须可取消、可观测，不得携带用户会话正文或敏感文件。

一、上下文分层

实现三层上下文，并为每一层生成可诊断的 content hash：

A. 稳定层
- Agent 身份和不变行为约束。
- 工具、MCP 和 Skills 定义。
- 项目规则文件。
- 固定系统提示。
- 同一任务后续请求应逐字节稳定，序列化顺序必须确定。

B. 低频层
- 项目结构摘要。
- 检索得到的长期记忆 Top 3-5。
- 任务计划和冻结历史摘要。
- 只有依赖版本、项目结构、任务计划或明确相关记忆改变时才更新。

C. 动态层
- 最近 3-5 轮必要对话。
- 压缩后的当前工具结果。
- 当前步骤、失败原因和用户最新输入。
- 每轮只追加或替换本轮局部数据。

请求排列固定为：稳定层 → 低频层 → 动态层。
不要把时间戳、随机 UUID、session salt、实时 token 统计放进稳定前缀。
不要仅为调试改变对象字段顺序或提示词空白。

请增加诊断字段：
- stable_prefix_hash
- low_frequency_hash
- dynamic_context_hash
- stable_prefix_changed
- stable_prefix_change_reason
- context_tokens_by_layer

这些字段进入任务账本或脱敏诊断，不进入发给模型的稳定前缀。

二、冻结摘要和锚点

- 对话超过配置阈值后，将最旧的一段压缩为冻结摘要。
- 冻结摘要创建后不原地重写；需要更新时新增摘要块并保留版本关系。
- 强锚点：任务目标、用户明确约束、规则、安全边界，每轮注入。
- 弱锚点：历史摘要和记忆，按相关性和 token 预算注入。
- 临时内容：工具结果和中间输出，仅在当前步骤或短期窗口有效。
- 强锚点也有总量上限；过长时提示用户或生成经过校验的等价摘要，不能无限累积。

提示句：
“先保留目标、约束和当前步骤，再压缩解释和重复内容；不得为了省 token 删除验收条件。”

三、工具结果压缩

- 文件读取按请求范围返回，不默认返回完整大文件。
- 命令输出保留退出码、错误摘要、关键首尾内容和原始日志路径。
- 截断时明确标记 omitted_lines、original_bytes 和 truncation_reason。
- 二进制、超大文件和未知编码不直接注入模型上下文。
- 文件缓存以规范化路径、内容哈希、mtime/size 和读取范围作为键。
- 写入、外部修改、Git checkout 或任务恢复后必须使相关缓存失效。

提示句：
“工具结果只保留下一步决策所需的信息；如果省略内容可能改变判断，先缩小读取范围，不要猜。”

四、输出控制

- 普通回答先给结论，再给必要依据，不复述用户问题。
- 原生工具调用使用供应商/SDK 的 tool call 协议，不强迫模型把所有工具调用写成普通 JSON 文本。
- 只有内部协议明确要求时才使用 JSON，并通过 schema 校验。
- max_tokens 按任务阶段和复杂度设置，并记录选择原因。
- 不依赖截断代替合理预算；输出可能被截断时先缩小范围或分阶段。
- 反思循环必须有轮数上限；达到上限后给出结论、保守方案或询问用户。
- 跑偏检测只能在高置信度下终止，并保存终止原因；不得误杀合法代码和长答案。

提示句：
“先给可执行结论，再给支持结论所需的最少证据。不要写开场白，不要重复任务，不要用冗长总结替代实际结果。”

五、工具调用

- 无依赖且只读的工具可以并行。
- 有写入关系、共享目录、同一文件或前一步决定后一步参数时必须串行。
- 并行调用必须保持结果与请求 ID 的稳定映射。
- 每个工具描述补充“何时调用”和“何时不要调用”。
- 记录有效调用、重复调用、空结果调用、失败调用和缓存命中。
- 无效调用率的定义必须固定：无助于下一步决策且没有形成必要证据的调用 / 总调用。

提示句：
“先判断调用之间是否存在数据或副作用依赖；只有真正独立的读取才并行。不要为了减少轮数并行写同一文件。”

六、失败重试

- 重试不是从头执行。复用稳定层、低频层、任务计划、已完成步骤和已验证产物。
- 只注入结构化失败摘要：error_kind、operation、target、message_summary、retry_count。
- 不重复注入完整 stdout、堆栈和已读文件，原始内容保留在日志路径。
- 写入和外部副作用操作重试前先确认是否已经部分成功。
- 设置每类错误的重试上限和降级策略。
- 认证错误、权限拒绝、明确用户取消和确定性参数错误不得盲目自动重试。

提示句：
“先确认上次操作是否产生了部分结果，再决定重试。已经成功的步骤不要重做，可能重复产生副作用的动作必须停下来核对。”

七、跨任务复用

- 高频任务模板只提供建议计划和工具序列，不绕过 Agent 对实际项目的检查。
- 模板必须版本化，并记录 template_id 和 template_version。
- 不同工作区的规则、记忆、文件缓存和项目摘要严格隔离。
- 跨会话只复用项目稳定前缀，不复用另一个会话的用户私有动态内容。
- 预热默认关闭；启用时记录请求、费用、命中和失效时间。

八、预算调度

- 任务开始时建立输入、输出、工具和重试预算。
- 预算按已消耗、已预留和剩余分别记录。
- 80% 只是默认软阈值，可配置；达到阈值时先保留任务目标、安全约束和当前验收条件。
- 预算不足时减少冗余解释、重复读取和低相关记忆，不降低文件验证和安全检查。
- 切换模型前说明原因；不要假设不同模型共享缓存。

提示句：
“预算不足时优先完成当前可验证步骤，保留安全检查和产物验证；减少说明文字，而不是省略关键验证。”

九、指标

每次 API 请求记录：
- input_tokens、output_tokens、total_tokens。
- API 实际提供的 cache hit/miss token 字段。
- cache_hit_rate 或 unavailable。
- stable_prefix_hash、low_frequency_hash。
- request_latency_ms、time_to_first_token_ms。
- model、endpoint、retry_count、task_stage。
- tool_calls、tool_cache_hits、invalid_tool_calls。

每个任务记录：
- 成功/失败/部分完成。
- 实际产物验证结果。
- 用户干预次数。
- 总 token、总费用、总耗时。
- 与同类基线的变化百分比。

十、基线和对照实验

- 使用相同提交、相同工作区夹具、相同模型、相同端点和相同提示词。
- 优化前后每个场景至少运行 3 次；模型波动较大时运行 5 次。
- 报告中展示中位数和 P95，不只展示最好一次。
- 缓存测试区分冷启动、同会话热缓存、跨会话同项目和缓存过期。
- 质量对比使用固定验收器：文件 hash/diff、测试退出码、必需内容、禁止变更和安全边界。
- 若无法复现优化前版本，明确标记“无可比基线”，不估算节省比例。

十一、阶段执行

阶段 0：建立隔离测试环境和基线。
阶段 1：上下文分层、冻结摘要、锚点和缓存诊断。
阶段 2：输出、工具压缩、并行调用和文件缓存。
阶段 3：失败重试、部分成功检测、降级和恢复。
阶段 4：模板、预算和可选预热。
阶段 5：综合回归、质量、稳定性和成本报告。

每个阶段结束后必须停止推进，完成问题处理与改进闭环，提交阶段报告并等待用户确认。用户确认前不得进入下一阶段，也不得提前实施下一阶段内容。

阶段门禁：
- 阶段 0：隔离环境、真实 API 连通性和基线表已完成。
- 阶段 1：三层上下文正确、恢复不完整重放、缓存命中率达到该环境可验证的目标。
- 阶段 2：输出约束生效、独立工具调用可并行、无效调用率低于 15%。
- 阶段 3：重试保持稳定前缀、部分成功不重复执行、降级策略生效。
- 阶段 4：模板复用、跨会话稳定前缀、预算调度和经授权的预热测试完成。
- 阶段 5：token 目标、质量回归、20 任务稳定性和历史缺陷回归全部完成。

十二、停止条件

遇到以下任一情况立即停止相关真实 API 测试并保留现场：
- 单次或批次 token/费用超过配置上限。
- API usage 字段异常或无法可信计算缓存指标。
- 任务质量、文件正确率或安全边界下降。
- 真实凭证进入日志、报告或截图。
- 重试产生重复写入或其他副作用。
- 稳定前缀意外变化且无法解释。
- 测试工作目录指向真实用户 data 或重要项目。
- 同一阶段连续修复或验证失败 3 次；暂停自动循环，提交现象、已尝试方案和需要用户决定的事项。

十三、必须执行的验证

- npm run typecheck
- npm run lint
- npm run check:format
- npm run check:lines
- npm run test:unit
- npm test
- npm run build
- 涉及 UI、发送、流式、权限、恢复时，运行真实 Electron 点击流程。
- npm run test:app 仅在 Electron 环境可用时执行；若无法执行，报告原因，不伪报通过。

十四、交付物

1. 修改文件和新增字段/函数清单。
2. 优化前后请求组装流程图。
3. 三层上下文、冻结摘要和锚点设计。
4. 缓存 usage 字段和命中率计算说明。
5. 每轮和每任务指标 schema。
6. 基线与优化后的中位数/P95 对比。
7. 质量、安全、恢复和 UI 回归结果。
8. 失败、修复和仍未解决的问题。
9. 回退开关和数据迁移说明。
10. docs/测试记录/token优化测试.md。
11. docs/测试记录/token优化问题.md。
12. docs/token优化说明.md。
13. CHANGELOG.md 中每阶段的原因、改动和踩坑记录。
14. 验收标准 a-u 的逐项证据表。

不要仅提交实现说明。实现、测试、真实产物验证和报告必须同时完成。
```

## 4. 测试执行方式：保持应用运行

### 4.1 总体原则

测试期间，除非测试用例明确要求，否则不要反复关闭和打开 Harbor。反复重启会破坏缓存命中率、跨会话稳定前缀、预算连续性和任务恢复的测试条件，同时浪费时间和真实 API token。

核心规则：

1. 整个测试过程只在阶段 0 首次启动应用。
2. 阶段 1-4 保持同一应用实例运行。
3. 需要干净上下文时新建对话，不重启应用。
4. 只有检查点恢复、预热缓存和计划内稳定性重启可以关闭应用。
5. 整个测试过程允许的计划内重启次数最多为 3 次。
6. 某阶段重启超过 1 次时，立即停止该阶段并报告原因，等待用户确认。
7. 整个测试过程重启超过 3 次时，暂停测试并报告，不继续消耗真实 API。

“重启一次”定义为完成一组 `关闭应用 → 确认退出 → 重新打开应用`。应用崩溃后重新打开也计入重启次数，并标记为非计划重启。

### 4.2 用新建对话代替重启

需要以下状态时，新建对话即可：

- 新的对话上下文。
- 清空当前对话历史。
- 独立预算计数。
- 独立记忆检索。
- 独立任务账本。
- 比较同一项目的跨会话稳定前缀。

错误做法：

```text
关闭应用 → 重新打开 → 新建对话
```

正确做法：

```text
保持应用运行 → 新建对话
```

新建对话不能替代以下重启场景：

- 验证数据持久化和进程恢复。
- 验证真正的冷启动缓存或启动预热。
- 验证全局配置在进程启动时重新加载。
- 验证应用退出后的进程、句柄和任务状态。

### 4.3 测试分类：哪些需要重启，哪些不需要

绝大多数测试通过新建对话、继续当前对话或继续当前任务获得所需状态，不需要重启应用。

#### 4.3.1 不需要重启的测试

| 测试 | 获得所需状态的方式 | 隔离和记录要求 |
|---|---|---|
| 上下文分层验证 | 新建对话 | 记录第一轮和第二轮三层 hash |
| 缓存命中率验证 | 同一对话连续发消息 | 不改变模型、端点和稳定前缀 |
| 冻结摘要验证 | 同一对话发满 N 轮 | 固定 prompt 序列，记录摘要版本 |
| 锚点机制验证 | 同一对话内检查 | 分别记录强、弱、临时锚点 |
| 入口压缩验证 | 同一任务内连续调用工具 | 保存压缩前后大小和截断标记 |
| 结构化输出验证 | 新建对话发任务 | 记录原生 tool call 或 JSON schema |
| 动态 `max_tokens` 验证 | 同一对话发三个不同任务 | 每个任务使用独立 task_id，记录阶段和复杂度 |
| 反思循环检测 | 同一对话发模糊任务 | 设置轮数和 token 上限 |
| 并行工具调用验证 | 同一任务内 | 记录调用时间线和依赖关系 |
| 工具结果缓存验证 | 同一任务内连续调用 | 首次读取后文件不得被外部修改 |
| 无效调用比例验证 | 同一对话连续发 10 个任务 | 每个任务独立计数，再汇总比例 |
| 缓存感知重试验证 | 同一任务内触发重试 | 保存重试前后前缀 hash |
| 失败原因注入验证 | 同一任务内连续失败 | 只注入结构化失败摘要 |
| 降级策略验证 | 同一任务内连续失败 5 次 | 受“三次连续失败暂停”规则约束，达到三次先报告确认 |
| 任务模板验证 | 同一对话连续做 3 次同类任务 | 使用不同测试文件，避免产物复用造成假命中 |
| 跨会话前缀复用验证 | 新建对话，不重启 | 保持项目、模型、工具和规则不变 |
| 预算调度验证 | 同一任务内消耗到 80% | 使用专用预算，避免影响后续任务 |
| 综合场景测试 | 每个场景新建对话 | 每个场景使用独立 task_id 和 workspace fixture |
| 回归验证 | 新建对话 | 每个历史 bug 使用固定复现夹具 |
| 任务质量验证 | 新建对话 | 使用固定评分器和相同输入 |
| 稳定性验证（连续 20 个任务） | 同一应用内连续运行 | 任务之间按测试计划新建对话，不关闭应用 |

**按本表实际计数，21 类测试的主体均不需要重启；加上检查点恢复和预热缓存两类必要重启测试，共计 23 类，其中 21 类不需要重启。** 
稳定性验证主体的连续 20 个任务不需要重启；只有测试计划明确包含“运行后重启恢复检查”时，才在 20 个任务完成后使用第 3 次计划内重启。

#### 4.3.2 必须重启的测试

| 测试 | 为什么必须重启 | 预计占用重启次数 |
|---|---|---:|
| 检查点恢复验证 | 验证进程退出后的任务持久化和恢复 | 1 |
| 预热缓存验证 | 验证真正的启动预热和首次请求 | 1 |
| 稳定性重启场景（可选） | 验证连续 20 个任务后的重启一致性 | 0 或 1 |

#### 4.3.3 执行顺序建议

为了减少重启并保持状态连续，按以下顺序安排：

1. 阶段 0 启动应用一次。
2. 执行阶段 1 中不需要重启的测试。
3. 在阶段 1 末执行检查点恢复，使用第 1 次重启。
4. 保持应用运行，执行阶段 2、阶段 3 和阶段 4 的非预热测试。
5. 在阶段 4 最后执行预热缓存，使用第 2 次重启。
6. 保持应用运行，执行阶段 5 的综合、回归、质量和连续 20 任务测试。
7. 只有计划要求时执行稳定性重启，使用第 3 次重启。

若某项测试意外要求额外重启，先记录原因并检查是否可以通过新建对话、清理测试任务或更换独立 fixture 解决；不得为了“方便清状态”直接重启。

### 4.4 检查点恢复测试

这是一次必要的计划内重启：

1. 保持应用运行并发起一个多步任务。
2. 执行到第 3 步时暂停任务。
3. 记录任务 ID、对话 ID、检查点 ID、已完成步骤、任务账本路径和当前 token 统计。
4. 关闭应用。
5. 确认 Harbor、Electron 和任务子进程已退出。
6. 重新打开同一测试应用和同一测试 data。
7. 恢复任务并检查：
   - 只重放最近 3-5 轮。
   - 包含任务计划和已完成步骤摘要。
   - 不注入不必要的中间工具调用细节。
   - 不重复已完成且可能产生副作用的步骤。
8. 记录恢复请求的 input/output/cache token、前缀 hash 和实际产物。
9. 测试结束后保持应用运行。

### 4.5 预热缓存测试

预热测试安排在其他不需要重启的阶段 4 用例之后，并且只有用户已经授权预热请求和费用上限时执行：

1. 记录关闭前的应用实例、对话、任务、缓存和费用数据。
2. 关闭应用并确认所有进程退出。
3. 等待 5 秒，不把固定等待当作退出证据；同时检查进程确实不存在。
4. 重新打开应用。
5. 不发送用户消息，等待 10 秒预热窗口。
6. 记录预热期间是否产生请求、使用的模型、token、费用和前缀 hash。
7. 发送第一个任务：“读一下 README。”
8. 记录首次请求的缓存原始字段和命中率。
9. 与关闭预热时的冷启动基线比较。
10. 测试结束后保持应用运行。

如果服务端缓存生命周期、模型或端点发生变化，结果标记为不可直接比较，不能为了达到 50% 指标反复重启和重试。

### 4.6 稳定性重启测试

只有阶段 5 测试计划明确包含时执行：

1. 保持应用运行，连续完成 20 个混合任务。
2. 记录内存、CPU、句柄、响应时间、失败数和 token。
3. 记录重启前所有未完成任务和检查点。
4. 关闭应用并确认进程退出。
5. 重新打开应用。
6. 检查任务账本、会话、未完成任务、检查点和 UI 状态。
7. 检查是否出现重复恢复、幽灵任务、状态不一致或遗漏任务。
8. 测试结束后保持应用运行。

### 4.7 非计划退出

发生崩溃、系统重启、进程被杀或应用无响应时：

- 保存崩溃日志、任务 ID、对话 ID、最后一个检查点和进程信息。
- 计入总重启次数和当前阶段重启次数。
- 标记原因 `unplanned_crash`、`forced_kill`、`system_restart` 或 `hang_recovery`。
- 不自动连续重新打开应用超过一次。
- 若该阶段已经重启过一次，停止并报告。

## 5. 每阶段问题处理与改进闭环

以下流程来自最新任务要求，阶段 1-5 每次结束后必须完整执行；阶段 0 发现环境或基线问题时同样适用。

### 5.1 问题收集与分级

把本阶段所有异常、失败、未达标项和可疑数据写入 `docs/测试记录/token优化问题.md`：

| 级别 | 定义 | 示例 | 阶段能否通过 |
|---|---|---|---|
| P0 | 任务无法完成、数据损坏、状态丢失、成本严重超标、安全事故 | 重试重复写文件、真实 data 被清空 | 否 |
| P1 | 核心优化或功能不工作 | 缓存前缀不稳定、恢复完整重放 | 否 |
| P2 | 性能、日志或非核心 UI 未达预期 | 诊断字段缺失、部分延迟回退 | 需说明并评估 |
| P3 | 文案、非关键异常或后续优化 | 指标名称不清晰 | 可记录待办 |

每条问题使用唯一 ID，例如 `TOK-P1-003`，记录发现阶段、关联测试、首次出现提交和证据路径。

### 5.2 根因分析

每个 P0/P1 必须记录：

```text
问题 ID：
现象：
触发条件：
复现步骤：
定位文件/函数/逻辑：
直接原因：
根因：
影响范围：
是否涉及数据迁移：
是否涉及真实 API 成本：
修复方案：
回退方案：
```

不能只写“缓存没命中”或“测试失败”。根因需要回答稳定前缀哪一段变化、由什么输入触发、为什么已有测试没有发现。

### 5.3 修复

修复顺序为 P0 → P1 → P2。每个修复必须：

1. 先添加可稳定复现问题的测试或诊断夹具。
2. 实施最小范围修复。
3. 运行新增测试和相关测试。
4. 检查 token、缓存、任务质量和副作用。
5. 更新问题状态为“已修复”或“待用户决定”。

禁止为了达标修改统计口径、隐藏失败样本、降低质量验收器或删除回归测试。

### 5.4 回归验证

修复完成后：

- 重跑本阶段全部测试。
- 重跑上一阶段核心测试。
- 涉及数据结构时验证旧数据、迁移幂等和默认字段。
- 涉及发送、流式、恢复、权限或 UI 时执行真实 Electron 点击。
- 使用新的 run_id 保存回归结果，不覆盖原失败证据。

### 5.5 达标判定

每阶段必须给出 `通过`、`部分通过` 或 `不通过`：

- 有未修复 P0/P1：不通过。
- 核心指标无可信证据：不通过。
- P2 未解决但不影响核心目标：可部分通过，但必须等待用户决定。
- 全部门禁满足且证据齐全：通过。

### 5.6 主动发现额外优化点

对测试中出现的计划外优化，记录：

```text
优化点：
发现依据：
预期 token 节省：
预期延迟变化：
质量/安全风险：
实现成本：低 / 中 / 高
建议：立即实施 / 后续待办 / 不实施
```

收益明确、成本低且属于当前阶段范围的优化可以实施并验证；高成本、跨阶段或扩大权限的优化只记录待办，不能擅自扩展任务。

### 5.7 文档同步

每阶段结束更新：

- `docs/测试记录/token优化测试.md`：测试输入、预期、实际、token、缓存、结果和证据。
- `docs/测试记录/token优化问题.md`：问题、根因、修复和回归。
- `docs/token优化说明.md`：最终实现结构和配置。
- `CHANGELOG.md`：为什么改、改了什么、遇到什么问题。

## 6. 建议追加到系统提示的短句

这些句子适合集中管理，按任务阶段选择注入，不要每轮全部重复。

### 6.1 通用精简

```text
先给结论，再给必要依据；不要复述任务，不写开场白。
只保留完成当前步骤所需的上下文，重复信息引用已有摘要。
模型自报完成不算完成，必须检查实际产物或退出码。
```

### 6.2 读取任务

```text
先定位相关文件和范围，再读取内容；不要默认读取整个仓库或完整大文件。
已有内容哈希未变化且缓存覆盖所需范围时，复用缓存并记录命中。
```

### 6.3 修改任务

```text
修改前确认目标、约束和受影响文件；只改完成任务所需的最小范围。
修改后检查真实 diff 和必要测试，不以编辑工具返回成功作为最终成功。
```

### 6.4 工具调用

```text
没有依赖关系的只读调用可以并行；共享文件、写入或参数依赖必须串行。
不要重复调用已经得到有效结果且数据未变化的工具。
```

### 6.5 失败重试

```text
重试前检查上次操作是否部分成功；已完成步骤不要重做。
只携带结构化失败原因和下一步所需信息，不重复注入完整失败输出。
```

### 6.6 预算接近上限

```text
剩余预算有限。优先完成当前可验证步骤，保留安全检查和产物验证；减少解释、重复读取和低相关记忆。
```

### 6.7 恢复任务

```text
从最后一个已验证检查点继续。不要重放完整历史，也不要重复执行可能产生副作用的已完成动作。
```

### 6.8 任务结束

```text
简要报告实际完成内容、验证结果和仍未完成事项。不要把计划、尝试或模型判断写成已完成事实。
```

## 9. 根据最新文本补充的执行保护

1. “清空 data”改为建立独立测试 data，避免误删真实凭证和会话。
2. 缓存字段以 API 实际响应为准，缺失时不伪造统计。
3. 预热缓存默认关闭，因为它会产生真实费用且服务端缓存生命周期未必可控。
4. 工具调用优先使用原生 tool-call 协议，不一律强制普通 JSON。
5. 并行只用于无依赖读取，避免同一文件或共享状态并发写入。
6. 缓存命中率阈值作为观测目标，不脱离模型、端点和冷/热状态做硬结论。
7. token 下降必须与任务质量、实际产物、安全和人工干预共同判断。
