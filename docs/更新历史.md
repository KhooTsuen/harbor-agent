# 更新历史（Release 归档）

> 这个文件解决一件事：**GitHub 上删掉的 release，更新内容去哪查**。
> 每个版本的完整正文（为什么改 / 改了什么 / 验证数字 / 遗留）一律在
> [`CHANGELOG.md`](../CHANGELOG.md)（版本段从 `0.2.0` 起；**有多少段看文件里 `## [` 的条数**，
> 每发一版就涨，不在这里写死）。本表只是**索引**：版本、发布日期、状态、一句话、「去 CHANGELOG 搜哪个标题」。
>
> **保留策略**：GitHub 上只保留 **1 个 beta + 1 个正式版**（规矩见 [`发布检查.md`](发布检查.md)）。
> 删除的是「版本入口 + 构建 zip」；**代码提交都还在 git 历史里**。
> 清理用 `npm run release:prune -- --keep=v<正式版>,v<beta> [--tags] [--apply]`（默认 dry-run）；
> 要查旧 tag 指向哪个提交：`git show-ref --tags`（tag 已删的话，SHA 在本表的 commit 列里）。
> （原来这里写着「权威清单 `tmp/releases-manifest-all.json`」—— 那个文件**已经不在仓库里**了。）

## 说明

- **保留（2）**：`v1.29.0`（最新正式版，GitHub「Latest」）+ `v1.30.0-beta.15`（最新 beta）。
- **已删除（49）**：历次按保留策略替换下来的版本（最大的一批是 2026-09-26/27/28 清理，
  起因是版本过多 —— 2026-09-25 一天连发 16 个 beta）。
  删除时逐个记录了 tag → commit SHA；早期批次的附件清单（zip 名/大小/下载数）因文件重名被覆盖，
  但 zip 命名规则固定（`harbor-<版本>-win-x64.zip`），SHA 与标题均完好。
- **commit 列填的一律是 commit SHA，不是 tag 对象 SHA**：tag 删掉后 tag 对象会被 `git gc` 清成悬空引用，
  只有 commit SHA 在 main 历史里长期可查（2026-10-08 把残留的 29 行 tag 对象 SHA 统一换成 commit SHA）。
- 另有 **186 个版本只存在于 CHANGELOG、从未发过 GitHub release**（例如 `1.7.x` / `1.8.x` / `1.10.x` 系列）
  —— 算法：CHANGELOG 里唯一版本号 237 − 本表 51 = 186（`grep -c '^## \['` 后去重）
  —— 它们本来就不在 Releases 页，检索方式同上。
- 归档原则：**正文只写一份**（CHANGELOG），本表不复制内容，避免两处漂移。
