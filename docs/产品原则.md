# 产品原则（长期方向）

> **这份记的是「方向」，不是「流程」。** 它回答「Harbor 要做成什么样的东西」，
> 不回答「这一件活分几步」—— 后者在 [`../AGENT.md`](../AGENT.md)（硬约束 / 硬禁区 / 收工必跑）
> 和 [`开发流程.md`](开发流程.md)。
>
> **这五条不新增任何执行限制。** 它们是判断依据，不是闸门：硬约束照旧、硬禁区照旧，
> 而**用户本轮明确授予的权限也不被它们覆盖**（他说「可以改」，就是可以改）。

## 为什么要有这一份

这类方向以前只活在**对话里**。换一个开发会话，它就不在场了 —— 已经真丢过一次：

> 「Harbor 自己的数据尽量放在软件所在磁盘，而不是默认堆在系统 C 盘」是早期就定下的要求，
> 但它从来没有写进任何一份会被自动加载的文件。后来连续几轮开发都没继承它，
> 直到用户自己重新提出来（2026-11-06）。

所以它必须住在**新会话读得到的地方**，而不是靠人记得复述。

**存放约定**：五条方向的**全文只有这一处**。`AGENT.md` 第 0.5 节只有每条的**一句话标签**
+ 指向本文件的路径 —— 这是 `AGENT.md` 第 8 节「附录外置」的同一套做法，
为的是既不重复（重复就会漂），又不让这份文档只靠「有人记得去读」。

## 1. 用户意图与控制权

**目标**：降低普通人把想法付诸实践的执行门槛，**不局限于编程**。

**怎么分权**：用户决定**目标和重要边界**；Agent 在**授权范围内自主完成执行**。
用户不需要逐步指挥，但也不能被替做决定 —— 拿不准时按 `AGENT.md` 第 0 节那句话推：
宁可多问一次、多留一个回滚点。

**和现有规范的关系**：`AGENT.md` 第 0 节已经写了「控制权」这一半；
「降低门槛、不限于编程」这一半**此前没有任何文档写过**，是本份新增的。

## 2. 存储位置

**原则**：Harbor **自身可管理**的运行数据、日志、缓存、记忆、备份及其他应用数据，
应优先放在**软件所在磁盘**或**用户指定的位置**；不要无必要地默认使用系统 C 盘。

**必须区分三类，不能机械化**：

| 类别 | 谁该管 | 说明 |
| --- | --- | --- |
| Harbor 自己的数据 | 这条原则管 | 运行数据、日志、会话、记忆、备份、缓存 |
| 第三方工具的产物 | 各自工具的约定 | 例如 CLI 自己写进用户目录的配置，Harbor 不强行改它 |
| 操作系统必须管理的数据 | 系统 | 注册表、系统服务、系统级缓存 —— 挪了会坏 |

「不堆 C 盘」指的是**第一类**。把它机械化成「什么都不能在 C 盘」，会去动后两类，
那不是本地优先，那是破坏。

**现状**：见下面「覆盖情况」一节 —— 这条**部分由代码保障**，但缺「用户指定目录」这个入口。

## 3. 模型选择自由

**原则**：保留 Harbor **独立的 Agent 内核**（不做某个厂商客户端的壳）；
支持 DeepSeek 与 ChatGPT/Codex；**默认由用户手动选择 Provider**。

多模型**自动协作**和**自动切换**属于**用户主动启用的可选模式**，
不是默认行为 —— 装上升级完就变成两个模型一起干活，是错的。

**现状**：双模型协作默认关（代码保障）；失败降级默认开（**这是缺口**，见下）。

## 4. 可靠性与数据保护

**原则**：功能重在实际价值和**可靠性**，不在数量。重视真实验证、任务恢复、
数据完整性、权限控制和可追溯性。**不得把尚未验证的结果报告为已完成。**

**和现有规范的关系**：这条与 `AGENT.md` 硬约束 7 **完全重合**，措辞一致 ——
这里只是把它归到「长期方向」里，避免它被当成某一批活的一次性要求。

## 5. 开发自主性

**原则**：在用户明确授权的范围内，Agent 可以自主使用 Shell、修改代码、运行测试、
处理相关小问题。**长期原则不能被解释成额外的全局工具限制**，
也不能覆盖用户当前明确授予的执行权限。

**为什么单列**：这条是防**反向**误用的。`electron/core/user-constraints.cjs` 会把
「只分析」「先别动」这类说法判成整轮只读 —— 那是**用户当场说的**，该生效；
但**没人说的时候**，不该因为「原则里讲了稳妥」就自己把工具关掉。

## 还差什么（后续独立开发决策，不在本次文档工作里改）

**缺口 1 · 没有「用户指定数据目录」的入口。**
`paths.cjs` 的 `dataDir()` **写死** `<root>/data`，找不到任何「用户把数据放别处」的开关：
它唯一读的环境变量是 `HARBOR_UNIT_TEST_DATA_DIR`，而那个只在测试态生效、
且必须落在 `data/harbor-test/runs/` 里面（往外就抛错）—— 它不是产品入口。
后果：想放到**另一个磁盘**的用户只能把整个程序挪过去，没有「数据放 E 盘、程序留 D 盘」这条路。

**缺口 2 · 「不落 C 盘」的检查比原则窄，而且只报警不拦。**
`auditNonC()` 列了 5 项（运行数据 / 日志 / 会话 / 工作目录 / 对话目录），
但这 5 项里后四者全是 `data/` 的子目录，所以**覆盖面本身是完整的**
（`backups` / `events` / `errors` / `crash` 等也都在 `data/` 下，跟着一起被覆盖）。
真正的两点不足：

- **判据只有盘符**：比对的是 `c:\` 前缀。D 盘上的系统位置、UNC 路径、符号链接指向
  C 盘这些情形都识别不了 —— 判据是「盘符是不是 C」，不是「是不是系统位置」。
- **只报警不拦**：`electron/main.cjs` 启动时对它命中的项只 `log.error` 一行，
  照样启动；自检里也只落到 `audits[].ok`。也就是说违反这条原则**不会被挡住**。
  这是有意的（拦了用户就起不来），但要知道它只是**报告**，不是**保障**。

**缺口 3 · 失败降级默认开着，且会换到另一个 provider。**
`config-defaults.cjs` 里 `fallback.enabled` 默认 `true`，`loop-model.cjs` 会在失败后
挑第一个「有 key 且提供同一模型」的 provider 继续。这与「自动切换属于用户主动启用」
有张力。**要说清区别**：它**不换模型**、只在同模型下换 provider，属于故障转移而非
多模型协作；但它确实是默认开着的自动行为，用户没主动启用过。
改不改、改成什么默认值，是产品决定，不在本次范围内动。

> 与 `README.md` 的「后续计划 → 在试」那段**不冲突**：那里说的「让它自己挑用哪个模型，
> 这个开关现在是关着的」指的是**模型路由**（`config.router.enabled = false`），
> 与本条缺口（**故障降级** `fallback`）是两套机制，别混。改的时候别只看一处。

**缺口 4 · 「第三方工具产物 / 系统必须管的数据」没有任何文档写过。**
这三类的区分目前只在本文件里 —— 如果后续要实现「可选数据目录」，
需要先定清哪些目录跟着搬、哪些不搬（比如 `data/chromium` 跟着搬，第三方 CLI 的配置不搬）。
