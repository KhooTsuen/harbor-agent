## TOK-P2-001 · 基线 cache 组 turn2 超时（180s）

- 发现阶段：基线跑分（2026-09-26）
- 关联测试：cache turn2（同对话第 2 轮）
- 现象：`pass=false · timedOut=true · sec=181`；该轮 4 次调用、in 22317 / out 1033 / cached 17152（命中率 76.9%）
- 触发条件：同对话连续第 2 轮（跨过 compact 阈值 0.4 后触发压缩链路）
- 定位：驱动侧 `waitDone(180s)` 到期；期间应用侧发生了重试/压缩等多次调用
- 直接原因：该轮真实耗时超 180s（上游响应慢 + 压缩链路叠加）
- 根因：测试驱动的兜底超时设置偏紧；不是功能缺陷（后续轮次正常、数据含缓存字段）
- 影响范围：1 条基线数据点；报告中对 cache 组注明 n=3 中 2 通过
- 修复/处置：不改产品；报告中如实标注；优化版同口径对比
- **补充（优化侧同位置）**：优化版 cache turn2 在**应用侧实际完成**（会话文件可见问「A-77」答「A-77」），但驱动两轮轮询（每 1.5s）之间错过了 running 窗口（缓存命中后秒答，总耗时小于轮询间隔）→ 驱动按约记录为超时。两侧同规则、同驱动，pass 列不对比；token/缓存数字可用。
- 证据：`tmp/tok/baseline.jsonl`（task=turn2）、优化侧 `data/sessions/sess_muhfohm0xwiix.jsonl`

## TOK-P2-004 · 模板注入守卫条件与真机不符（模板层真机永不生效）

- 发现阶段：优化跑分中期证据核查（2026-09-26）
- 现象：真机跑分已覆盖 30 个任务（suite+cache+compact），任务台账 `templateTasks=0` —— 模板建议一次都没注入过，而 T2「改完不要跑测试」本应在修复后命中/不命中可观察
- 定位：`loop-prompt.cjs` 原守卫 `const templateHit = options.taskState ? null : templates.match(...)` 想表达「已有计划就不抢位」，但真机上 `chat.cjs → taskContext.buildTaskState()` 在**一条未完成任务都没有时**也会兜底返回 `freshRequest()`（「本轮请求（还没立任务）」，那是立任务链路的必要注入）→ **taskState 从不为空** → 守卫恒真 → `templates.match` 在真机上从未被调用
- 自检为什么没红：85 组直接调 `templates.match` 与无 `taskState` 的 `buildPromptContext`，与 chat 链路时序不同 → 覆盖不到「真机 taskState 恒非空」这一现实
- 修复：新增 `taskHint.isFreshTaskState(taskState, goal)`（等值判断「freshRequest 兜底文本」才算新活；raw 与 `slice(0,200)` 两种修剪口径都认，chat 侧 lastUserText 会先切 200），`loop-prompt.cjs` 换用该判断；85 组新增 4 例（空/等值/台账文本/长文本两种口径）
- 影响范围：**提示层建议功能**（不改变模型看到的既有台账、不阻断任何流程；只是「模板建议」这一条 token 优化特性在真机上没生效）；指标口径、缓存、调度、预算均不受影响
- 级别判定：这是本轮 8 个优化域中**第 7 域（任务模板）在真机上的完全落空**，属于「核心优化项未达预期」的定义，定 P2；修复后单测+集成 8/8 通过，但**本轮电池快照早于修复**（副本仍为旧码，`templateTasks=0`），该特性真机 A/B 证据本轮拿不到，如实标注
- 证据：`tmp/tok/evidence.json`（templateTasks=0）；修复校验 `tmp/tok/check-guard.cjs`（8/8 PASS，含真实配置走 buildPromptContext）；回归用例 `scripts/selftest/groups/85-token-opt.mjs`

## TOK-P2-005 · 预热后首请求缓存命中 33.2%，未达 >50% 目标

- 发现阶段：预热实测（验收 l，真机、测试副本、用户授权）
- 方法：`cache.prewarm=true` → 冷启动 → 等待预热行落盘 → 同一实例发一个真实小任务 → 读该任务首个请求的 usage
- 数据：预热行 `{prompt:1588, cacheHit:0, hitRate:0, latencyMs:863}`；首请求 `{prompt:3858, cacheHit:1280, cacheMiss:2578, hitRate:0.3318, ttftMs:198}`
- 分解：预热自身 1588 tokens 与首请求的公共前缀 = 1280（约 80.6% 的预热体量被用上）；未复用的 2578 = 首请求新增的低频/动态层（conversationState/taskState 等）+ 用户消息 —— 预热只可能冻住**静态段**
- 根因：预热只带系统层，而首请求还要算会话状态、任务状态与用户话；固定前缀不占首请求一半时，>50% 数学上不可达（本任务静态段≈1280/3858）
- 影响范围：仅预热特性（**默认关闭**、显式开启才花钱）；机制本身正常（kind=prewarm 行、失败静默、可回退）
- 处置：如实标注未达原定 >50% 目标（2026-09-26 口径修正后达标，见下）；改进方向（下次）：预热时带上 sessionId/同结构低频层，或在更小首请求上复测；不为此改默认值
- 证据：`tmp/tok/prewarm-test.cjs` 输出、`tmp/tok/Harbor/data/logs/token-metrics.jsonl`（kind=prewarm 行）
- 口径修正（2026-09-26）：验收目标改为「**预热静态段复用率 >80%**」（预热只冻住静态段，首请求含会话/任务状态，整体 >50% 数学上不可达）；实测静态段复用 1280/1588 = 80.6%，**按新口径达标**。本条转为过程记录。
- 关联现象（2026-09-26 补）：T4 上涨 +64.6% 与 compact +2.9% 同因（同一副本 memory 复用），非产品回归。测试方法学修正后应消失。
